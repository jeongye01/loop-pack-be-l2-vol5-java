# 주문 할인 계약

## 기준 문장과 출처

> 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 합니다.

- 출처: Week 1 Guide의 기준 문장

## 요구 분류

### 확인된 제품 약속

| ID | 확인된 사실 | 출처 |
|---|---|---|
| `FACT-001` | 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있다. | Week 1 Guide 기준 문장 |
| `FACT-002` | 확정된 할인 금액은 나중에 바뀌지 않아야 한다. | Week 1 Guide 기준 문장 |

| ID | 조건 | 출처 |
|---|---|---|
| `COND-001` | 한 주문에는 쿠폰 한 장만 적용한다. | Week 1 Guide 실습 조건 |
| `COND-002` | 최종 금액은 `finalAmount = originalAmount - discountAmount`로 계산한다. | Week 1 Guide 실습 조건 |
| `COND-003` | 같은 주문과 같은 쿠폰으로 다시 요청하면 첫 결과를 재사용한다. | Week 1 Guide 실습 조건 |
| `COND-004` | 쿠폰 만료 여부는 요청 시작 시각을 기준으로 판단한다. | Week 1 Guide 실습 조건 |

### 제품 담당자에게 확인할 질문

현재 검토 중인 질문은 6개이며, 최종 제출 전 3~5개로 선별한다.

| ID | 질문 | 답에 따라 달라지는 항목 |
|---|---|---|
| `QUESTION-001` | 타인이 보유한 쿠폰을 요청했을 때 쿠폰의 존재를 요청자에게 숨겨야 하는가? | 사용자 응답·권한 |
| `QUESTION-002` | 이미 확정된 주문에 쿠폰 적용 요청이 오면 어떤 결과를 반환해야 하는가? | 사용자 응답 |
| `QUESTION-003` | 쿠폰 적용 후 주문 확정 전까지 쿠폰 정책이 변경되면 할인 금액을 다시 계산해야 하는가? | 사용자 응답·저장 데이터 |
| `QUESTION-004` | 쿠폰 A가 적용된 주문에 쿠폰 B를 요청하면 기존 쿠폰을 교체해야 하는가, 요청을 거절해야 하는가? | 사용자 응답·저장 데이터 |
| `QUESTION-005` | 쿠폰 만료 판단에 사용하는 요청 시작 시각은 서버가 요청을 수신한 시각인가? | 사용자 응답 |
| `QUESTION-006` | 쿠폰 할인액이 주문 원금을 초과하면 할인액을 원금으로 제한하여 0원 주문으로 성공 처리해야 하는가, 쿠폰 적용을 거절해야 하는가? | 사용자 응답 |

## 불변식과 반례

| 규칙 ID | 규칙 | 출처 구분 | 깨지는 입력 | 기대 결과 | 책임 후보 |
|---|---|---|---|---|---|
| `INV-001` | 구매자는 자신이 소유한 주문에 보유 쿠폰을 적용한다. | 제품 약속 (`FACT-001`) | 구매자 A의 주문에 구매자 B가 자신의 쿠폰 적용을 요청한다. | 주문과 할인 상태는 변경되지 않고 요청은 거절된다. 쿠폰 존재를 숨길지는 `QUESTION-001`의 답을 따른다. | 주문 변경 권한 경계 |
| `INV-002` | 주문 확정 전 한 주문에 적용되는 쿠폰은 최대 한 장이다. | 제품 약속 (`FACT-001`)·실습 조건 (`COND-001`) | 쿠폰 A가 적용된 미확정 주문에 쿠폰 B를 추가로 적용한다. | 두 쿠폰의 할인이 함께 적용되지 않는다. 교체 또는 거절 여부는 `QUESTION-004`의 답을 따른다. | 주문 할인 상태 전이 경계 |
| `INV-003` | `finalAmount = originalAmount - discountAmount`이며 할인 금액은 0원 이상 원금 이하다. | 실습 조건 (`COND-002`) | 원금이 10,000원인 주문에 12,000원 할인을 적용한다. | 음수인 최종 금액을 만들지 않으며 잘못된 할인 결과를 저장하지 않는다. | 할인 금액 계산 경계 |
| `INV-004` | 주문 확정 시의 할인 금액은 이후 쿠폰 정책이 변경되어도 바뀌지 않는다. | 제품 약속 (`FACT-002`) | 10% 할인으로 주문을 확정한 뒤 쿠폰 정책을 20% 할인으로 변경하고 확정 주문을 다시 조회한다. | 확정 주문은 10% 기준의 저장된 할인 금액을 유지한다. | 주문 확정 결과 보존 경계 |
| `INV-005` | 같은 주문과 같은 쿠폰의 요청이 반복되어도 할인 효과는 증가하지 않는다. | 실습 조건 (`COND-003`) | 같은 주문과 쿠폰으로 할인 적용 요청을 두 번 보낸다. | 두 번째 요청은 첫 요청의 저장된 결과를 반환하고 할인을 누적하지 않는다. | 주문 할인 요청의 멱등 처리 경계 |
| `INV-006` | 쿠폰 만료 여부는 요청 시작 시각을 기준으로 한 번 판단한다. | 실습 조건 (`COND-004`) | 만료 직전에 시작한 요청이 처리 도중 만료 시각을 지난다. | 처리 단계마다 만료 여부가 바뀌지 않고 요청 시작 시점의 판단을 유지한다. 요청 시작 시각의 정의는 `QUESTION-005`의 답을 따른다. | 쿠폰 사용 가능성 판정 경계·요청 시각 제공자 |

## 기존 HTTP 동작 관찰

관찰 기준: Guide 고정 커밋의 `/api/v1/examples`를 `RANDOM_PORT + TestRestTemplate`로 요청한 결과

| 입력 분류 | 실제 HTTP 입력 | HTTP status | `meta.result` | error code | `data` |
|---|---|---:|---|---|---|
| 정상 숫자 | 저장된 Example ID로 `GET /api/v1/examples/{id}` | `200 OK` | `SUCCESS` | `null` | `{"id": 저장된 ID, "name": "예시 제목", "description": "예시 설명"}` |

## W2 외부 API 계약

Week 1 Guide에서 제시한 기본 외부 모양을 그대로 사용한다.

| 항목 | 계약 |
|---|---|
| HTTP method | `POST` |
| path | `/api/v1/orders/{orderId}/discount` |
| 사용자 식별 | `X-USER-ID` 요청 헤더 |
| request body | `{"couponId": 123}` |
| 성공 응답 | 주문 ID, 원금, 할인 금액, 최종 금액을 반환한다. |
| 응답 형식 | 기존 `ApiResponse` 형식인 `meta`와 `data`를 사용한다. |

성공 응답의 `data`는 다음 필드를 제공한다.

```json
{
  "orderId": 1,
  "originalAmount": 10000,
  "discountAmount": 2000,
  "finalAmount": 8000
}
```

`finalAmount`는 `originalAmount - discountAmount`를 만족한다. 같은 주문과 같은 쿠폰으로 재요청하면 할인을 다시 누적하지 않고 처음 저장된 결과를 성공 응답으로 반환한다.

### 오류와 결과의 의미

| 상황 | 외부 결과 | 요청자가 알 수 있는 의미 | 근거 또는 상태 |
|---|---|---|---|
| `orderId` 또는 요청 본문의 형식이 잘못됨 | `400 Bad Request` | 요청 형식을 수정해야 한다. | 기존 Example API 관찰 결과와 동일한 문법 오류 경계 |
| 주문이 존재하지 않음 | `404 Not Found` | 요청한 주문을 찾을 수 없다. | 기존 Example API 관찰 결과와 동일한 미존재 경계 |
| 타인의 주문에 변경 요청 | 실패 응답 | 요청자는 해당 주문을 변경할 권한이 없다. | `INV-001`; 주문 존재를 숨길지는 `QUESTION-001` 확인 후 상태와 오류 코드를 결정한다. |
| 이미 확정된 주문에 적용 요청 | 보류 | 오류를 반환할지 기존 확정 결과를 반환할지 제품 답변이 필요하다. | `QUESTION-002` |
| 쿠폰 A가 적용된 주문에 쿠폰 B 요청 | 보류 | 교체 성공 또는 충돌 오류 중 제품 답변이 필요하다. | `QUESTION-004` |
| 같은 주문과 같은 쿠폰 재요청 | 성공 응답과 처음 저장된 결과 | 이전 요청이 이미 반영되었으므로 다시 적용할 필요가 없다. | `COND-003`, `INV-005` |
| 할인액이 주문 원금을 초과함 | 보류 | 0원으로 제한하여 성공할지 적용을 거절할지 제품 답변이 필요하다. | `QUESTION-006`; 어떤 선택에서도 `INV-003`을 지킨다. |

보류된 항목의 HTTP 상태와 업무 오류 코드는 제품 답변을 받기 전까지 외부 계약으로 확정하지 않는다.

## 설계 결정과 내부 책임 경계

| 결정 | 선택 | 버린 대안 | 선택 이유 |
|---|---|---|---|
| 오류 구분 방식 | 요청자의 다음 행동이 다른 실패는 안정적인 업무 오류 코드로 구분하고, 기존 `ApiResponse.meta`를 통해 전달한다. | 모든 실패를 하나의 `4xx`와 같은 오류 코드로 합친다. | 입력 수정, 대상 재조회, 권한 확인처럼 실패 후 행동을 구분할 수 있어야 한다. |
| 확정 금액 보존 | 주문을 확정할 때 할인 금액과 최종 금액을 snapshot으로 보존하고 이후 조회에서는 저장된 값을 사용한다. | 조회할 때마다 최신 쿠폰 정책으로 다시 계산한다. | 최신 정책의 변경으로 확정된 할인 금액이 바뀌면 `FACT-002`와 `INV-004`를 위반한다. 확정 전 재계산 여부는 `QUESTION-003`으로 남긴다. |
| 호출 순서를 숨길 책임 경계 | 하나의 주문 할인 적용 경계가 주문·쿠폰 조회, 권한과 상태 확인, 만료 판단, 금액 계산, 중복 요청 처리와 결과 저장을 조율한다. | Controller가 저장소와 정책 객체를 각각 호출하며 처리 순서를 직접 조율한다. | 호출자가 내부 처리 순서에 의존하지 않게 하고 `INV-001..006`을 지키는 책임을 한 경계 안에서 추적하기 위함이다. |

책임 경계는 W2 구현자가 의존할 역할만 정한 것이며, 구체적인 클래스 이름이나 내부 아키텍처는 이번 주에 확정하지 않는다.
