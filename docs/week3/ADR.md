# 3주차 동시성 설계 ADR

## ADR-001. Product와 Stock의 잠금 범위를 분리한다

- **상태**: 결정 (2026-10-08)
- **범위**: 주문 생성·확정·포인트 충전·좋아요 등록·관리자 상품/재고 변경·브랜드 삭제가 동시에 실행되는 경우
- **갱신**: 2026-10-09, 상품 생성의 브랜드 공유락 추가 (`7017661`), 주문 생성의 상품 공유락·충전 재시도 제거·브랜드 수정 낙관적 락 반영

Product와 Stock이 묶여 있으면 재고 차감에도 Product 행을 배타적으로 잠글 수 있다. 분리하면 Product는 공유락으로 삭제·수정과의 순서를 조정하고, Stock만 배타락으로 잠글 수 있어 재고 경합을 Stock 행에 집중할 수 있다.

| 대상 | 잠금 |
| --- | --- |
| Brand | 상품 생성 시 `PESSIMISTIC_READ`, 수정 시 `@Version`(재시도 없음), 삭제 시 `PESSIMISTIC_WRITE` |
| Product | 주문 생성·확정·좋아요·재고 확인 `PESSIMISTIC_READ`, 수정·삭제 `PESSIMISTIC_WRITE` |
| Stock | `PESSIMISTIC_WRITE` 배타락 |
| Point | `@Version` 낙관적 충돌 검사 |
| Order | `@Version` 낙관적 충돌 검사 |

주문 확정은 Product를 `PESSIMISTIC_READ`로 확인하고 Stock을 `PESSIMISTIC_WRITE`로 차감한다. Product 수정·삭제는 `PESSIMISTIC_WRITE`로 주문 확정과의 순서를 조정한다. Point 충전은 `@Version` 충돌 시 롤백하고 자동 재시도하지 않는다. 주문 확정은 Point 차감까지 포함한 전체 트랜잭션을 2회까지 새 트랜잭션으로 재시도한다.

관리자 재고 변경도 Product `PESSIMISTIC_READ` → Stock `PESSIMISTIC_WRITE` 순서를 사용한다. Product 공유락은 삭제된 상품의 재고 변경을 막고 삭제와의 순서를 보장하며, Stock 배타락은 주문 확정과 재고 수량 갱신이 겹칠 때 갱신 유실과 음수 재고를 막는다.

좋아요 등록은 Product `PESSIMISTIC_READ`로 활성 상품을 확인한 뒤 Like를 저장한다. 상품 삭제가 등록 중간에 끼어드는 것을 막고, 삭제 완료 후에는 새 좋아요를 거절한다.

포인트 충전은 주문 확정과 별도 경로이므로 Point의 `@Version`을 사용한다. 사용자 잔액에 대한 동시 변경을 민감한 충돌로 보고, 버전 충돌이 발생한 충전은 전체를 롤백해 실패로 처리한다. 서버가 최신 잔액으로 자동 재시도해 충전을 완료시키지는 않는다. 동시 요청이 시간상 겹쳤다는 이유만으로 모두 거절하는 것은 아니며, 실제 버전 충돌이 발생한 요청을 실패시킨다.

브랜드 수정은 Brand를 일반 조회하고 `@Version`으로 동시 변경을 감지한다. 충돌한 수정은 롤백하고 자동 재시도하지 않는다. 주문에는 브랜드 이름을 저장하지 않으므로 브랜드 이름 수정과 주문 처리를 직렬화하지 않는다. 브랜드 삭제는 Brand와 연결 Product를 `PESSIMISTIC_WRITE`로 잠가 주문 생성·확정과 상품 삭제의 순서를 맞춘다. Brand의 버전은 삭제 시에도 증가하므로 삭제 전에 읽은 오래된 수정 요청이 삭제 상태를 덮어쓰지 못한다. Product 수정은 배타락을 사용하며 Product에는 별도 낙관적 버전을 두지 않는다.

상품 생성은 Brand를 `PESSIMISTIC_READ`로 읽고 활성 여부를 확인한다. 일반 조회만 사용하면 활성 브랜드를 확인한 뒤 브랜드 삭제가 완료되고, 뒤늦게 활성 상품이 저장될 수 있다. 브랜드 공유락을 생성 트랜잭션 종료까지 유지해 브랜드 삭제의 배타락과 순서를 맞춘다. 공유락끼리는 호환되므로 같은 브랜드의 상품 생성 요청을 이 락만으로 모두 직렬화하지는 않는다.

주문 생성도 Product를 `PESSIMISTIC_READ`로 조회한다. 상품의 활성 여부를 확인하고 이름·가격을 주문 품목에 복사한 뒤 DRAFT를 저장할 때까지 수정·삭제가 끼어들지 않게 한다. 공유락은 주문 생성끼리 호환되며 생성 중 Stock·Point는 잠그거나 변경하지 않는다. 생성 트랜잭션이 끝난 뒤 상품 변경은 허용하고, 주문에는 생성 당시 이름·가격을 유지한다. 현재 OrderItem에는 브랜드 이름을 저장하지 않으므로 주문 생성에서 Brand 잠금은 추가하지 않는다.

상품명·가격은 주문 품목에 보존되므로 Product soft delete 이후에도 기존 주문 정보는 유지된다.

### 대안 검토

- **낙관적 락**: 인기 상품과 경합 수준을 미리 알 수 없고, 충돌 시 재시도가 늘어 요청 부하와 지연 시간이 커질 수 있다.
- **조건부 갱신**: 재고 한 행에는 적용할 수 있지만, 재고·포인트·주문 상태를 함께 변경할 때 영향 행 수 해석과 JPA 상태 동기화를 별도로 관리해야 한다.
- **선택 이유**: Stock 차감은 비관적 락으로 직렬화하고, Product·Brand의 공유락/배타락으로 읽기와 수정·삭제의 순서를 맞춘다. Point·Order·Brand 수정은 버전으로 충돌을 감지하며, 자동 재시도는 주문 확정에만 적용한다.

`.handoff/lock-api-checklist.md`의 목록을 현재 구현과 대조해 정리했다. 아래의 “별도 잠금 조회 없음”은 명시적인 locking read가 없다는 뜻이며, INSERT·UPDATE 시 DB 내부 잠금까지 없다는 뜻은 아니다.

| 주문 확정 | Product 공유락 → Stock 배타락, Point·Order `@Version` | **상품:** 주문끼리 읽기는 허용하되 확정 중 수정·삭제를 막는다.<br>**재고:** 인기 상품에 주문이 몰려도 즉시 충돌로 거절하기보다, 앞선 요청을 기다린 뒤 남은 재고로 구매를 진행한다.<br>**포인트:** 잔액 충돌 시 서버가 최신 잔액으로 전체 확정 트랜잭션을 최대 2회 재시도한다.<br>**주문:** 같은 주문은 한 번만 확정하고, 나머지는 재시도에서 변경된 상태를 확인해 `ORDER_ALREADY_CONFIRMED`로 안내한다. |
| 포인트 충전 | Point `@Version`, 자동 재시도 없음 | 사용자 잔액을 동시에 변경하는 요청을 민감하게 보고, 버전 충돌이 발생한 충전은 롤백하고 실패로 처리한다. 서버가 자동 재시도해 충전을 완료시키지 않는다. |
| 좋아요 등록 | Product 공유락, Like의 사용자·상품 복합 유니크 제약 | 활성 상품 확인과 등록 사이에 상품 삭제가 끼어들지 않게 한다. 좋아요 관계 중복은 공유락이 아니라 DB 유니크 제약으로 막는다. |
| 관리자 상품 생성 | Brand 공유락 | 활성 브랜드 확인부터 상품·재고 저장 완료까지 브랜드 삭제가 끼어들지 않게 한다. |
| 관리자 상품 수정 | Product 배타락 | 상품명·가격 변경과 주문 확정·삭제의 실행 순서를 맞춘다. |
| 관리자 상품 삭제 | Product 배타락 | 상품을 확인하고 처리하는 주문 확정·좋아요 등록·재고 변경과 삭제의 순서를 맞춘다. |
| 관리자 재고 변경 | Product 공유락 → Stock 배타락 | 삭제된 상품의 재고 변경을 막고, 주문 차감과 관리자의 최종 수량 설정이 겹칠 때 갱신 유실을 막는다. |

| 관리자 브랜드 삭제 | Brand 배타락 → 연결 Product 배타락 | 주문 생성·확정과 브랜드의 연결 상품 삭제를 직렬화해, 주문 처리 중 상품이 삭제되지 않도록 한다. 주문의 Product 공유락과 삭제의 Product 배타락으로 순서를 맞춘다. Brand 배타락은 상품 생성·다른 삭제와의 순서도 보호하고, 오래된 브랜드 수정은 버전으로 감지한다. 브랜드·상품 삭제는 함께 commit·rollback한다. |


### 잠금 순서와 재시도 경계

- 주문 생성은 중복 상품 ID를 제거한 뒤 ID 오름차순으로 Product를 공유락 조회하고, 주문 품목은 기존 요청 순서와 중복 품목 합산 계약을 유지한다. 주문 확정은 Product ID 오름차순으로 Product를 조회한 뒤 같은 순서로 Stock을 잠근다. 관리자 재고 변경도 Product → Stock 순서를 따른다.
- 브랜드 삭제는 Brand를 먼저 잠그고 연결 Product를 ID 오름차순으로 잠근다. 상품 생성도 Brand를 먼저 잠근다.
- 비관적 잠금은 해당 트랜잭션 종료까지 유지한다. 외부 API 호출 등 긴 작업을 잠금 구간에 추가하지 않는다.
- HTTP 호출처럼 기존 트랜잭션이 없는 경로에서는 주문 확정의 낙관적 충돌 시 `REQUIRES_NEW` 트랜잭션으로 처음부터 최대 2회 다시 실행한다. 충전은 재시도 횟수를 0으로 지정해 트랜잭션을 한 번만 실행하고 충돌 예외를 전달한다. 이미 트랜잭션이 있는 호출은 그 트랜잭션에 참여하며 내부 재시도하지 않는다.
- 브랜드 수정은 Spring 프록시를 거치는 `@Transactional` 메서드를 한 번만 실행한다. flush·commit 시 버전 충돌이 발생하면 롤백하고 예외를 전달하며, 재시도 실행기는 사용하지 않는다.
- 재시도와 rollback은 재고·포인트·주문 상태를 하나의 결과로 다루기 위한 장치다. 락의 성능뿐 아니라 사용자가 성공·거절·재시도 중 어떤 결과를 받는지도 선택 기준으로 삼는다.

### 상품 생성과 브랜드 삭제 경합의 추가 검증

`7017661`에서 `ProductUseCase.create`의 브랜드 확인을 `BrandRepository.findForProductCreate`로 바꾸고 `PESSIMISTIC_READ`를 적용했다. [BrandProductConcurrencyTest](../../apps/commerce-api/src/test/java/com/loopers/product/application/BrandProductConcurrencyTest.java)에서 실제 MySQL과 독립 트랜잭션으로 두 실행 순서를 확인했다.

- **삭제가 먼저 잠금을 획득**: 상품 생성은 삭제 트랜잭션 종료까지 기다린 뒤 `BRAND_NOT_FOUND`로 거절된다. 상품·재고는 저장되지 않는다. 수정 전에는 이 시나리오에서 상품 생성이 성공하는 문제를 재현했다.
- **생성이 먼저 잠금을 획득**: 브랜드 삭제는 생성 트랜잭션 종료까지 기다린 뒤 새로 생성된 상품까지 함께 삭제한다. 브랜드·상품은 삭제 상태이고 재고 기록은 보존된다.

두 테스트와 관련 통합 테스트·ArchUnit·Checkstyle이 통과했으며, 푸시 전 `./gradlew :apps:commerce-api:check`도 통과했다. 기존 SQL 관찰 기록은 [잠금 SQL 검증 기록](./lock-sql-verification.md)에 정리되어 있다. 상품 생성의 Brand 공유락은 이번 추가 테스트와 코드 매핑으로 확인했으며, 기존 SQL 관찰 표에는 아직 포함되지 않는다.

### 주문 생성의 Product 공유락 검증

[OrderCreationConcurrencyTest](../../apps/commerce-api/src/test/java/com/loopers/order/application/OrderCreationConcurrencyTest.java)는 실제 MySQL과 독립 트랜잭션으로 다음을 검증한다. 저장 전 대기는 테스트의 저장소 spy에만 두며 production 코드에는 추가하지 않는다.

- 상품을 확인한 뒤 DRAFT 저장 직전에 생성 요청을 멈추면, 상품 수정·삭제는 생성 완료까지 기다린다. 생성된 주문은 당시 이름·가격을 보존하고 재고·잔액은 유지한다.
- 상품 삭제가 먼저 잠금을 획득하면 주문 생성은 삭제 완료 후 `PRODUCT_NOT_FOUND`로 거절되고 DRAFT를 남기지 않는다.
- 서로 다른 주문 생성 두 건은 같은 Product의 공유락을 함께 획득할 수 있다.
- 중복 상품은 ID 오름차순으로 한 번씩 잠그되 품목의 요청 순서와 중복 수량 합산은 유지한다.

공유락 적용 전에는 앞의 수정·삭제 경합 세 사례가 모두 실패하는 것을 확인했다. 적용 후에는 위 테스트 5건과 관련 주문·브랜드 HTTP/통합/트랜잭션/동시성 회귀 테스트, ArchUnit, main·test Checkstyle이 통과했다.

[BrandUpdateConcurrencyTest](../../apps/commerce-api/src/test/java/com/loopers/brand/application/BrandUpdateConcurrencyTest.java)의 두 사례도 통과했다. 같은 버전을 읽은 두 수정은 성공 1·낙관적 충돌 1이며 자동 재시도하지 않는다. 브랜드 조회 뒤 삭제가 먼저 완료된 경우 오래된 수정은 충돌하고 브랜드·연결 상품의 삭제 상태를 유지한다. [PointChargeConflictTest](../../apps/commerce-api/src/test/java/com/loopers/user/application/PointChargeConflictTest.java)는 테스트 저장 경계에서 낙관적 충돌을 유발해 충전 저장이 한 번만 실행되고 잔액 변경이 롤백되는지 확인했다.
