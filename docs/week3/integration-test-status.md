# 3주차 통합 테스트 현황

기준: [3주차 과제](../../.handoff/week3-과제.md). 아래의 "기존"은 현재 테스트 코드에 있는 검증이며, 3주차 과제의 완료를 뜻하지 않는다.

| 흐름 | 기존 검증 | 추가할 검증·작업 |
| --- | --- | --- |
| 브랜드 삭제 | 브랜드·연결 상품 일괄 삭제, 다른 브랜드·상품·과거 주문 보존. HTTP에서 삭제 상품 고객 상세 제외 확인. 재삭제 거절도 검증 | 브랜드 삭제 경로에서 고객 목록·좋아요·새 주문·관리자 수정/재고 변경 제한 및 기존 좋아요 취소 확인 |
| 브랜드 중간 실패 | 없음 | 실제 변경 SQL을 보낸 뒤 다음 저장에서 예외를 주입하고, 서비스 트랜잭션 종료 후 별도 DB 조회로 브랜드·상품 전체 rollback 확인 |
| 주문 확정 | 단일 주문의 성공 시 재고·잔액 저장, 재고·포인트 부족 시 거절. HTTP에서 결제 결과·재확정·삭제 상품 거절 확인 | 여러 품목의 확정 결과를 새 DB 경계에서 확인. 실제 변경 뒤 예외를 주입해 DRAFT·재고·잔액·결제 결과 전체 rollback 확인 |
| 동시 변경 | 없음 | 갱신 유실 대조군과 실제 서비스의 재고 경쟁(5개/8건), 포인트 경쟁(10,000원/4,000원 3건), 충전·결제 경쟁 검증. 요청 결과별 집계와 최종 DB 수량·잔액 비교 |

현재 `BrandUseCase.delete()`는 `BrandRemovalService`를 호출해 브랜드와 연결 상품을 같은 트랜잭션에서 논리 삭제한다. `OrderUseCase.confirm()`에는 트랜잭션이 있지만 재고·포인트·주문을 보호하는 잠금이나 조건부 갱신은 없다.

## 테스트 경계와 마무리

- 기존 `BrandUseCaseIntegrationTest`·`OrderUseCaseIntegrationTest`는 테스트 클래스에 `@Transactional`이 있다. 3주차 rollback·경쟁 검증은 준비 데이터를 먼저 commit하고, 서비스 트랜잭션 종료 후 새 경계에서 조회한다.
- 동시성 테스트 전략과 잠금 방식은 별도로 결정한다. 선택 후 주문 확정뿐 아니라 포인트 충전·관리자 재고 변경 경로에도 같은 보호 규칙을 적용한다.
- 브랜드 삭제와 주문 확정의 대표 HTTP 성공·실패 및 관리자·사용자 접근을 확인한다. 영향받는 기존 테스트, Checkstyle·ArchUnit을 포함한 `:apps:commerce-api:check`를 실행한다.
- 설계 문서에 트랜잭션 시작점·호출 경로·예외·잠금 순서와 선택 이유를 반영하고, 기술 글을 작성한다.
