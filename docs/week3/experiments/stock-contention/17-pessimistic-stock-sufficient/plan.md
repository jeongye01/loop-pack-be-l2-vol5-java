# 동시성 실험 계획서: 충분한 재고에서 비관적 재고 잠금

- 실험 ID: 17
- 상태: 계획
- 기준 커밋: `d46d3d8` (`Point`·`Stock` 분리 직후, 잠금 전략 미적용)
- 변경 전략: `Stock` 조회에 JPA `PESSIMISTIC_WRITE` 적용
- 공통 절차·결과 형식: [프로토콜](../../protocol.md)
- 공통 시스템 스펙·시나리오: [재고 경쟁 실험](../README.md)

## 질문

재고가 충분해 품절 거절이 발생하지 않는 인기 상품 집중 부하에서, 재고 행에 비관적 쓰기 잠금을 적용했을 때 처리량과 응답 시간이 어떻게 나타나는지 확인한다. 재고 부족으로 요청이 빠르게 종료되는 효과를 제거하고 잠금 경합 자체를 비교한다.

## 실험 조건

- 대상 API: `POST /api/v1/orders/{orderId}/confirm`
- 시나리오: S1. 모든 주문이 상품 A 1개를 구매한다.
- 초기 재고: 각 Run의 계획 요청 수보다 크게 설정한다. L1 1,000개, L2 3,000개, L3 10,000개로 고정한다.
- 포인트: 모든 주문이 결제할 수 있도록 사용자별 잔액을 충분히 준비한다.
- 주문·사용자·상품 조합과 품목 순서는 고정 시드를 사용해 전략 간 재사용한다.
- 재시도: 사용하지 않는다. 데드락·잠금 대기 시간 초과·기술 오류는 성공으로 바꾸지 않고 별도 결과로 기록한다.
- 커넥션 풀: 최대 200, 최소 유휴 200, 획득 대기 3,000ms. MySQL `max_connections`는 300 이상으로 맞춘다.

## 부하 단계

| 단계 | 목표 RPS | 측정 시간 | 계획 요청 수 | 초기 A 재고 |
| --- | ---: | ---: | ---: | ---: |
| L1 | 10 | 60초 | 600 | 1,000 |
| L2 | 30 | 60초 | 1,800 | 3,000 |
| L3 | 100 | 60초 | 6,000 | 10,000 |

각 단계는 준비 실행 후 데이터를 초기화·커밋하고 3회 측정한다. 전체 측정은 9개 Run이다. 모든 Run에서 재고가 남아야 하므로 품절 거절은 기대값 0이다.

## 기록·검증

Run별로 Git SHA, 목표·실제 요청 수, 전체·성공·기술 오류 TPS, p50·p95·p99, 데드락·잠금 대기 시간 초과, 환경 스냅샷을 기록한다. 성공 주문 수와 실제 `stock.quantity`, 사용자 잔액, 주문 상태·결제 결과가 일치하는지 DB에서 검증한다.

HTTP 부하와 Run별 최종 DB 검증을 실행한다. 이 전략 비교에서는 이미 별도로 검증한 동시성 통합 테스트를 반복하지 않는다. 보고서는 실행이 끝난 뒤 실제 결과만 작성한다.
