## 고정 시스템 스펙

전략 외의 성능 변수를 줄이기 위해 실험군 안에서는 로컬 구성을 고정한다. 기존 01~04는 기본 풀 크기에서 실행했고, 새 실험군은 커넥션 풀이 잠금 경합보다 먼저 포화되지 않도록 별도 스펙을 사용한다.

| 항목 | 고정 조건 |
| --- | --- |
| 호스트 | 같은 Mac·Docker 자원 할당 |
| 애플리케이션 | 인스턴스 1개, 동일 Java 21 배포판·패치·JVM 옵션 |
| MySQL | 8.0 계열의 실제 버전·이미지·자원 설정·기본 격리 수준. 새 실험군은 `max_connections` 300 이상 |
| HikariCP | 기존 01~04: 최대 40·최소 유휴 30. 새 실험군: 최대 200·최소 유휴 200·획득 대기 3,000ms |
| Tomcat | 최대 스레드 200, 최소 유지 10(사용 중·유휴 포함) |
| 로그 | SQL 출력 끄기, 나머지 로그 수준 동일 |

기존 [JPA](../../../../modules/jpa/src/main/resources/jpa.yml)·[서버 설정](../../../../apps/commerce-api/src/main/resources/application.yml)을 기준으로 한다. 새 실험군에서는 최대 200 VU가 커넥션 풀에서 대기하지 않도록 Hikari와 MySQL 상한을 함께 올린다. [근거](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)

실제 자원·버전은 각 실행의 환경 스냅샷에 기록한다. 설정 적용·실행 결과는 개별 실험에서 관리하며, 로컬 결과를 운영 서버의 최대 처리량으로 해석하지 않는다.

## 구매 시나리오

대상: `POST /api/v1/orders/{orderId}/confirm`

| ID | 시나리오 | 주문 구성 | 초기 재고 | 확인할 것 |
| --- | --- | --- | --- | --- |
| S1 | 한 상품에 구매 집중 | A만 구매 | A = 계획 요청 수의 30% | 같은 상품의 락 경합과 품절 전후 성능 |
| S2 | 인기 상품을 포함한 구매 | A + B~J 중 무작위 1~2종 | A = 계획 요청 수의 30%, 나머지 충분히 | 공통 상품 A의 락 경합이 주문 전체 응답시간과 처리량에 미치는 영향 |
| S3 | 여러 상품으로 구매 분산 | A~J 중 무작위 2~3종 | 모두 충분히 | 구매가 분산된 상황의 처리 성능 |

- 상품은 중복 없이 종류별 1개씩 구매한다. 요청마다 다른 사용자·DRAFT 주문을 사용하고 잔액은 충분히 둔다.
- S2·S3의 2종/3종 비율은 동일하게 한다. 사용자·주문·상품 조합·품목 순서·초기 재고를 같은 부하 단계의 모든 전략에서 재사용한다.
- 충분한 재고는 모든 계획 주문을 감당할 수량이다. A의 30%는 한정 재고를 재현하기 위한 실험값이다.
- S1·S2는 품절 영향이 있으므로 성공·품절 거절과 품절 전후 성능을 나눠 본다.

## 부하 단계

RPS는 초당 주문 확정 요청 수다. 계획 요청 수는 RPS × 시간이며 성공 건수와 구분한다.

| 단계 | RPS | 측정 시간 | 계획 요청 수 | S1·S2의 A 재고 |
| --- | --- | --- | --- | --- |
| L1 | 10 | 60초 | 600건 | 180개 |
| L2 | 30 | 60초 | 1,800건 | 540개 |
| L3 | 100 | 60초 | 6,000건 | 1,800개 |

- **요청률**: 응답 속도에 관계없이 같은 부하를 주도록 k6 `constant-arrival-rate`를 사용한다. 반복 1회에 요청 1건이다. [근거](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)
- **10·30·100**: 약 3배씩 늘려 넓은 범위를 살펴보는 초기값이다. 예비 실행에서 너무 낮거나 높으면 조정한 뒤 모든 전략에 공통 적용한다.
- **준비 30초·측정 60초·3회 반복**: 초기 실행 영향과 실행 간 편차를 확인한다. 안정되지 않으면 예비 실행에서 시간을 늘린다. 이 수치들은 공식 권장값이 아니다.

## 결과 지표

| 지표 | 의미 |
| --- | --- |
| 목표 RPS | 초당 보내기로 한 요청 수 |
| 측정 횟수 | 같은 조건으로 실제 측정한 반복 횟수 |
| Run당 전체 요청 | 한 번의 부하 실행에서 보낸 전체 요청 수 |
| Run당 성공 주문 | 한 번의 부하 실행에서 주문 확정에 성공한 요청 수 |
| Run당 품절 거절 | 한 번의 부하 실행에서 재고 부족으로 정상 거절된 요청 수 |
| Run당 데드락 범위 | 반복 실행 중 한 Run에서 발생한 데드락 건수의 최소~최대 |
| p50 | 응답 시간의 중간값. 절반의 요청이 이 시간 이내에 끝남 |
| p95 | 응답 시간의 95백분위수. 95%의 요청이 이 시간 이내에 끝남 |
| p99 | 응답 시간의 99백분위수. 가장 느린 1%까지 반영함 |
| 전송되지 않은 요청 | 목표한 요청 중 부하 생성기가 실제로 시작하지 못한 요청 수 |
| 데이터 정합성 | 성공 주문 수와 재고·잔액·주문·결제 결과가 서로 맞는지 확인한 결과 |
| 전체 TPS | 성공·품절·기술 오류를 포함한 전체 완료 트랜잭션 처리량 |
| 성공 TPS | 실제 주문 확정 성공 트랜잭션 처리량 |
| 품절 거절 TPS | 재고 부족으로 거절된 트랜잭션 처리량 |
| 기술 오류 TPS | 데드락·타임아웃 등 기술 오류로 끝난 트랜잭션 처리량 |

S1의 성공 건수는 A 재고를 계획 요청 수의 30%로 둔 실험 조건의 영향을 받는다. 품절 거절은 업무 결과로 구분하고, 데드락·기술 오류와 미시작 요청은 별도로 기록한다.

## 실행·검증

- **통합 테스트**: [OrderConcurrencyTest](../../../../apps/commerce-api/src/test/java/com/loopers/order/application/OrderConcurrencyTest.java) 4개 × 10회. 기존 test 프로필의 풀 설정과 기대값을 유지한다.
- **HTTP 부하**: 시나리오 3개 × 부하 3단계 × 3회 = 27 Run. 매번 준비 실행 후 데이터를 초기화·커밋하고 측정한다.
- **DB 검증**: 성공 주문의 품목·결제액과 재고·잔액 차감이 일치하고, 실패한 확정에는 부분 차감·결제 결과가 없어야 한다.

```bash
./gradlew :apps:commerce-api:test --tests '*OrderConcurrencyTest' --rerun-tasks
```
