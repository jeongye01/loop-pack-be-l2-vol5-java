# 주문 확정·상품 수정 동시 요청 실험

상품 정보 수정과 주문 확정이 같은 상품에서 동시에 실행될 때 최종 상태의 정합성을 확인한다.

## 고정 시나리오

- 상품: `Air`, `1,000원`, 재고 `5개`
- 주문: `Air` 1개를 담은 `DRAFT`
- 구매자 포인트: `1,000원`
- 상품 수정: `Updated Air`, `1,100원`
- 주문 확정: 재고 1개와 기존 주문 금액 `1,000원` 차감

실행 순서는 통제하지 않는다. 상품 수정이 먼저 실행되거나 주문 확정이 먼저 실행되어도 다음 최종 상태를 확인한다.

- 상품: `Updated Air`, `1,100원`, 재고 `4개`
- 주문: `CONFIRMED`, 결제액 `1,000원`
- 주문 품목: `Air`, 단가 `1,000원`, 수량 `1개`
- 구매자 포인트: `0원`

## 고정 시스템 스펙

락 전략 외의 조건은 모든 실험에서 고정한다.

| 항목 | 조건 |
| --- | --- |
| 애플리케이션 | 인스턴스 1개, 동일 Java 21·JVM 옵션 |
| MySQL | 동일 8.0 계열 이미지·자원, `max_connections` 300 이상 |
| HikariCP | 최대 200, 최소 유휴 200, 획득 대기 3,000ms |
| Tomcat | 최대 스레드 200, 최소 유지 10 |
| 실행 환경 | 같은 Mac·Docker 자원 할당, 측정 중 다른 작업 종료 |
| 로그 | SQL 로그 끄기, 나머지 로그 수준 고정 |

실제 CPU·메모리·JVM·DB·풀 값은 각 Run의 `environment.json`에 기록한다.

## 부하 단계

관리자 상품 수정은 실험마다 1건만 실행하고, 고객 주문 확정만 부하를 증가시킨다. 상품 수정 요청은 주문 확정 요청과 같은 상품을 대상으로 하며, 부하 중 한 시점에 실행해 경합을 만든다.

| 단계 | 주문 확정 목표 RPS | 측정 시간 | 주문 확정 계획 수 | 관리자 상품 수정 |
| --- | ---: | ---: | ---: | ---: |
| L1 | 10 | 60초 | 600 | 1건 |
| L2 | 30 | 60초 | 1,800 | 1건 |
| L3 | 100 | 60초 | 6,000 | 1건 |

- 각 단계는 30초 준비 실행 후 데이터를 초기화·커밋하고 60초 측정한다. 관리자 수정은 측정 중 한 번 실행한다.
- 각 단계는 3회 반복한다. 같은 사용자·DRAFT 주문·상품 조합을 전략별로 재사용한다.
- 통합 테스트에서는 먼저 `OrderConcurrencyTest`를 10회 반복해 순서 무관 최종 상태를 확인한다.
- 고객 관점에서는 주문 확정의 전체·성공·기술 오류 처리량과 p50·p95·p99를 기록한다.
- 관리자 관점에서는 상품 수정 요청의 성공·거절·기술 오류, 응답 시간, 락 대기·데드락 여부를 별도로 기록한다.
- 두 관점 모두 최종 상품·재고·주문·결제 상태를 확인한다.

## Run 산출물

- `traces.json`: 주문 확정 요청 trace만 저장한다.
- `admin-traces.json`: 중간에 투입한 관리자 상품 수정 요청 trace만 저장한다.
- `result.json`: 주문 집계와 관리자 `admin`·`adminLatencyMs` 집계를 함께 저장한다.
- 원시 k6 trace와 서버 로그는 각 Run의 `build/serializable-experiment` 경로를 가리키는 `raw` 항목으로 연결한다.

## 기준선 결과: 락 없음

2026-10-07 현재 코드에서 낙관적·비관적 락과 재시도를 제거한 상태로 마지막 테스트를 실행했다.

```text
./gradlew :apps:commerce-api:test \
  --tests 'com.loopers.order.application.OrderConcurrencyTest.preservesProductAndOrderStateUnderConcurrentUpdateAndConfirmation' \
  --rerun-tasks
```

대상 테스트:

`[INV-ORDERITEM-40][INV-ORDER-36·43·44] 상품 수정과 주문 확정이 어느 순서로 실행되어도 최종 상품 Updated Air·1,100원·재고 4개, 주문 CONFIRMED·결제액 1,000원·품목 Air·1,000원을 유지한다.`

결과: **실패**

- 기대 재고: `4`
- 실제 재고: `5`
- 상품 수정이 이전 재고 값을 다시 저장해 주문 확정의 재고 차감을 덮어썼다.
- 상품명·가격, 주문 상태·결제액·품목 스냅샷 검증은 통과했다.

## 실행 순서

1. 현재 코드에서 기준 실험을 실행하고 10회 결과를 기록한다.
2. 낙관적 락과 재시도 영향을 제거한다.
3. 동일한 데이터와 실행 조건으로 비관적 락 실험을 실행한다.
4. 각 전략은 별도 Git 커밋과 결과 파일로 보존한다.

공통 실행·환경·결과 형식은 [실험 프로토콜](../protocol.md)을 따른다.
