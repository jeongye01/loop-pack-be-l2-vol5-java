# EC2 상품 목록 부하 예비 측정

측정일: 2026-10-13 (KST) / 실행: `ec2-20261013-023025`

**이번 실행에서는 2 RPS까지 오류 없이 처리했고, 3 RPS에서 요청 91건 중 82건이 실패했다.** 3 RPS에서 상승을 중단해 5·6·8 RPS는 실행하지 않았다. 단회 30초 탐색이므로 절대적인 최대 처리량으로 확정하지 않는다.

## 조건

- 요청: `GET /api/v1/products?brandId=7&sort=price_asc&page=0&size=20`, `X-USER-ID: 1`.
- 데이터: `uniform-10k-v1`, 상품 10,000·좋아요 999,493행. 기존 CSV로 기준 응답을 검증했다.
- 앱·DB 각각 m7i-flex.large, 2 vCPU·8 GiB, Ubuntu 26.04 x86, 시드니 같은 AZ. 로컬 Mac k6에서 공개 HTTP로 요청.
- 앱은 Docker `local,docker`, ddl-auto=none. Hikari 최대40·최소유휴30·획득대기3초, Tomcat 최대200. MySQL8.0.46, 상품 캐시 없음.
- 동일 `products.js` 재사용: constant-arrival-rate, 100 VU, timeout5초, 종료유예10초.
- 1 RPS 준비15초 후 단계당30초·1회. 단계 사이 풀 회복과 CSV 기준 응답을 확인했다. 준비 실행은 아래 표에서 제외.
- HTTP 실패·응답 검증 실패·미전송 한 건이라도 발생하면 상승 중단. 로컬 예비 측정의 1% 규칙보다 엄격한 탐색 중단 조건이다.

- 정상 응답 중 내용 불일치는 관측되지 않았다. 기존 `invalid_response` 지표는 HTTP 실패도 포함하므로 90.11%를 내용 불일치율로 해석하지 않는다.
- k6 로그에서 클라이언트 `request timeout`을 확인했다. `http_req_duration`은 연결 수립을 제외한다. 3 RPS의 연결 수립 평균은 약206ms이고 duration p95는4805ms이므로, timeout5초와 모순되지 않는다. 개별 구간의 p95를 합산해 전체 p95로 계산하지 않는다.

## 관찰과 한계

- 3 RPS에서 MySQL CPU 샘플 평균197.2%, 최대200.03%였다. Docker 다중 코어 합산 값이며 2 vCPU의 자원이 거의 사용된 것으로 보인다. 해당 단계 샘플은4개뿐이며 연속적인 고해상도 시계열은 아니다.
- 같은 단계 앱 CPU 샘플 평균17.4%, 최대42.13%. DB CPU 사용과 서버 연결 풀 고갈이 함께 관측됐다.
- 서버 로그에 `total=40, active=40, idle=0, waiting=4`와 커넥션 획득3000ms timeout이 남았다. 클라이언트 timeout 뒤 서버 작업이 계속 남을 수 있으므로 단순히 클라이언트 종료로 회복을 판단하지 않았다.
- 좋아요 반복 COUNT와 인덱스 접근 비용은 기존 코드상 분석 후보다. 실제 요청별 SQL 수·실행 시간·EXPLAIN ANALYZE는 이번에 수집하지 않아 원인별 비용을 확정하지 않는다. 풀을 늘리면 해결된다는 근거도 아니다.
- M7i-flex의 가변 CPU 여력, 새 DB의 준비 상태, 네트워크, 단회 측정의 영향을 분리하지 않았다. 로컬5~6 RPS 경계와 장비·배치가 달라 코드 개선/악화로 비교할 수 없다.
- 부하 생성기는100 VU를 미리 할당한다. 짧은 실행에서는 여러 VU의 최초 TCP 연결 비용이 섞이며 실제 연결 재사용 비율을 별도로 확정하지 않았다.
