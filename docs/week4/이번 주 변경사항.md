# Week4 상품 조회 개선 내역

상품 100만 개·좋아요 69만 개 환경에서 SQL·인덱스부터 캐시와 로깅까지 개선했다. 아래 성능은 각 실험 당시의 조건이다. 후속 API 분리·캐시 확장은 EC2에 배포했지만, 아래 고정 데이터 캐시 성능을 새 설계의 혼합 부하 성능으로 해석하지 않는다.

| 단계 | 변경 내용 | 확인한 결과·기록 |
| --- | --- | --- |
| 좋아요 인덱스 | `product_like(product_id)` 추가 | 상품 하나의 좋아요 집계가 69만 행 전체 읽기 → 해당 상품 1,000행 읽기. 별도 실행계획 126 → 0.174ms. [보고서](experiments/04-optimize-likes-query/report.md) |
| 좋아요순 알고리즘 | 상품별 사전 집계 → 순위 정렬 → 유효 상품을 필요한 수만큼 선택. 좋아요 0개·동점·삭제 조건 유지 | 무필터 목록 SQL 평균 92.1ms. [보고서](experiments/04-optimize-likes-query/report-rank-first.md) |
| 브랜드별 좋아요순 | 해당 브랜드 상품을 먼저 좁히고 좋아요 집계 | 브랜드 1 목록 SQL 548.9 → 39.9ms. [보고서](experiments/04-optimize-likes-query/report-brand-first.md) |
| 페이지 응답 | 전체 COUNT 대신 21개 조회 후 20개 반환·`last` 판정 | 전체 개수 쿼리 제거. page/size 기반 OFFSET 유지. [API 계약](상품%20목록%20조회%20API%20계약.md) |
| N+1 제거 | 선택한 상품의 브랜드·재고·좋아요 수를 일괄 조회 | 좋아요순 요청 SQL 63 → 6회, 서버 처리 204.2 → 136.6ms. [보고서](experiments/04-optimize-likes-query/report-batch-reads.md) |
| 좋아요 집계 재사용 | 정렬 때 구한 좋아요 수를 응답에도 사용 | 당시 결합 응답의 재집계 1회 제거. [보고서](experiments/04-optimize-likes-query/report-reuse-like-count.md) |
| 최신순 인덱스 | 삭제 여부·브랜드 등치 조건 뒤 생성일 DESC·ID ASC | 무필터 100만 → 21행, 목록 SQL 3,920 → 1.2ms. [보고서](experiments/05-optimize-latest-query/report-index.md) |
| 가격순 인덱스 | 삭제 여부·브랜드 등치 조건 뒤 가격 ASC·ID ASC | 무필터 100만 → 21행, 목록 SQL 3,198.7 → 1.4ms. [보고서](experiments/06-optimize-price-query/report-index.md) |
| Redis 성능 실험 | 변경 없는 최신순 첫 페이지 응답 캐시 | miss·hit 비교 후 별도 서울 EC2 부하기로 네트워크·부하기 영향을 분리. [보고서](experiments/13-cache-ec2-load/report.md) |
| 로깅 병목 진단 | 풀·Tomcat 지표와 스레드 덤프 확인 → 출력 OFF → 비동기 → 상세 기록 1% | 로그 출력 락 대기 확인. 비동기 전수 기록만으로는 p99 목표 미달. [덤프](experiments/16-cache-thread-dump/report.md), [비동기](experiments/18-cache-async-log/report.md) |
| 로깅 최종 측정 | 미선택 요청은 상세 계측·JSON 생성 생략, 선택된 기록은 비동기 출력 | 1,700 RPS·VU 3,000·60초·3회 p99 **51 / 73 / 30ms**, 성공률 100%, 미시작 0. [보고서](experiments/19-cache-sampled-log/report.md) |
| API 분리 | 기본 상품 정보와 좋아요 수·품절 상태를 분리 | 기본 응답은 id/name/price/brand. 두 일괄 API를 프론트에서 합성. [계약](../week2/api-contract.md) |
| 캐시 확장 | 목록·상세·내 좋아요·관리자 브랜드·좋아요 수·품절 상태에 Spring Cache 적용 | `@Cacheable`, 키 생성 `CacheKeys`로 통일. 전체 TTL 5분 ±30초, hit은 만료를 연장하지 않음. [ADR](ADR.md) |
| 변경 반영 | 쓰기와 DB revision을 같은 트랜잭션으로 갱신 | 롤백·늦은 재삽입·Redis 오류에도 새 요청이 이전 revision을 재사용하지 않도록 구성. hit에도 revision DB 조회 비용이 남음. [DDL](migrations/05-add-read-cache-revision.sql) |

최신순·가격순 수치는 예열 후 단건 3회 평균이다. p99 결과는 고정 데이터·동일 최신순 첫 페이지·캐시 hit·서울 EC2 사설 경로에서 측정했다. API 분리 후 여러 읽기·쓰기를 섞은 성능으로 해석하지 않는다.

새 설계의 기본 TTL은 좋아요 수·순위를 포함해 전체 5분·Jitter ±30초로 통일했다. 무효화는 기존 그룹별 DB revision을 유지하기로 했다. 메모리·Bulkhead 세부 설정은 검토 중이다. 전체 TTL 5분 ±30초를 로컬 코드에 적용하고 키를 v3로 분리했으며, 설계와 구현 상태를 [ADR](ADR.md)에 구분했다.

## 적용 상태

- EC2: `catalog-b2e84c4`. API 분리·공통 캐시·revision과 Redis 타임아웃 설정 반영. 기존 실험용 캐시는 OFF. [배포 기록](experiments/22-cache-redis-recovery/report.md).
- 프론트 응답 합성·revision DDL·EC2 쓰기/자연 만료 검증은 [21번 보고서](experiments/21-cache-path-validation/report.md)에 기록했다.
- Redis 메모리 한도·제거 정책의 실제 설정과 Bulkhead 세부 정책은 별도 과제다. 새 API 전체와 쓰기 혼합 부하 SLO는 별도로 측정한다.

병목을 찾아간 과정은 [Week4 인사이트](../../.handoff/insights/week4-인사이트.md)에 정리했다.

## 이번 구현 검증

전체 415개 테스트 통과(일반 411개 + 별도 JVM 비동기 로그 4개), 실패·건너뜀 0개. API·OpenAPI·ArchUnit과 캐시 TTL, 본인 확인, 수정·삭제, 롤백, 늦은 재삽입, Redis 오류 우회, 주문 확정 후 재고 갱신을 확인했다. Checkstyle·diff 검사도 완료했다. 새 캐시의 EC2 부하 성능은 아직 측정하지 않았다.

후속 구현: 전체 캐시 TTL 5분 ±30초, 저장마다 Jitter 재선정, hit 시 TTL 유지. 기존 무기한 캐시와 격리하도록 v3 키를 사용한다. [실행 계획](experiments/execution-plan.md).

TTL 후속 변경 검증: 관련 테스트 21개·Checkstyle 통과. TTL 경계·저장별 재선정·전체 캐시 적용·hit 시 비연장, 기존 revision·권한·삭제·롤백·Redis 오류 동작을 확인했다. 이전 전체 415개 결과와 별도 실행이다.

TTL 변경 후 전체 회귀 검증: 일반 테스트 415개 + 별도 JVM 비동기 로그 4개, 총 **419개 통과**(실패·오류·건너뜀 0개). API·OpenAPI 계약, ArchUnit 포함. Checkstyle 통과.
