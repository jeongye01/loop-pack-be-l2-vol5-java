# Redis 장애·복구 검증

| 항목 | 내용 |
| --- | --- |
| 환경 | 로컬 Spring Boot·MockMvc + 실제 MySQL·전용 Redis 7.0 Testcontainers |
| 대상 | 상품 상세 공통 캐시, 기존 관리자 수정·삭제 API |
| 정상 | miss/hit 응답 일치, hit에서 원본 조회 생략 |
| 장애 | 실제 Redis 컨테이너 중단 → 가격 수정·다른 상품 삭제 → DB 우회 응답·대기 시간·get/put 오류 측정 |
| 복구 | 같은 컨테이너·포트 재시작 → 남아 있는 옛 키 무시 → 새 revision 재채움 → hit 원본 조회 감소·삭제 404 |
| 정리 | finally에서 전용 DB fixture 정리, AfterAll에서 전용 Redis 제거 |

운영 Redis·EC2는 건드리지 않는다. 캐시 읽기는 실제 설정의 master 전용 연결을 사용하고, 테스트의 master/replica 주소 모두 이 전용 컨테이너를 가리킨다. 초기 측정은 기존 Redis timeout으로 실행했다. 후속 개선은 명령·연결 timeout 각 100ms, 재연결 대기 최대 1초로 실행한다.

Docker 재시작 시 임의 공개 포트가 변경될 수 있어 전용 포트를 고정한다. 재시작 후 포트 동일성, 서버 PONG, 앱 연결의 자동 복구를 차례로 확인한다.

옛 캐시가 만료되어 우연히 검증을 통과하지 않도록 **테스트의 기존 두 키만 TTL을 15분으로 연장하고 SAVE**한다. 운영 TTL 5분 ±30초는 변경하지 않는다. 복구 후 새 키는 운영 TTL 범위를 확인한다. 전체 테스트 제한은 300초다.

```sh
./gradlew :apps:commerce-api:test --tests '*RedisRecoveryHttpTest' \
  :apps:commerce-api:checkstyleTest
```

부하·EC2 지연·장애 상태 SLO 검증은 별도다. 실제 대기가 길면 정상 응답 성공과 분리해 기록한다.

## 필수 보호 조건 추가

각 시나리오를 Redis 중단 상태·복구 상태에서 각각 실행한다. 시나리오 사이에는 Spring 컨텍스트를 새로 만들어 이전 연결의 재시도 상태가 다음 테스트에 섞이지 않게 한다.

| 시나리오 | 확인 |
| --- | --- |
| 사용자 경계 | 타인 좋아요·주문 조회/확정 거절, 본인 목록·포인트만 반환, 거절 후 주문·재고·잔액 불변 |
| 주문 판단 | DB 가격으로 주문 생성, 생성 후 가격 변경에도 저장 단가로 결제, 실제 재고·포인트 차감, 부족 시 거절·상태 보존 |
| 브랜드 삭제 | 소속 상품 목록·상세·일괄·내 좋아요 제외, 새 주문 거절, 다른 브랜드 유지, 과거 주문·결제액 보존 |

## 재연결 개선 검증

- 공통 Redis 연결에 명령·연결 타임아웃 각 100ms와 재연결 지연 상한 1초를 적용한다. 환경변수로 조정 가능하다.
- 기존 중단 → 수정·삭제 → 복구 → 옛 키 무시 → 재채움 시나리오를 3회 반복한다.
- 기존 정합성·복구 조건은 유지한다. 장애 중 조회의 5초 미만 검사는 과거 60초 대기의 회귀 방지이며 p99 SLO가 아니다.
- 사용자 경계·주문·브랜드 삭제 보호 6개와 전체 회귀·Checkstyle·ArchUnit을 확인한다.
- 이번 범위는 로컬 Testcontainers 검증이며 EC2 배포·장애 부하 SLO 검증은 별도다.
