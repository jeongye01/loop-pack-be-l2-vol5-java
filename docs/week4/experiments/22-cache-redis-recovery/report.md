# Redis 중단·복구 검증

2026-10-15, 로컬 Spring Boot·실제 MySQL·Redis 7.0 Testcontainers. **장애 중 DB 우회와 복구 후 재채움 통과.** EC2·부하 실험은 아니다.

| 시나리오 | 결과 |
| --- | --- |
| 정상 miss → hit | 응답 일치, 원본 상품 조회 총 1회 |
| Redis 중단 중 관리자 가격 수정 | 새 이름·400원 반환, 41ms |
| Redis 중단 중 다른 상품 삭제 | 상세 404, 26ms |
| 장애 감지 | 캐시 get 오류 2회·put 오류 1회 증가 |
| 동일 Redis 재시작 | 앱 연결 강제 초기화 없이 자동 재연결 확인, 확인 구간 255ms |
| 옛 키가 남은 상태에서 조회 | 옛 키를 사용하지 않고 새 revision 키에 현재 가격 저장 |
| 복구 후 반복 조회 | 첫 조회만 원본 호출, 다음 hit 원본 호출 0회. 새 키 TTL 269~330초 |
| 복구 후 삭제 상품 | 옛 키가 있어도 404 유지 |

기존 키 두 개만 테스트용 TTL 15분으로 연장하고 `SAVE`해 재시작 후에도 옛 값이 남는 조건을 만들었다. 운영 TTL 정책은 변경하지 않았다. 데이터·revision은 기존 관리자 트랜잭션에서 커밋하므로 Redis 삭제 성공 여부에 의존하지 않는다.

처음에는 Docker의 임의 공개 포트가 재시작 후 바뀌어 복구 검사가 실패했다. 별도 컨테이너에서도 포트 변경을 재현했다. 테스트 포트를 고정하고 재시작 전후 동일한지 검증했으며, Redis 서버 PONG과 앱의 자동 재연결도 구분했다. 운영 코드나 테스트 기대 결과를 완화하지 않았다.

**관련 테스트 33개 통과**, 실패·오류·skip 0개. 캐시·TTL·ArchUnit 29개와 별도 비동기 로그 4개, Checkstyle 통과. 실행 1분 4초. DB fixture는 finally에서 정리하고 전용 Redis는 AfterAll에서 제거한다.

이 수치는 연결이 끊기는 중단 상황의 단일 관측이다. 패킷을 응답 없이 버리는 장애·느린 Redis·부하 상태의 timeout/SLO는 검증하지 않았다. 따라서 장애 시 모든 요청이 41ms 이내라고 보장하지 않는다. 브랜드 일괄 삭제·주문 이력·사용자 경계의 장애 중 조합은 이 테스트 범위 밖이다.

## 후속: 필수 보호 조건

위 단일 복구 검증에서 제외했던 사용자 경계·주문·브랜드 삭제 조합을 추가했다. **사용자 경계, 주문 판단, 브랜드 삭제 각각 장애 중/복구 후 2가지로 총 6개 통과**, 기존 복구 시나리오 포함 7개 통과. [보호 조건 결과](protection-results.json)

| 보호 조건 | 확인한 실제 결과 |
| --- | --- |
| 소유권 | Bob의 Alice 좋아요·주문 조회와 주문 확정은 404. 본인 목록·잔액만 반환, 거절 후 주문 DRAFT·재고·두 사용자 잔액 불변 |
| 가격·결제 | 100원 캐시 후 장애 중 DB 가격 400원으로 수정해 주문 생성. 이후 상품을 900원으로 수정해도 주문 단가·결제액은 400원 |
| 재고·포인트 | 결제 후 재고 2→1·잔액 1,000→600. 포인트 부족·재고 부족은 각각 거절하고 DRAFT·재고·잔액 보존 |
| 브랜드 삭제 | 소속 상품 2개는 3종 정렬·상세·좋아요·재고·내 좋아요에서 제외, 새 주문 404. 다른 브랜드 상품·과거 주문 전체 응답·결제액·잔액 유지 |

초기 검사 실패도 [별도 보존](protection-first-run.json)했다. 관리자 요청의 필수 이름 누락은 요청을 보완했고, 과거 주문은 확정 응답(KST)과 조회 응답(UTC)을 비교하던 것을 삭제 전후 **같은 조회 응답** 비교로 고쳤다. 실제 값·오류 기대값은 완화하지 않았다.

같은 Spring 연결로 반복 중단했을 때 약 **60,135ms 대기와 재연결 검사 실패**가 관측됐다. 각 독립 시나리오가 이전 연결의 재시도 상태를 물려받지 않도록 Spring 컨텍스트를 격리한 뒤 7개가 통과했다. 격리 후 단건 관측은 수정 조회 66ms·삭제 조회 31ms·재연결 확인 1ms였으나, 이것으로 반복 장애의 지연 문제까지 해결했다고 보지 않는다. 운영 코드·timeout·재연결 설정은 변경하지 않았다.

전체 회귀에서 발생한 추가 실패 2건은 **장애 상태 시나리오의 종료 후 정리 단계**였다. [실패 스택](protection-cleanup-failures.json)의 `restoreOwnRedis`에서 폐기할 앱 연결까지 재연결시키다 실패했다. 정리 단계는 Redis 서버 준비만 확인하고 앱 컨텍스트를 폐기하도록 분리했다. 복구 상태 시나리오의 앱 자동 재연결·응답·재채움 검증은 그대로 유지한다.

### 최종 전체 검사

`./gradlew :apps:commerce-api:check`: **450개 중 449개 통과·1개 실패**, 오류·skip 0개, 4분 7초. Checkstyle·ArchUnit 통과. [최종 결과·실패 스택](protection-full-check.json)

추가 보호 조건 6개는 모두 통과했다. 남은 실패는 기존 `outageWritesAndRecoveryNeverReuseOldRevision`의 **앱 자동 재연결 확인**이다. 이번에는 정리 단계 실패가 아니며, 복구 관찰 루프에서 성공을 확인하지 못했다. 해당 검사는 그대로 남겼고 완료 체크를 취소했다. 앞선 단독 실행 성공으로 자동 재연결의 안정성까지 보장할 수 없다. 10초 관찰 범위는 테스트용 유한 대기이며 서비스 복구 SLO로 합의한 값은 아니다.

### DEBUG 재현: 타임아웃·재연결 대기

기존 복구 테스트 1개에 ConnectionWatchdog DEBUG 로그만 추가하고 기대값·대기는 유지했다. 결과는 동일 재연결 검사 실패다. [진단 로그](reconnect-diagnostic.log)

| 관측 | 결과 |
| --- | --- |
| 장애 중 수정 후 조회 | 60,168ms, 캐시 get 오류 2회·put 오류 1회 |
| 재연결 대기 | 점차 증가해 16,384ms → 30,000ms |
| 마지막 예약 | 09:45:43.914~915에 30초 뒤 시도 예약 |
| 복구 확인 | 서버 PONG, 앱은 약 10초 관찰 동안 RedisSystemException |

다음 시도 예정은 약 09:46:13.9로, 테스트 실패 시점(약 09:46:09)보다 뒤였다. 이번 실패는 서버 기동 여부와 앱 재연결 시점이 다르고, 관찰 시간이 재시도 간격보다 짧아서 발생했다. 다음 시도에서 실제 성공하는지까지 관측한 것은 아니다.

현재 `RedisConfig`는 Lettuce 명령 타임아웃을 지정하지 않는다. 사용 중인 Spring Data Redis 3.4.4의 빌더 기본값은 60초이며 로컬 라이브러리 바이트코드에서 확인했다. Lettuce 6.4.2의 [ConnectionWatchdog 구현](https://raw.githubusercontent.com/redis/lettuce/6.4.2.RELEASE/src/main/java/io/lettuce/core/protocol/ConnectionWatchdog.java)은 재시도 횟수에 따른 지연 후 재연결을 예약한다.

운영 설정 변경은 아직 없다. 짧은 명령·연결 타임아웃과 재연결 간격, 복구 허용 시간을 정한 뒤 반복 검증해야 한다. 대기 시간만 늘려 통과시키는 것으로 60초 응답 지연이 해결되지는 않는다. 이번 로그로 과거 모든 실패의 원인이 같다고 단정하지 않는다.

### 개선 후: 명령·연결 100ms, 재연결 최대 1초

공통 Redis 설정에 명령 타임아웃 100ms·TCP 연결 타임아웃 100ms를 적용하고, 지수 증가하는 재연결 대기를 최대 1초로 제한했다. master·replica 연결 모두 적용되며 클라이언트 리소스는 Spring 빈으로 공유·종료한다. 환경변수는 `REDIS_COMMAND_TIMEOUT`, `REDIS_CONNECT_TIMEOUT`, `REDIS_RECONNECT_MAX_DELAY`다. 캐시 TTL·revision·DB fallback 정책은 변경하지 않았다.

기존 복구 기대값·관찰 횟수를 유지하고 같은 시나리오를 3회 반복했다. 과거 60초 대기를 잡는 5초 미만 회귀 검사를 추가했다. **복구 3회 + 보호 조건 6개 모두 통과**. [실행 결과](timeout-fix-focused.json)

| 회차 | 장애 중 수정 상품 조회 | 장애 중 삭제 상품 조회 | 서버 준비 후 앱 연결 확인 |
| --- | --- | --- | --- |
| 1 | 249ms | 126ms | 81ms |
| 2 | 229ms | 117ms | 56ms |
| 3 | 13ms | 11ms | 57ms |

모든 회차에서 옛 키 보존·새 revision 재채움·hit 원본 호출 0회·삭제 상품 404를 확인했다. 위 시간은 로컬 단건 관측이며 p99가 아니다. API 한 번에서 캐시 읽기·저장이 각각 timeout을 기다릴 수 있으므로 명령 100ms가 API 전체 100ms를 보장하지 않는다. 재연결 지연 상한도 서버 준비·연결·스레드 스케줄링을 포함하는 전체 복구 시간 보장은 아니다. EC2는 배포하지 않았다.

**개선 후 전체 검사 성공:** `:apps:commerce-api:check :modules:redis:check`, 2분 47초. 테스트 결과 총 **452개 통과**, 실패·오류·skip 0개. 이번 전체 회귀 448개와 직전 실행한 비동기 로그 4개(전체 검사에서는 UP-TO-DATE)를 합산했다. Checkstyle·ArchUnit 통과. [전체 결과](timeout-fix-full-check.json)

전체 회귀에서도 복구 3회가 통과했다. 수정 상품 조회 12·218·53ms, 삭제 조회 8·110·8ms, 앱 연결 확인 51·99·42ms였다. 단독 실행과 전체 회귀에서 각각 3회, 총 6회 성공했으며 이전 실패 기록은 그대로 보존한다.
