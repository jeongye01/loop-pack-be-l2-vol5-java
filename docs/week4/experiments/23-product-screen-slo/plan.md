# 첫 화면 세 API 조합 SLO 현황

최신순·무브랜드·첫 페이지 20개 → 받은 상품 ID로 좋아요 수·재고 병렬 조회. 전체 호출 흐름 p99 ≤ 200ms, 성공률 100%, 미시작·미완료 0을 목표로 한다.

- 부하: 초당 방문 1,700회, 정상 완료 기준 약 5,100 API RPS. VU 3,000, API별 timeout 5초.
- 예열: 300·700 방문/초 각 20초. 본 측정: 60초 1회. 실패·미시작 발생 시 다음 부하를 진행하지 않는다.
- 환경: 기존 부하 EC2 → 앱 EC2 사설 IP. 현재 배포 버전, TTL 5분 ±30초 유지. 키 삭제·TTL 연장·앱 재배포 없음.
- 응답 검증: 기존 seed 기반으로 목록·좋아요 수·재고 응답을 모두 비교. 기준 불일치 시 중단.
- 전체 시간: 목록 요청 직전부터 두 병렬 응답 수신 완료까지. 프론트 렌더링 제외, 목록 파싱·후속 요청 준비 포함. API별 p99를 합산하지 않는다.
- 집계: 전체 및 성공 방문 p99, 시작·완료·실패·미시작 수, 실제 API RPS. 방문당 로그 출력 대신 k6 전수 메트릭 집계.
- 수집: 공통 RemoteRunner의 환경·서버 로그·Prometheus·앱/DB/부하기 자원·회복 확인 재사용. 전후 대상 캐시 TTL 기록. 만료가 섞이면 순수 hit 기준선으로 해석하지 않는다.

현재 상태 탐색 1회이며, 스탬피드 재현 및 반복 안정성 검증은 이후 진행한다.
