# 좋아요순 브랜드 필터 비교

서울 EC2, `likes_desc`, `page=0`, `size=20`. 현재 배포된 집계값 재사용 버전에서 무필터·브랜드 1·브랜드 601을 번갈아 순차 요청했다. 각각 워밍업 3회 후 단건 3회 평균, 프론트 제외. 코드·인덱스·데이터 변경 없음.

| 조건 | 해당 상품 수 | 서버 처리 | 전체 응답 | 후보 선택 SQL | SQL 수 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 무필터 | 1,000,000개 | 110.7ms | 123.2ms | 92.2ms | 5회 |
| 브랜드 1 | 5,000개 | 566.9ms | 590.9ms | 548.9ms | 6회 |
| 브랜드 601 | 333개 | 566.4ms | 587.7ms | 547.6ms | 6회 |

**브랜드 필터가 있으면 전체 응답이 약 4.8배 느렸다.** 상품이 5,000개인 브랜드와 333개인 브랜드의 시간이 비슷하고, 후보 선택 SQL이 약 548ms로 대부분을 차지했다.

무필터는 좋아요순 후보를 먼저 제한한 뒤 상품 조건을 확인한다. 브랜드 필터는 전체 좋아요를 상품별로 집계하고 상품과 조인한 뒤, 브랜드 조건을 적용해 상위 상품을 고르는 별도 SQL 경로다. 브랜드 상품 수가 작다고 그만큼 조회 비용이 줄어드는 구조는 아니다. 실제 스캔·조인 행 수는 이번 HTTP Trace만으로 확정하지 않았다.

추가된 SQL 1회는 브랜드 유효성 확인이다. 재고·브랜드는 여전히 일괄 조회하고, 좋아요 수는 후보 집계값을 재사용한다. N+1 재발이 아니라 후보 선택 SQL의 비용 차이다.

세 조건 모두 HTTP 200, 상품 20개, `last=false`. 필터 응답의 모든 상품이 지정 브랜드에 속하며 좋아요 내림차순·ID 오름차순, 중복 없음, 각 조건의 3회 응답 동일을 확인했다.

요청: `GET /api/v1/products?sort=likes_desc&page=0&size=20`에 `brandId=1` 또는 `brandId=601` 추가. `X-USER-ID: 1`.
원본: `build/04-optimize-likes-query/brand-filter/`. Run: `brands-1791924251`.
