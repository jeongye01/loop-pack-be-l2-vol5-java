# 좋아요순 페이지 깊이에 따른 성능

서울 EC2, 무필터 `likes_desc`, `size=20`, 집계값 재사용 버전. 1·10·100페이지를 번갈아 순차 요청했다. 각 페이지 워밍업 3회 후 본 측정 3회, 프론트 제외. 코드·인덱스 변경 없음.

| 페이지 | 서버 처리 평균 | 전체 응답 평균 | SQL 수 | 좋아요 집계·후보 조회 |
| --- | ---: | ---: | ---: | ---: |
| 1페이지 (`page=0`) | 113.5ms | 125.4ms | 5회 | 1회 |
| 10페이지 (`page=9`) | 115.1ms | 127.1ms | 5회 | 1회 |
| 100페이지 (`page=99`) | 226.0ms | 296.1ms | 6회 | 2회 |

**10페이지까지 차이는 작고, 100페이지에서는 서버 처리가 약 2배로 늘었다.** 현재 구현은 후보를 최대 1,024개씩 읽는다. 100페이지는 앞의 1,980개를 건너뛰어야 하므로 후보 SQL이 2번 실행되고, 좋아요 집계·정렬도 반복된다. 두 후보 SQL은 각각 약 100ms였다.

100페이지 전체 응답은 322.2 / 327.6 / 238.5ms, 서버 처리는 226.0 / 227.9 / 224.0ms였다. 전체 응답과 서버 처리의 차이를 전부 DB 비용이나 네트워크 원인으로 단정하지 않는다.

각 페이지의 반복 응답은 동일했고, 좋아요 내림차순·ID 오름차순, 상품 20개·중복 없음·`last=false`를 확인했다. 페이지 사이 전체 누락 검증은 이번 측정 범위가 아니다.

커서는 아직 구현·측정하지 않았다. 이 결과는 OFFSET 기반 현재 구현의 페이지 깊이 비교이며, 커서가 얼마나 빨라지는지는 별도 측정해야 한다.

원본: `build/04-optimize-likes-query/deep-pages/`. Run: `deep-1791922402`.

## 마지막 페이지 단건 조회

조회 가능한 상품 1,000,000개, 페이지당 20개이므로 마지막은 50,000페이지(`page=49999`). 한 번 요청한 결과 HTTP 200, 상품 20개, `last=true`였다.

| 전체 응답 | 서버 처리 | SQL 실행 합계 | SQL 수 | 후보 집계·조회 |
| ---: | ---: | ---: | ---: | ---: |
| 29.347초 | 29.235초 | 28.374초 | 210회 | 206회 |

현재 구현은 깊은 페이지에서도 좋아요순 후보를 처음부터 최대 1,024개씩 읽고 건너뛴다. 좋아요 있는 상품 구간을 지나 0개 구간으로 들어가기까지 후보 집계·조회 SQL이 206회 반복됐다. 단순 OFFSET 비용뿐 아니라, 후보 묶음마다 전체 좋아요 집계·정렬을 반복하는 구현이 크게 영향을 준다.

클라이언트 제한 30초 이내에 완료했지만, 합의한 응답 기준 5초는 초과했다. 위 3회 평균과 달리 마지막 페이지는 단건 관측이다.
원본: `build/04-optimize-likes-query/last-page-depth/`, 요청 ID `last-depth-49999-once`.

별도 실험: [같은 위치의 OFFSET·커서 SQL 비교](report-cursor-comparison.md). SQL 시간과 API 전체 응답 시간은 구분한다.
