# OFFSET과 커서 SQL 비교

서울 EC2의 동일 데이터에서 좋아요순으로 같은 위치의 상품 ID·좋아요 수를 조회했다. 각 SQL 워밍업 1회 후 3회, 순차 실행. MySQL 세션 profiling의 쿼리 실행 시간이며 **API 전체 응답 시간이 아니다.** 앱·프론트·API 계약은 변경하지 않았다.

| 위치 | 단일 OFFSET SQL 평균 | 커서 SQL 평균 |
| --- | ---: | ---: |
| 1페이지 | 90.63ms | 91.09ms |
| 10페이지 | 93.71ms | 147.58ms |
| 100페이지 | 92.66ms | 145.46ms |
| 50000페이지 | 1161.19ms | 0.39ms |

**좋아요가 있는 구간에서는 커서가 더 빠르지 않았다.** `(좋아요 수 < 직전 개수) OR (좋아요 수 = 직전 개수 AND 상품 ID > 직전 ID)`를 HAVING에 넣어도, 69만 좋아요의 상품별 집계는 필요하다. 이번 구현·관측에서 10·100페이지는 커서가 더 느렸다.

**좋아요 0개인 마지막 구간은 커서가 크게 빨랐다.** 커서가 0개 구간임을 알려주므로 전체 좋아요 집계를 생략하고 `상품 ID > 999975` 및 `NOT EXISTS`로 다음 상품을 찾는다.

## 비교 범위

- 이 표의 OFFSET은 페이지 위치를 SQL 한 번으로 읽는 실험용 비교군이다. 현재 앱처럼 후보 1,024개씩 집계·조회하는 반복문은 포함하지 않는다.
- 마지막 OFFSET 비교군도 좋아요 있는 상품이 210,000개임을 미리 알아서, 0개 구간에서 789,980개를 건너뛴다. 이 구간 계산 비용은 제외했다.
- 커서는 직전 페이지 마지막 값이 이미 있다는 조건이다. 10페이지 `(72, 96547)`, 100페이지 `(28, 114354)`, 마지막 `(0, 999975)`. 기준점을 얻는 사전 조회 시간은 제외했다. 첫 페이지는 커서 없이 동일 SQL이다.
- 실제 앱 마지막 페이지 **29.35초 → 커서 API 0.4ms**로 비교하면 안 된다. 0.4ms는 후보 SQL만의 시간이다. 현재 앱 결과는 [페이지 깊이 보고서](report-page-depth.md)에 별도 기록했다.

세 번 모두 OFFSET·커서의 후보 결과가 같고, 앞서 API로 읽은 상품 20개의 ID·좋아요 수도 일치했다. 마지막은 20개, 나머지는 다음 페이지 확인용 21개였다. 현재 데이터는 상품 100만 개 모두 미삭제다. 삭제·브랜드 필터·양수에서 0개로 넘어가는 페이지·동시 좋아요 변경까지 처리하는 운영용 커서 구현 검증은 아니다.

결론: **페이지 번호 UI를 버리기 전에 현재의 반복 집계부터 줄일 가치가 있다.** 커서가 모든 좋아요순 페이지를 같은 시간에 읽게 만드는 것은 아니다.
