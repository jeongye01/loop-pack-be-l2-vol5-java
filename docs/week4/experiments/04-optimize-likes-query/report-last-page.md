# 전체 개수 대신 마지막 페이지 여부 반환

고객 상품 목록의 `totalElements`를 `last`로 변경했다. `page * size`부터 `size + 1`개를 확인하고, 최대 `size`개만 응답한다. 추가 상품이 없으면 `last: true`다. 추가 확인용 상품에는 재고·브랜드·좋아요 수의 상세 조회를 수행하지 않는다.

프론트는 `last: true`에서 무한 스크롤을 멈추며 전체 상품 수를 표시하지 않는다. 관리자·내 좋아요·주문 목록의 기존 전체 개수 응답은 유지한다.

이번 변경은 사용자가 승인한 **응답 계약 변경으로 불필요한 조회를 제거한 것**이다. 기존 응답을 그대로 유지한 SQL 튜닝과 구분한다. 무필터 상품 목록의 전체 상품 COUNT는 제거했지만, 브랜드 필터·좋아요순의 뒤쪽 0개 구간에서는 위치 계산용 좋아요 있는 상품 COUNT가 남을 수 있다.

## 페이지네이션 방식 검토

| 방식 | 장점 | 한계 | 현재 선택 |
| --- | --- | --- | --- |
| 페이지 번호 + `last` | 기존 요청 형식을 유지하고 전체 상품 COUNT 제거 | 깊은 페이지에서는 앞 순위를 건너뛰는 비용이 남음 | 적용 |
| 정렬값·ID 커서 + `last` | 다음 조회를 이어갈 위치를 전달해 앞부분 재탐색을 줄일 여지 | 좋아요를 매번 집계·정렬하는 비용은 남음. 좋아요 변경 시 순위 이동으로 중복·누락 가능 | 후속 검토 |
| 순위 스냅샷 + 커서 | 스크롤 중 순위가 고정됨 | 결과 저장·만료·갱신 정책 필요. 현재 결과 캐시 없이 조회하는 목표와 다름 | 미적용 |

퀸잇 뷰티 홈에서 관찰한 `nextCursor`는 다음 요청의 `cursor`로 전달되었다. 다만 외부 payload만으로 내부 SQL이 키셋 조회인지, 순위 결과를 저장하는지는 알 수 없다. 우리도 커서 도입 전에 순위 변경을 실시간으로 반영할지, 탐색 중 고정할지 정해야 한다.

## 실측

2026-10-14, 서울 EC2에 `commerce-api:week4-last-page-20261014` 배포. 무필터 `likes_desc`, `page=0`, `size=20`을 로컬 curl로 순차 요청했다. 프론트 제외, 부하·결과 캐시 없음, DB 버퍼 풀은 비우지 않았다. 재시작 후 첫 측정은 클라이언트 679ms·서버 611ms로 별도 기록한다. 이후 3회는 아래와 같다.

| 구간 | 1회 | 2회 | 3회 | 평균 |
| --- | ---: | ---: | ---: | ---: |
| 전체 응답 | 255ms | 376ms | 284ms | **305ms** |
| 서버 처리 | 244ms | 270ms | 217ms | **243ms** |
| 서버 처리 중 SQL 합계 | 146ms | 149ms | 134ms | **143ms** |

SQL 중 후보 선택은 평균 92ms다. 서버 처리에서 SQL을 뺀 시간은 평균 101ms이며 커넥션 획득·ORM·직렬화 등 미분리 구간을 포함한다. 전체 응답에서 서버 처리를 뺀 평균 62ms도 순수 네트워크 시간으로 단정하지 않는다.

요청당 SQL은 64회에서 63회로 줄었고, 전체 상품 COUNT는 0회였다. 응답의 상품 20개·순서·필드는 이전과 동일하며 `last: false`와 `totalElements` 제거를 확인했다. 이전 전체 응답 평균 296ms보다 이번 평균이 낮지 않아 **전체 응답 개선은 이번 표본에서 확인되지 않았다.** 재시작 후 측정이므로 충분히 워밍업된 동일 조건 비교와 나머지 앱 구간 분석이 필요하다.

백엔드 HTTP·통합·ArchUnit 157개 테스트와 Checkstyle, 프론트 78개 테스트·타입·린트 검사를 통과했다. 원본은 `build/04-optimize-likes-query/last-page-timing/`에 보관한다. 과거 응답을 보존하는 실험과 구분하도록 공통 실험 도구의 기대 응답도 `last`로 갱신했다.
