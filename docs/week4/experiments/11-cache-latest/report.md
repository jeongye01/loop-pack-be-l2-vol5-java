# 최신순 목록 Redis 캐시 실험 결과

**SQL 5회 → 1회로 줄었고 DB 연결 대기는 감소했다. 3회 모두 p99 200ms·성공률 100% 목표는 미달했다.** 마지막 회차는 102,000건 전부 시작했지만, 회차별 차이가 크므로 안정적으로 목표 부하를 처리한다고 결론내리지 않는다.

- 조건: 데이터 변경 없음, 최신순·브랜드 없음·첫 페이지 20개, 1,700 RPS·VU 3,000·60초·timeout 5초·3회.
- 준비: 새 앱 배포 후 1 RPS·30초. 캐시를 채운 뒤 측정했고 3회 모두 측정 구간 cache miss/fill 증분 0건.
- 구현: 실험 프로필+스위치에서만 공통 응답 캐시. 사용자 확인 유지, Redis master 읽기, TTL 10분. 운영 무효화·정합성 구현이 아니다.

CPU 합산 상한 200%, 2 vCPU 전체 대비 상한 100%. 캐시 전 연결 대기는 평균 90~121ms·최대 157~161개였다. 캐시 후 SQL은 사용자 확인 1회이며 목록·브랜드·좋아요·재고 조회를 건너뛴다.

서버 처리 p99와 클라이언트 p99는 측정 경계가 다르다. 그 차이에는 서버 계측 이전 큐·연결·네트워크·발생기 지연 등이 섞이며 단순 네트워크 지연으로 단정할 수 없다. 이번 자료로 남은 대기 원인을 확정하지 않는다.

## 검증과 한계

- 실제 Redis HTTP 테스트 포함 89개·ArchUnit·Checkstyle 통과, 공통 집계 테스트 4개 통과. 기존 테스트·실패 기준은 변경하지 않았다.
- [miss/hit 확인](cache-check.json): 응답이 CSV 기대값과 같고 SQL 5회 → 1회. 각 Run의 cache-metrics.json에 hit/miss 증분을 기록했다(사전·회복 확인 요청 포함).
- 1회차 서버 로그 중복 ID 2개(총 이벤트 6개)로 원본 집계가 실패했다. result.json은 그대로 보존하고 중복 ID 전체를 제외한 analysis.json을 별도로 생성했다. 클라이언트 시작/종료와 k6 건수는 일치한다.
- 서버 Trace 연결 누락은 1회 1,568건(중복 제외 포함), 2회 21건, 3회 13건이다. 서버 내부 수치는 연결된 표본만의 통계이며 measurementComplete=false를 유지한다.
- 새 앱을 배포한 뒤 회차마다 결과가 개선됐다. 낮은 부하의 30초 준비만으로 JIT·연결 등 모든 준비가 끝났다고 볼 수 없으며, 가장 좋은 회차만으로 개선 폭을 확정하지 않는다.
- 2·3회차 실행 일부에 로컬 이전 결과 집계가 겹쳤다. 아래 원인 분석에 표본 시점과 자원 사용을 기록했다. 추가 부하 실험은 수행하지 않았다.
- 데이터 고정·같은 키 반복 실험이다. 데이터 변경·만료·서로 다른 조건이 섞인 트래픽 성능이나 운영 정합성을 검증한 결과가 아니다.

## 회차별 차이 원인 분석

**측정 시작 시 JVM 준비가 끝나지 않았다는 근거가 강하다. 연결·응답 대기 감소도 함께 관측됐으며, 모든 지연을 JIT 하나로 설명할 수는 없다.** 새 부하는 보내지 않고 기존 Trace·5초 간격 자원 표본을 분석했다.

| 관측값 | 1회 | 2회 | 3회 |
| --- | ---: | ---: | ---: |
| JVM 컴파일 누적 시간 증가 | 73.143초 | 36.120초 | 3.829초 |
| GC 중단 시간 합계 증가 | 0.868초 | 0.532초 | 0.450초 |
| TCP 연결 시간 평균 / p99 | 399.3 / 3,972.8ms | 0.45 / 8.25ms | 0.43 / 11.68ms |
| 성공·서버 연결 표본의 클라이언트 평균 | 3,006.3ms | 1,886.0ms | 191.2ms |
| 같은 표본의 서버 처리 평균 | 32.5ms | 16.0ms | 8.7ms |
| 같은 요청별 클라이언트−서버 시간 차 평균 | 2,973.9ms | 1,870.0ms | 182.5ms |

컴파일 시간은 `jvm_compilation_time_ms_total`의 첫/마지막 표본 차이다(약 60초 구간). 여러 컴파일 스레드의 누적 경과 시간이므로 앱이 73초 정지했다거나 CPU 시간의 일정 비율을 차지했다는 뜻은 아니다. 2회차도 전반 30초 동안 5초마다 약 4.5~5.6초씩 증가했고 후반에는 수백 ms 이하로 줄었다. 낮은 준비 부하 1 RPS·30초가 고부하 경로의 준비 완료를 보장하지 못했다.

3회차도 시작 직후부터 안정적이었던 것은 아니다. 요청 시작 시각 기준으로 10초씩 묶으면 다음과 같다.

| 3회차 구간 | 클라이언트 평균 | 클라이언트 p99 | 연결된 서버 처리 평균 |
| --- | ---: | ---: | ---: |
| 0~10초 | 414.2ms | 865ms | 10.2ms |
| 10~20초 | 377.4ms | 777ms | 10.2ms |
| 20~30초 | 220.0ms | 337ms | 9.8ms |
| 30~40초 | 95.7ms | 208ms | 8.9ms |
| 40~50초 | 19.9ms | 88ms | 6.7ms |
| 50~60초 | 19.8ms | 85ms | 6.4ms |

- **캐시 채움 지연은 아님:** 세 회차 모두 측정 중 miss 0건이다.
- **DB 연결 풀 대기가 주원인이라는 근거는 약함:** 평균 대기 0.025~0.129ms, 대기 최대 0~2개였다.
- **GC만으로 수초 지연을 설명하기 어려움:** 표본에서 관측한 pause max는 회차별 최대 45 / 45 / 37ms였고 총 pause 증가량도 1초 미만이다.
- **1회차는 연결 수립 지연도 큼:** TCP 연결 p99 약 4초. 2·3회차에도 응답 첫 바이트 대기 비중이 높았으므로 연결 수립만이 원인은 아니다. k6는 회차마다 새 프로세스라 이전 회차의 클라이언트 연결이 그대로 재사용된 것으로 설명하면 안 된다.
- **서버 내부 계측 밖의 대기가 큼:** 같은 요청으로 연결한 성공 표본에서 클라이언트−서버 시간 차가 위 표처럼 크다. TCP/서버 진입 전 큐, 동기 로그 출력, 네트워크와 클라이언트 처리 중 어느 구간인지 이번 기록만으로 확정할 수 없다. 서버 로그 직렬화·출력은 기록된 serverDurationMs에 비용이 포함된다고 보장할 수 없는 위치에 있다.
- **발생기 간섭도 있었음:** 2회차 약 39초와 3회차 약 9~19초 표본에서 추가 Python 집계 프로세스가 관측됐다. 3회차 중 하나는 RSS 약 1.1GiB·CPU 코어 합산 61.6%였다. 로컬 총 CPU·메모리 압박/스왑을 수집하지 않아 영향 크기는 미확정이다. 앞서 3회차만 언급한 기록을 정정한다.

결론: 현재 세 값은 충분히 준비된 동일 상태의 반복 측정으로 보기 어렵다. JIT 활동이 크게 남아 있는 상태에서 시작했고, 연결·응답 대기가 실행 중 감소했다. 마지막 20초가 빠르다는 것은 재검증할 단서이며, 해당 구간만 골라 SLO를 통과했다고 판단하지 않는다. 원인별 기여율을 확정하려면 안정화 기준을 확인한 후 측정하고, 로컬 집계를 분리하며 서버 진입 전 대기·TCP 상태를 추가 계측해야 한다.
