원본 횟수는 본 측정 run ID 기준이며 동시는 DB 풀 대기를 포함한다. 캐시 지표는 preflight/recovery 등이 포함될 수 있고 자원은 5초 표본이다. 구매 대조는 주문·재고·포인트, 좋아요 대조는 실제 201 등록→200 취소와 DB 잔존 관계를 확인한다. 표시 캐시의 장애 정합성이 해결됐다는 뜻은 아니다.

## 비교와 범위

좋아요를 포함한 기존 10건/초 결과는 읽기 p99 214/197/139ms, 구매 338/316/282ms였다. 20건/초에서는 읽기 232/149ms, 구매 377/250ms였다. 모두 같은 고정 읽기·좋아요 조건이지만 측정 시점과 JVM 상태는 동일하지 않다. 이번 두 회차만으로 안정적인 최대 처리량이나 구매 부하에 따른 단조로운 성능 변화를 확정하지 않는다.

앱 코드·API는 그대로다. 기존 공통 드라이버에 통과해도 2회 실행하는 옵션만 추가했고 Python 구문 및 diff 검사를 확인했다. 실제 부하 수집·회복·DB 대조를 실행했다. 앱 테스트는 재실행하지 않았다.
