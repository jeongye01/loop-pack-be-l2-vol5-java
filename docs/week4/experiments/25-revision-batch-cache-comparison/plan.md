# Revision 일괄 조회 후 캐시 OFF / ON 비교

- 변경: 요청에서 필요한 revision을 한 SQL로 읽고 재사용한다. 통합 상품 응답·TTL·정합성 계약·읽기 트랜잭션 범위는 유지한다.
- 같은 빌드·같은 seed·같은 최신순 첫 20개 입력으로 OFF → ON 순서로 실행한다. 쓰기 없는 조회 실험이며 종료 시 ON으로 복구한다. 기존 고정 데이터 실험용 캐시는 계속 OFF다.
- 각 조건 배포 재시작·health·seed 응답 확인 → 300 RPS 20초 예열 → 1,700 RPS 60초 본 측정 1회. VU 3,000·timeout 5초, 별도 부하 EC2 → 앱 사설 IP, 1% 서버 Trace.
- 사용자의 즉시 본 실험 지시를 이어 받아 예열 오류가 있어도 회복·수집이 정상이면 본 측정한다. 안정된 정상 hit 성능을 보장하는 예열 절차는 아니다. 두 조건 모두 같은 절차를 적용한다.
- SLO: 전체 응답 p99 ≤ 200ms, 성공률 100%, 미시작·미완료 0. 실제 전달량이 목표 미달이면 달성으로 판정하지 않는다.
- 전수 k6 지표로 실패·timeout·미시작을 구분하고 응답 내용을 seed와 비교한다. 공통 Runner·수집기·분석기를 재사용한다.
- ON의 원본 조회/집계 생략과 인증+revision SQL 2회를 표본 Trace로 확인한다. OFF의 SQL 수·지연과 앱 CPU·Hikari·Tomcat·Redis/DB 자원, JIT·회복을 함께 비교한다. 캐시 TTL을 강제로 연장하지 않고 만료가 섞였는지 기록한다.
- 순차 1회씩의 탐색이다. JIT·서버 재시작·캐시 만료 등 차이를 기록하고 특정 변경 하나의 인과 효과로 단정하지 않는다. 이전 revision 4회 기준선은 [24번](../24-combined-product-slo/report.md)에 보존한다.
