# 로컬 Single Flight 혼합 부하 — 3회 결과

**원본 목록 조회는 줄었지만 읽기·구매 모두 3회 전부 p99 100ms SLO에 미달했다.** Redis 분산 락이 아니라 단일 JVM 내부의 캐시 재채움 조율을 적용한 결과다.

읽기 1,700 RPS + 구매 10건/초, 60초. VU는 각각 3,000/100, 목록 TTL 2초·다른 캐시 300±30초, revision ON. 한 배포본을 재시작 없이 3회 측정했다.

## 원본 호출·대기

| 조건 | 원본 목록 횟수 | 읽기 1,000건당 목록 원본 | 목록 최대 동시 | 재고 원본 횟수 / 최대 동시 | Hikari pending 최대 | Tomcat busy 최대 |
| --- | ---: | ---: | ---: | --- | ---: | ---: |
| 31번 미적용 | 553 | 6.13 | 27 | 전수 미계측 | 157 | 200 |
| run-1 | 41 | 0.53 | 3 | 601 / 5 | 1 | 200 |
| run-2 | 44 | 0.43 | 4 | 611 / 4 | 129 | 200 |
| run-3 | 38 | 0.37 | 3 | 582 / 4 | 0 | 200 |

풀 대기 표본은 감소했지만 2회차에는 최대 129개로 다시 발생했다. 평균 커넥션 획득 시간은 이전 읽기 표본 63.60ms에서 이번 11.89 / 9.77 / 10.22ms였다. 자원은 5초 표본이므로 pending=0이 순간 대기가 전혀 없다는 뜻은 아니다.

앱 CPU 평균은 169.91 / 180.60 / 180.75%, 최대 약 198%로 2코어를 거의 사용한 표본이 있었다. Tomcat 최대 busy는 세 회차 모두 200이다. DB 중복 조회 감소가 전체 응답 지연 해결로 이어지지는 않았다. 동기식 Future 대기는 DB 커넥션을 점유하지 않아도 Tomcat 스레드는 점유한다. 추가 revision·캐시 재확인, CPU 부담, 요청 처리 진입 전 대기 등이 남아 있을 수 있다. Future 대기 시간과 Tomcat 큐 시간을 직접 잰 것은 아니므로 각각의 기여도를 확정하지 않는다.

Redis 전후 전역 카운터이며 순수 부하 60초 외 검증·회복·수집 구간도 포함한다. 캐시 종류별 수치나 요청 단위 hit율이 아니다. 대기자도 캐시를 재확인하므로 **Redis miss가 늘어도 실제 DB 원본 호출은 줄 수 있다.** 31번과 비교할 때 수집 방식·구간 차이도 고려한다.

## 구현 범위와 한계

- `ConcurrentHashMap`과 `CompletableFuture`로 **캐시 종류 + revision을 포함한 첫 miss 키**의 진행 중 재채움을 조율했다. Redis `SET NX`는 사용하지 않았다.
- 소유 요청만 DB 트랜잭션에 진입한다. 대기자는 트랜잭션 밖에서 기다린 뒤 자신의 revision·캐시를 다시 읽는다. 완성 응답이나 다른 요청의 오류를 공유하지 않는다.
- 성공·실패 시 in-flight 항목을 제거한다. 캐시 비활성/실험 revision bypass 경로는 기존 동작을 유지한다.
- 서로 다른 첫 miss 키·revision은 동시에 실행될 수 있다. 이후 다른 캐시가 만료되거나 revision이 바뀌면 원본 호출이 겹칠 수 있어 전역 동시 원본 1회를 보장하지 않는다. 앱 여러 대 사이의 조율도 하지 않는다.
- Redis 장애·저장 실패 시에는 캐시 재적재를 공유하지 못해 다시 DB를 읽을 수 있다. 별도의 DB 보호 제한을 대체하지 않는다.

## 비교 한계와 예열

31번은 1회, 이번은 3회이며 실행 시점·JVM 상태가 다르다. 이번 배포에는 재고 원본 전수 카운터와 구매 상세 Trace도 추가되어 계측 차이가 있다. 1회차는 배포 직후, 이후는 재시작 없이 실행했다. 숫자 차이 전체를 Single Flight 단독 효과로 단정하지 않는다.

이번 실험은 회차별 300→700 RPS 각 30초 예열을 수행했다. 첫 300 RPS 예열에서 timeout 104건이 발생했고 회복 후 700 RPS는 p99 44ms·오류 0이었다. 2회차 예열 p99 8/11ms, 3회차 6/9ms, 오류 0이다. 초반 실패와 회차별 지연 감소를 숨기지 않는다. 회차가 갈수록 좋아졌다는 것만으로 안정적인 100ms 달성을 주장하지 않는다.

**사용자 요청에 따라 다음 실험부터 최초 예열 1회 → 측정 → 회복 확인 → 다음 측정으로 변경했다.** 반복 실행기는 컨테이너 ID·시작 시각·이미지가 바뀌면 재예열하고 이유를 기록한다. 이번 과거 실행을 재현할 때만 `--warmup-each-run`을 사용한다.
