# Single Flight 적용 후 혼합 부하 3회

31번과 같은 목록 TTL 2초·읽기 1,700 RPS/VU 3,000·구매 10건/초/VU 100·60초 조건을 3회 측정한다. 각 회차 읽기 300→700 RPS 각 30초 예열 후 본 측정한다. 읽기와 구매 전체 각각 p99 ≤ 100ms, 시작 성공률 100%, 미시작·미완료 0을 판정한다.

## 구현

캐시 종류 + revision이 포함된 첫 miss 키로 단일 JVM 안의 재채움을 조율한다. 소유 요청만 DB 읽기 트랜잭션에 진입한다. 대기 요청은 커넥션을 점유하지 않고 기다린 뒤 자신의 revision·캐시를 다시 읽는다. 응답·오류 객체를 다른 요청에 재사용하지 않는다. 소유 요청의 성공·실패 모두 in-flight 항목을 제거한다.

기존 revision·삭제·사용자 경계와 miss의 일관된 읽기 규칙은 유지한다. 분산 락이 아니므로 앱 여러 대 사이에는 중복 원본 조회가 남는다. 다른 첫 miss 키나 revision을 가진 요청은 동시에 실행될 수 있고, 재조회 시 revision이 변경될 수도 있어 전체 재고 원본 호출을 전역 1회로 보장하지 않는다. Redis 장애·저장 실패 때 재적재를 공유할 수 없으면 후속 요청은 다시 원본을 읽는다. 별도의 DB bulkhead를 대체하지 않는다. 대기자는 Tomcat 스레드는 계속 점유한다.

## 검증·수집

새 동시성 테스트로 같은 키 합류, 다른 키/revision 독립 실행, 실패 후 해제, 응답 비공유, 트랜잭션 밖 대기를 확인한다. 기존 전체 회귀·Checkstyle·ArchUnit을 실행한다.

각 회차 전용 구매자 650명·각 10억 포인트를 새로 준비한다. 실제 첫 20개 상품을 순환 구매하고 전후 주문·재고·포인트를 대조한다. seed 응답 동일성 검사는 하지 않는다. 실제 쓰기 결과는 보존한다.

공통 부하·수집·집계 스크립트를 재사용한다. 읽기/구매 지연·성공·미시작, DB 원본 호출, 풀/스레드 대기, Redis 전체 hit/miss를 기록한다. 이번 배포본에는 기존 작업 중 추가한 재고 원본 전수 카운터와 구매 요청 상세 Trace도 포함되므로 31번과 계측 차이를 보고서에 명시한다. CPU·지연 차이를 Single Flight 단독 효과라고 단정하지 않는다.

## 재현 명령

전용 구매자는 `mixed_purchase_fixture.py prepare`로 이미 준비했다. 중복 실행하면 기존 fixture가 있어 중단된다.

```sh
python3 docs/week4/experiments/support/run_mixed_repeats.py \
  --experiment docs/week4/experiments/32-single-flight-mixed \
  --ssh-key <실험용 SSH 키 경로> \
  --warmup-each-run
```

이 명령은 새 실험용 run-* 폴더·fixture로 실행한다. 이미 수행한 폴더를 재사용하면 동일 구매자의 재구매가 되어 독립 회차가 아니므로 재측정용 새 폴더를 준비한다. SLO 미달만으로 다음 회차를 생략하지 않되, 수집·회복 실패나 구매 정합성 실패 시 중단한다.

2026-10-16 사용자 결정: 다음 반복 실험부터 최초 예열 1회와 회차 간 회복 확인을 기본으로 한다. 위 명령의 `--warmup-each-run`은 이미 수행한 이번 실험의 과거 조건을 재현하기 위한 옵션이다.
