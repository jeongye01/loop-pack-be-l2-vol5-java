## 환경 기록

- **실행 조건 기록:** [장비 사양](environments/ec2-seoul.md)·배포 버전·설정·데이터 상태를 시작 시 저장하고, 종료 시 변경 여부를 확인한다.
- **실행 중 기록:** k6로 처리량·지연·오류를 기록하고, SSH로 서버 자원 사용과 Actuator의 DB 연결 사용·대기를 수집해 파일로 남긴다. 로컬 부하 생성기의 자원 사용도 함께 기록한다.

Prometheus·Grafana 구축은 필요해지면 진행한다. 수집 시각·간격과 누락 항목을 남기며 비밀번호·개인키는 저장하지 않는다.

CPU 수치는 아래 기준을 구분해서 표시한다. Docker 사용률과 서버의 `/proc/stat` 원본은 모두 `resources.json`에 수집한다.

| 표시 이름 | 의미 |
| --- | --- |
| 컨테이너 CPU — 모든 코어 사용량 합산（상한: vCPU 수 × 100%） | Docker 사용률. 여러 코어에서 소비한 CPU 시간을 합산하며 특정 코어 하나의 사용률이 아니다. 2 vCPU에서 196.7%는 약 1.967코어를 사용한 양 |
| 컨테이너 CPU — 서버 전체 용량 대비（상한: 100%） | 위 합산값 ÷ 서버 vCPU 수. 예: 196.7% ÷ 2 = 98.4%. 컨테이너가 차지한 비율이며 다른 프로세스를 포함한 서버 전체 사용률은 아님 |
| 서버 CPU — 전체 용량 대비（상한: 100%） | `/proc/stat`의 `cpu` 행에서 샘플 간 시간 차이로 계산. 모든 코어의 사용 시간을 모든 코어의 총 시간으로 나눈 비율이며 다른 프로세스도 포함 |
| 서버 CPU — 개별 코어별（각 상한: 100%） | `/proc/stat`의 `cpu0`, `cpu1` 등을 각각 계산. 코어마다 따로 표시하며 Docker 합산값만으로 개별 코어 사용률을 알 수는 없음 |

현재 baseline에서 제시한 196.7%와 98.4%는 같은 Docker 측정값과 그 환산값이다. 서버 전체·코어별 CPU는 원본만 수집했으며 별도 사용률 집계는 아직 하지 않았다.

## 실행·중단·회복

1. 버전·장비·데이터·요청·계측 조건을 고정하고, 상품 목록의 내용·순서·페이지 정보가 예상대로 나오는지 확인한다. 측정 중에는 다른 부하 테스트를 돌리거나 앱을 배포하거나 DB에 데이터를 넣지 않는다.
2. 준비 실행은 통계에서 제외한다. k6 `constant-arrival-rate`로 요청을 보내고 RPS·시간·VU·timeout·반복 번호를 기록한다.
3. 상품 내용·순서·페이지 정보가 예상과 다르면 측정을 즉시 멈춘다. 응답 시간이 제한을 넘거나 서버가 오류를 반환하거나 부하 도구가 예정한 요청을 보내지 못하면, RPS를 더 올리지 않고 당시 부하와 오류를 기록한다.
4. 부하를 멈춘 뒤 남은 요청이 모두 끝나고, 사용 중이거나 기다리는 DB 연결이 없어졌는지 확인한다. 상품 조회가 다시 정상 응답하고 CPU·메모리 사용이 안정되면 다음 실험을 시작한다. 60초 안에 회복되지 않으면 다음 실험은 진행하지 않는다.
5. 같은 조건의 반복 결과를 모두 비교한다. 실패·중단 Run도 보존한다.

부하 레벨은 [baseline](01-baseline/plan.md) 완료 후 정한다. 탐색 절차·실행 시간은 개별 계획서에 둔다. 서비스 SLO는 아직 미정이다. 데이터 적재는 별도로 수행하고 `ddl-auto=none`을 유지한다.

## Trace: 요청 한 건의 기록

**Latency:** 로컬 k6의 HTTP 호출 직전부터 응답 본문 수신 완료까지의 시간. 연결 수립·네트워크·서버 처리 시간을 포함하며, 서버 처리 시간만을 뜻하지 않는다. timeout·오류로 끝난 요청은 종료까지 걸린 시간을 정상 응답과 구분해 기록한다. 개선 전후에도 같은 기준을 적용한다.

**서버 처리 시간:** Tomcat이 요청 처리를 시작해서 응답 처리를 마칠 때까지의 시간. 앱 로직·DB 연결 대기·쿼리 실행·응답 생성을 포함한다. Tomcat 접근 로그에 기록하고, 같은 `requestId`로 k6 요청과 연결한다. 클라이언트 latency와의 차이를 전부 네트워크 시간으로 보지는 않는다.

| 기록 | 내용 |
| --- | --- |
| 요청 식별·입력 | runId·requestId·operation, brandId·sort·page·size·테스트 사용자 ID |
| 클라이언트 지연 시간 | `latencyMs`: 로컬 k6의 HTTP 호출 직전부터 응답 본문 수신 완료까지의 시간(ms). 연결 수립·네트워크·서버 처리를 포함. timeout·오류는 종료까지의 시간을 별도 분류 |
| 서버 처리 시간 | `serverDurationMs`: 같은 요청의 Tomcat 처리 시간(ms). `requestId`로 서버 로그와 연결해 Trace에 추가 |
| 요청 결과 | HTTP 상태·오류 코드, 정상 / 내용 불일치 / HTTP 오류 / 전송 오류·timeout, 불일치 기대값·실제값 |
| 쿼리 실행 시간 | 해당 요청에서 실행한 SQL과 각 SQL의 실행 시간 |
| 서버 내부 구간 | `stages`: JDBC 실행·결과 읽기·커넥션 작업, 리포지토리·서비스·컨트롤러, 응답 쓰기의 호출 수와 시간. `totalMs`는 하위 작업 포함, `selfMs`는 하위 작업 제외 |

구간별 합계는 `selfMs`로 계산한다. JDBC 시간은 DB 통신을 포함하며, 응답 쓰기는 직렬화·출력·MVC 마무리를 묶은 시간이다. Tomcat 전체와 `request.pipeline.totalMs`의 차이는 별도 미계측 구간으로 남긴다. 상세 계측 자체의 비용이 포함되므로 기존의 미분리 시간을 소급해서 확정하지 않는다.

응답 내용·상품 순서·페이지 정보가 기준 응답과 같은지 확인하고, 요청 실패는 별도로 기록한다.

## 결과 저장

EC2에 SSH로 접속해 **Docker 컨테이너 안의 Tomcat·앱 로그**를 가져온다. 요청 ID·요청 경로·HTTP 상태·서버 처리 시간·오류 메시지를 로컬에 저장하고, `requestId`로 k6 기록과 연결해 Trace를 만든다.

표준 출력 로그는 `docker logs`로 수집하고, 컨테이너 내부 파일 로그는 `docker cp`로 EC2에 꺼낸 뒤 로컬로 전송한다. Docker가 처리 시간을 자동으로 기록하는 것은 아니며, 요청 ID·처리 시간을 남기는 실험용 Tomcat·SQL 계측 코드는 작성돼 있으며 서울 배포 후 수집 검증이 필요하다.

실험별 `plan.md`, `report.md`를 두고 원본은 `results/{runId}/`에 저장한다.

| 파일 | 내용 |
| --- | --- |
| `config.json`, `environment.json` | 실행 조건·버전·장비·데이터·시작/종료 환경 |
| `expected.json`, `traces.jsonl` | 기준 응답·개별 요청 기록 |
| `result.json`, `summary.json` | 식별 정보·실행 시각·준비/측정 구분·집계·검증·중단 사유·회복 여부·원본 경로, k6 요약 |
| `resources.json`, `server.log` | 자원 시계열·서버 로그 |

미측정 값은 null과 사유를 남기고 기존 Run을 덮어쓰지 않는다. 보고서 수치 표는 JSON에서 생성하며 관찰·가설·한계·결론은 구분해 작성한다.

## Tomcat 공통 지표

실험 Compose에서 `SERVER_TOMCAT_MBEANREGISTRY_ENABLED=true`로 활성화한다. 기존 Prometheus 전체 수집에 포함하고 `resource-summary.json`의 `tomcatThreadsByConnector`에 집계한다.

| 지표 | 의미 |
| --- | --- |
| `tomcat_threads_busy_threads` | 표본 시점에 작업 중인 스레드 수 |
| `tomcat_threads_current_threads` | 현재 생성된 스레드 수 |
| `tomcat_threads_config_max_threads` | 설정된 최대 스레드 수 |

`name` 라벨로 앱 8080과 관리 8081을 구분한다. 누락은 0으로 해석하지 않는다. 기본 5초 표본의 최대값은 순간 최대값을 보장하지 않는다. busy가 max에 도달하면 스레드 포화 근거지만 큐 대기 시간·길이를 직접 측정한 것은 아니다. `accept-count`는 TCP 연결 backlog 설정으로 작업 큐 실측값이 아니다.

활성화 근거: [Spring Boot Tomcat metrics](https://docs.spring.io/spring-boot/reference/actuator/metrics.html).

## 실험 로그 비동기 출력

`experiment-async` 프로필은 `EXPERIMENT_TRACE`만 별도 AsyncAppender로 보낸다. 기존 JSON·Docker 수집 형식은 유지한다. 큐 8,192건, INFO 폐기 비활성(`discardingThreshold=0`), 큐 포화 시 대기(`neverBlock=false`), 정상 종료 flush 최대 30초다. 강제 종료·출력 장애에서도 영구 보존된다는 의미는 아니다.

공통 수집: `experiment_log_queue_size`(대기 건수), `experiment_log_queue_remaining`(남은 자리), `experiment_log_queue_capacity`(용량). 5초 표본은 순간 최대를 보장하지 않는다. 큐가 0이어도 worker가 가져간 배치가 남을 수 있어 종료 후 추가 수집 구간을 두고 요청 ID 전수 연결·중복/누락 검증을 유지한다. 비동기 실험은 `requireAsyncLogMetrics=true`, `logDrainSeconds=10`을 사용한다.

## 상세 기록 샘플링

`sampled-trace-experiment-compose.yml`을 비동기 로그 Compose와 함께 적용하면 요청 시작 시 1%를 무작위 선택한다. 선택되지 않은 요청은 상세 SQL·단계 계측과 JSON 생성을 건너뛴다. Micrometer의 전체 HTTP 통계와 기존 활성 요청 게이지 수집 범위는 유지한다. 현재 상세 기록 대상은 유효한 `X-Run-ID`·`X-Request-ID`가 있는 상품 목록 요청이다.

`EXPERIMENT_TRACE_SAMPLE_RATE`: `0.01`은 약 1%, `1`은 전수, `0`은 상세 계측 없음. 미설정 기본값은 기존 실험 재현을 위해 `1`이다. 선택된 JSON에 `sampleRate`를 기록한다. 오류·느린 요청의 상세 기록도 같은 확률로 선택되며 전수 보존하지 않는다. 기존 애플리케이션 오류 로거는 변경하지 않는다. Tempo 전송은 아직 적용하지 않았다.

샘플링 결과의 서버 지연·SQL 통계는 선택된 요청에만 해당한다. 기존 실행기의 요청 ID 전수 연결 검증은 그대로 유지하며, 샘플링 실험을 전수 검증 통과로 표시하지 않는다. 샘플링 부하 실험 전에는 별도의 표본 연결 검증이 필요하다. 성능 기준선은 17번 실험의 상세 로그 출력 OFF 1회 측정(평균 23ms, p99 237ms)이며, 샘플링 적용 성능은 별도 측정한다.
