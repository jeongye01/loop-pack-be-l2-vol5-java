# 조회 성능 실험 계획서: 최적화 후 좋아요순 부하 한계와 병목

- 실험 ID: 07-load-likes
- 상태: 좋아요순·최신순 50 RPS 예비 측정 완료. 단계별 탐색 미실행
- 작성일: 2026-10-14
- 실행 버전: 코드 기준 `3bc0f0c`. 실행 시 앱 이미지·배포 SHA와 DB 인덱스를 별도 기록한다.
- 공통 절차·결과 형식: [프로토콜](../protocol.md)
- 장비 사양: [서울 EC2](../environments/ec2-seoul.md)

## 실험 내용

**무필터 좋아요순 첫 페이지에 부하를 늘려, 정상 처리 가능한 RPS와 최초 병목을 찾는다.**

우선 **1 RPS 준비 부하 30초 → 회복 확인 → 50 RPS 본 측정 60초**를 1회 실행한다. 아래 단계별 탐색은 예비 결과를 보고 결정한다.

비교 요청으로 `sort=latest`도 동일 조건으로 1회 측정한다. 좋아요순 종료·회복 후 순차 실행하며, 설정은 `config.json`과 `config-latest.json`으로 구분한다.

```http
GET /api/v1/products?sort=likes_desc&page=0&size=20
X-USER-ID: 1
```

| 조건 | 값 |
| --- | --- |
| 데이터 | `perf_skewed_1m_v1`: 상품 100만·좋아요 69만·브랜드 1,000·사용자 24만 |
| 부하 | k6 `constant-arrival-rate`, 1 → 2 → 5 → 10 → 20 RPS |
| 확장 | 20 RPS까지 정상이면 40 → 80 RPS처럼 배증하여 최초 실패 구간 탐색 |
| 경계 확인 | 마지막 정상·최초 실패 RPS 사이를 이분 탐색, 간격 1 RPS 이하에서 양쪽 각각 3회 확인 |
| Run | 준비 부하 30초 제외, 본 측정 60초, VU 100, 요청 timeout 5초 |
| 정상 기준 | 예약 요청 누락 없이 모든 요청이 5초 이내 정상 응답하며, 상품·순서·`last`가 기대값과 일치 |

5초는 이번 실험의 timeout 기준이다. 실제 응답 품질은 p50·p95·p99로 별도 기록한다. 중단·회복은 공통 프로토콜을 따른다.

| 확인할 병목 | 함께 볼 증거 |
| --- | --- |
| 좋아요 집계·정렬 | 요청별 SQL 수·누적 시간, 목록 조회 단계 시간 |
| DB 자원 | DB CPU·메모리·디스크 I/O와 SQL 지연의 동반 증가 |
| DB 커넥션 대기 | Hikari active·pending·획득 시간과 서버 처리 시간 |
| 앱 처리·요청 대기 | 앱 CPU·메모리·GC, 처리 중 요청 수, 서버 단계별 시간 |
| 부하 발생기·통신 | 목표/실제 요청 시작 수·`dropped_iterations`, 발생기 자원, 클라이언트와 서버 시간 차이 |

결과는 **RPS별 처리량·p95·오류율·주요 자원** 표와 **최초 실패 구간의 병목 근거**로 정리한다. CPU는 전체 용량 대비 사용률과 Docker 코어 합산 사용률을 구분한다. VU 부족이나 발생기 한계는 서버 한계로 판정하지 않는다.

## 변경 사항

현재 최적화된 쿼리·인덱스로 측정한다. 결과 캐시와 저장된 좋아요 카운터는 사용하지 않는다. DB 버퍼·JVM 워밍업을 허용하며, 측정 중 데이터 변경은 없다.

첫 baseline의 공통 실행·수집 도구를 재사용한다. 실행 전 무필터 입력, 현재 `last` 응답 계약, 배포 인덱스, SQL·서버 단계·자원 지표 수집을 확인한다. 실행 설정의 RPS 상한도 이번 탐색 단계에 맞춘다.

## 적용 전 기록

- [첫 baseline 계획서](../01-baseline/plan.md): 부하 증가·경계 반복 측정 방식 참고. 데이터와 요청 조건이 달라 성능 배수로 직접 비교하지 않는다.
- [좋아요순 N+1 개선](../04-optimize-likes-query/report-batch-reads.md) · [좋아요 수 재사용](../04-optimize-likes-query/report-reuse-like-count.md): 무필터 목록 SQL 5회. 재사용 실험의 단건 평균은 서버 약 130ms·클라이언트 약 144ms.
- 실행 직전 같은 조건의 무부하 요청 3회를 다시 기록하여 이번 부하 결과의 기준으로 삼는다.
