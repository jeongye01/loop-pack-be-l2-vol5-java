# 50 RPS 예비 부하 테스트: 좋아요순·최신순

**최신순은 50 RPS를 정상 처리했다. 좋아요순은 DB CPU 포화와 커넥션 대기로 실패했다.**

무필터·첫 페이지 20개·사용자 1, 각 1 RPS 준비 30초 후 회복 확인 → 50 RPS 60초. timeout 5초·VU 100. 상품 100만·좋아요 69만, 캐시·저장 카운터 없음. 순차 실행했으며 두 실행 모두 종료 후 회복을 확인했다.

자원은 실행별 13회 표본의 평균·관측 최대다. Docker CPU와 호스트 CPU는 측정 범위·시점이 다르다. 디스크는 호스트 `nvme0n1`의 표본 간 증가량이며, 읽기 0은 물리 디스크 읽기가 관측되지 않았다는 뜻이다.

좋아요순은 요청마다 좋아요를 집계·정렬한다. 부하 중 해당 SQL 750회 평균은 **3,425.4ms**였다. DB의 두 코어가 모두 포화되고, 커넥션 점유가 길어져 다음 요청의 대기가 쌓였다. 로그에서도 `Connection is not available, request timed out after 3000ms (total=40, active=40, idle=0)`를 확인했다. 이 3초는 Hikari 커넥션 획득 timeout으로, 클라이언트의 5초 timeout과 다르다.

```text
좋아요 집계·정렬 반복 → DB CPU 포화 → SQL 지연
→ 커넥션 40개 점유 → 획득 대기·500 오류 → 클라이언트 timeout
```

클라이언트 timeout 이후 서버 작업도 남아 처리 중 요청이 관측 최대 136개까지 쌓였다. k6 역시 VU 100개가 묶이면서 1,596건을 시작하지 못했다. 따라서 **50 RPS 유지에 실패한 결과이며, 이 수치로 최대 처리량을 확정하지 않는다.** 메모리·디스크보다 DB CPU와 이어지는 커넥션 대기가 주요 병목으로 보인다.

최신순은 인덱스에서 필요한 행만 읽는 경로로, 이번 50 RPS에서는 커넥션 대기가 관측되지 않았다. 다음 한계 탐색은 좋아요순을 50 RPS보다 낮춰 진행할 필요가 있다. 최신순의 최대 처리량은 아직 측정하지 않았다.
