# 준비 부하 후 최신순 캐시 재측정

**시작한 요청은 3회 모두 성공했지만, p99 ≤ 200ms·미시작 0건 목표는 달성하지 못했다.** 1,000 RPS 준비 기준 통과가 1,700 RPS 측정의 안정성을 보장하지는 않았다.

고정 데이터 · 최신순 · 브랜드 없음 · 첫 페이지 20개 · Redis hit · 1,700 RPS · VU 3,000 · 60초 · 3회. 실행 중 전체 로그 집계는 하지 않았다.

성공률 분모는 실제 시작 요청이다. timeout·HTTP 오류·미완료는 모두 0건이며, 미시작은 별도 실패 조건이다. 실행기 `passed`는 수집·응답 검증 결과로, 3회차도 지연 SLO는 미달이다. 목표 건수는 회당 102,000건이며 실제 시작/미시작 합계는 k6 스케줄링 경계에서 소폭 차이 날 수 있어 원본 값을 유지했다.

## 준비 확인

300 → 700 RPS 각 30초 후 1,000 RPS를 30초씩 4회 실행했다. 마지막 두 번은 p95 **21 → 20ms**, 앱 CPU 평균 **40.18 → 38.86%**, JIT 증가율 **11.23 → 11.53ms/초**, 오류·미시작 0건으로 사전 기준을 통과했다. [준비 판정](stabilization.json)

## 무엇이 남았나

| 지표 | 1회 | 2회 | 3회 |
| --- | ---: | ---: | ---: |
| 앱 CPU 평균 — 전체 2코어 기준 | 72.6% | 63.2% | 72.3% |
| DB CPU 평균 — 전체 2코어 기준 | 20.4% | 20.2% | 21.9% |
| DB 커넥션 대기 평균 | 0.028ms | 0.022ms | 0.029ms |
| Hikari 대기 요청 최대 — 표본 | 0 | 0 | 0 |
| 요청당 SQL | 1 | 1 | 1 |
| JIT 누적 시간 증가 | 3.96초 | 1.89초 | 1.03초 |
| 동일 요청의 클라이언트−서버 시간 차이 평균 | 826ms | 852ms | 257ms |

캐시 miss·fill 증가 없이 조회는 hit로 처리됐고 SQL은 사용자 확인 1회만 남았다. 모든 요청의 서버 로그 연결·응답 비교·수집 검증이 완료됐다.

이전 실험의 큰 JIT 증가와 분석 작업 겹침을 줄였지만 클라이언트 지연은 여전히 크다. 서버 계측 구간은 평균 약 10~11ms로 비슷한 반면, 시간 차이는 대부분 응답 첫 바이트 대기에 나타났다. **워밍업만으로 설명할 수 없으며, 다음 진단은 부하 발생기·네트워크·서버 계측 시작 전 대기와 응답 전송 구간을 나눠 확인해야 한다.** 현재 자료만으로 특정 구간을 원인으로 확정하지 않는다. JIT 누적 시간은 요청 정지 시간과 다르다.
