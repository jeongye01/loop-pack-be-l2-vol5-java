# TTL 2초 + 구매 쓰기 혼합 부하

## 목적과 판정

목록 캐시가 만료되는 동안 구매 쓰기를 함께 보내 읽기·쓰기 성능을 각각 관찰한다. 각각 클라이언트 p99 ≤ 100ms, 성공률 100%, 미시작·미완료 0건을 목표로 한다. 쓰기는 주문 생성→확정 전체 시간이며 생성·확정 개별 시간도 기록한다.

## 조건

- 읽기: 최신순·브랜드 없음·page=0·size=20, 1,700 RPS, VU 3,000.
- 쓰기: 초당 구매 10건, VU 100. 주문 생성 POST→확정 POST, 상품 1개·수량 1. 약 20 HTTP RPS 추가.
- 본 측정: 두 시나리오를 동시에 60초, 1회. 읽기만 300→700 RPS 각 30초 예열한다.
- 목록 TTL 2초·jitter 0. 다른 캐시 300±30초. revision ON, hit/miss 트랜잭션 분리. Single Flight 없음.
- 직전 30번 실험 배포본을 그대로 사용한다. 이번 턴의 미배포 계측 수정은 측정 대상이 아니다.
- 첫 페이지 상품 20개를 순환 구매한다. 신규 전용 구매자 650명·각 10억 포인트를 격리 실습 DB에 준비한다. 한 구매에 다른 사용자를 배정해 동일 포인트 행 경합을 피한다. 기존 충분한 재고를 사용한다.
- 선행 구매 검증은 별도 사용자로 실행하고 본 측정에 섞지 않는다. timeout 등 모호한 쓰기는 자동 재시도하지 않는다.
- 사용자 요청에 따라 목록 seed 응답 일치 검사는 하지 않는다. HTTP/응답 SUCCESS 및 실제 구매 항목·금액·확정 결과는 확인한다.

## 수집과 비교

공통 products.js·RemoteRunner·run_combined_slo.py를 재사용한다. 읽기와 구매 전체의 요청 수·성공률·평균·p50·p95·p99·오류를 분리한다. 구매 생성·확정 지연도 별도 기록한다. Redis·DB·앱 자원, 원본 목록 조회 횟수·최대 동시 호출, DB 재고 감소·포인트 차감·확정 주문을 확인한다.

구매 확정은 재고 revision을 변경한다. 최신순 목록 TTL 만료와 재고 캐시 무효화가 겹치는 조건이다. 30번 읽기 단독 실험은 참고치이며 이번 한 번의 결과만으로 정확한 성능 차이를 일반화하지 않는다.

실험용 신규 사용자·주문·포인트와 구매에 따른 재고 변화는 기록으로 남긴다. 결과를 되돌리기 위한 기존 데이터 삭제나 덮어쓰기는 하지 않는다.
