# TTL 2초 + 구매 쓰기 혼합 부하 결과

**읽기 p99 2,524ms, 구매 전체 p99 4,691ms. 둘 다 100ms SLO 미달이다.** 시작된 요청은 모두 성공했지만 읽기 11,740건이 미시작됐다. 실제 혼합 부하를 60초간 1회 실행했다.

## 조건

- 최신순·무브랜드·page=0·size=20 통합 상품 목록: 1,700 RPS, VU 3,000.
- 구매: 초당 10건, VU 100. 주문 생성→확정 POST 2회, 상품 1개·수량 1. 목록의 첫 20개 상품에 순환 분산.
- 목록 TTL 2초·jitter 0, 나머지 캐시 300±30초, DB revision ON, hit/miss 트랜잭션 분리. Single Flight 없음.
- 읽기와 구매를 동시에 60초 실행. 구매 전체 시간은 생성 요청 시작부터 확정 응답 검증까지다.
- 별도 EC2 부하기, 사설 주소로 호출. 직전 30번과 같은 서버 이미지 `commerce-api:stampede-deb9ed7a9a3a`를 재배포 없이 사용했다.
- 새 구매자 650명·각 10억 포인트를 준비. 본 측정은 매 구매마다 다른 사용자를 사용한다. 충분한 기존 재고를 사용해 품절·포인트 부족에 따른 실패를 배제했다.
- 목록 seed 응답 일치 검사는 사용자 요청으로 제외했다. HTTP 성공·응답 SUCCESS와 구매 상품·금액·상태 검증은 수행했다.

## 읽기·쓰기 성능

단위 ms. 클라이언트 전수 측정이며 성공 응답만 따로 골라낸 결과가 아니다. 이번에는 시작된 요청이 모두 성공했다.

| 구분 | 성공/시작 | 평균 | p50 | p95 | p99 | 100ms 판정 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 읽기 — 목록 조회 | 90,261 / 90,261 | 1,887.86 | 1,963 | 2,351 | **2,524** | 미달 |
| 쓰기 — 구매 전체 | 600 / 600 | 3,697.39 | 3,905 | 4,538.30 | **4,691.13** | 미달 |
| 쓰기 상세 — 주문 생성 | 600 / 600 | 1,888.26 | 1,949 | 2,329.65 | 2,499.05 | 진단 지표 |
| 쓰기 상세 — 주문 확정 | 600 / 600 | 1,809.08 | 1,966 | 2,390.15 | 2,580 | 진단 지표 |

구매 전체 p99는 각 단계 p99의 합이 아니라 구매별 전체 소요 시간으로 계산했다. HTTP 쓰기 1,200건은 구매 600건에 해당한다.

| 항목 | 읽기 | 구매 |
| --- | ---: | ---: |
| 목표 부하 | 1,700 요청/초 | 10 구매/초 |
| 계획 건수 | 102,000 | 600 |
| 실제 시작·완료 | 90,261 | 600 |
| 미시작 | **11,740** | 0 |
| 미완료 | 0 | 0 |
| HTTP 오류·timeout | 0 | 0 |
| 시작된 작업의 성공률 | 100% | 100% |
| k6 완료율 (`rate`) | 1,451.74 요청/초 | 9.65 구매/초 |

k6 rate는 마지막 요청을 기다리는 종료 구간까지 포함한 약 62.18초 기준이다. 60초 동안 구매 600건은 모두 시작했고 종료 대기 중 완료한 건도 포함한다. 읽기 `started+dropped=102,001`은 실행 경계의 1건 차이다. 구매 600건은 모두 시작했으므로 전체 `dropped_iterations=11,740`은 읽기 미시작으로 확인된다. 이는 timeout이나 서버 오류와 다르다. **시작 요청 성공률 100%만으로 목표 1,700 RPS를 달성했다고 판정하지 않는다.**

예열은 읽기 위주이며 구매는 3건 동작 확인만 했다. 따라서 구매 경로의 충분한 워밍업을 증명한 실험은 아니다. 본 측정의 60개 1초 구간 모두 읽기 p99가 100ms를 넘었고 최악 구간은 2,770.32ms였다. 다만 1회 측정이므로 반복 재현과 대조 실험이 필요하다.

부하 종료 후 서버 회복과 자원·로그 수집은 모두 성공했다. `result.json.status=collected`, k6 exit code=0이다. 상위 실행기는 목표 요청 미달을 감지해 결과를 보존하고 의도적으로 비정상 종료했다. 수집 실패와 SLO 실패를 구분한다.

| InnoDB 행 락 대기 증가 | 280회, 누적 11,051ms |

자원은 5초 표본이다. 최대값이 측정 내내 지속됐다는 뜻은 아니다. 원본 목록 호출 수·최대 동시는 전수 계측이고 인증·revision·재고 원본 SQL을 전부 센 수치는 아니다.

코드상 흐름은 다음과 같다.

```text
구매 확정 → 재고 저장 → stock 그룹 revision 변경
→ 다음 목록 요청의 재고 캐시 키 변경 → miss
→ 목록 응답 조립을 DB 읽기 트랜잭션 안에서 재시도
→ revision 재조회·필요한 재고 원본 조회·Redis 접근
→ 그동안 DB 커넥션 점유
```

`CacheWriteConfiguration`은 `StockRepositoryAdapter.save` 때 `CacheVersions.changed("stock")`를 호출한다. `ProductReadFacade`는 이 revision으로 재고 캐시 키를 만들고, `CatalogReadTransaction`은 부분 miss에도 응답 조립 전체를 트랜잭션 안에서 다시 실행한다. 이번에는 재고가 줄어도 모든 상품의 `soldOut=false`는 유지되지만 revision은 구매마다 변경된다.

읽기 Trace 876건 중 **251건에서 revision 재조회**, **65건에서 재고 원본 호출**을 확인했다. revision 재조회 후 다른 요청이 채운 캐시를 hit할 수도 있어 두 수치는 같지 않다. 단순 목록 TTL 만료뿐 아니라 구매에 따른 재고 캐시 miss가 읽기 트랜잭션과 커넥션 점유를 늘리는 경로가 존재한다.

**확인된 현상은 커넥션 풀 포화·대기, Tomcat 스레드 포화, 앱 CPU 포화에 가까운 사용량이다.** 이 조건에서 읽기·쓰기가 함께 지연됐다. 클라이언트 지연은 서버 Trace보다 훨씬 크다. Trace 시작 전 요청 대기 등이 포함될 가능성이 있으나 서로 다른 표본의 p99를 빼서 큐 대기 시간을 확정하지 않는다.

Redis get 오류 카운터도 전후 18 증가했다(put 증가 0). 실패 시 fallback이 추가 부하에 기여했을 가능성을 배제하지 않는다. 행 락 대기는 집계치만 있으므로 특정 revision 행이 유일한 원인이라고 단정하지 않는다. 이번 배포본에는 쓰기 서버 Trace와 재고 원본 전수 카운터가 없어 쓰기 내부 지연을 단계별로 확정하지 못한다.

부하기 k6의 `ps %CPU`는 첫 표본 744%에서 후반 113~125%로 내려갔다(8코어). 이 값은 순간 CPU가 아니라 프로세스 수명 기준 비율이다. 서버 측 포화는 확인했지만 부하기 영향을 완전히 배제한 실험이라고 주장하지 않는다.

## 현재 현상 정리와 Single Flight 비교 후보 (2026-10-16)

**구매를 함께 보내자 읽기와 쓰기가 함께 느려졌다.** 읽기 단독 p99는 138 / 112 / 144ms였고, 혼합에서는 읽기 2,524ms·구매 전체 4,691ms였다. 시작된 작업은 모두 성공했지만 읽기 11,740건은 시작하지 못했다. 따라서 기능상 구매 실패보다 지연·처리량 목표 미달이 이번에 확인된 문제다.

우선 의심하는 경로는 **구매에 따른 재고 그룹 무효화 → 동시 cache miss → 읽기 트랜잭션 증가 → 공유 DB 커넥션 풀 대기 → 읽기·쓰기 동반 지연**이다. 상품 하나의 재고 변경이 공통 `stock` revision을 바꾸므로, 기존 revision을 포함하는 다른 재고 캐시 키도 더 이상 현재 조회에 사용되지 않는다. 이번에는 품절 표시가 그대로여도 구매마다 이 갱신이 발생했다.

이 가설을 뒷받침하는 관측은 revision 재조회 표본 251/876건, 커넥션 40/40 사용·대기 최대 157개, Tomcat 200/200 사용이다. 다만 **revision 재조회 251건이 모두 실제 원본 재고 조회라는 뜻은 아니다.** 다른 요청이 채운 캐시를 재시도에서 사용할 수도 있다. 앱 CPU, 행 락 대기, Redis get 오류도 관측되어 무효화만을 단독 원인으로 확정하지 않는다.

다음 비교 후보는 **Single Flight로 같은 키·같은 revision의 동시 재채움을 하나로 합치는 것**이다. 먼저 재채움하는 요청을 나머지가 기다렸다가 캐시를 다시 확인하도록 해 원본 중복과 커넥션 점유가 줄어드는지 본다. revision 변경과 정합성 규칙은 유지하며, 서로 다른 revision의 응답을 공유하지 않는다.

비교할 핵심 지표는 읽기·구매 각각의 p99/성공률/미시작 수, 원본 목록·재고 호출 수와 최대 동시 호출, Hikari active/pending이다. **기다리는 요청이 이미 DB 커넥션을 가진 채 대기하면 풀 포화를 해소하지 못할 수 있으므로 대기 위치도 확인한다.** Single Flight는 키가 계속 바뀌는 빈도 자체나 모든 쓰기 락·CPU 비용을 없애는 방법은 아니다.

이 항목은 다음 실험 후보 기록이며 아직 Single Flight를 구현·배포하거나 개선 효과를 측정하지 않았다.

## 이전 결과와 비교·다음 실험

30번 읽기 단독은 p99 138 / 112 / 144ms, 이번 혼합은 2,524ms다. 같은 배포본·읽기 부하·TTL을 사용했지만 실행 시점·JVM 상태가 다르며, 이번은 쓰기가 추가된 1회 결과다. 증가분 전체를 한 원인의 정확한 비용으로 환산하지 않는다.

다음은 동일 혼합 조건을 고정하고 병목 원인을 분리한다.

1. 같은 계측으로 읽기 단독 대조·혼합 반복을 수행해 편차와 재현성을 확인한다.
2. 재고 원본 전수 호출 수·쓰기 단계 Trace·락 대상을 수집해 재고 miss, 트랜잭션 점유, 쓰기 락의 비중을 구분한다.
3. 그 뒤 Single Flight 등 한 가지 완화책만 추가하여 원본 중복·풀 대기·읽기/쓰기 p99를 비교한다. 커넥션·스레드 수만 먼저 늘려 해결됐다고 판단하지 않는다.
