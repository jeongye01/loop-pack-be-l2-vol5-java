# 조회 경로별 캐시 TTL·쓰기 후 갱신 검증

- 일자: 2026-10-15
- 기준: `00f8ff8` + 이번 검증 테스트 추가분
- 환경: 로컬 Spring Boot·MockMvc, 실제 MySQL·Redis 7.0 Testcontainers, `catalog.cache.enabled=true`
- 범위: 캐시 대상 HTTP 조회 11가지, 쓰기 10가지. **EC2 배포·부하 테스트 결과가 아니다.**

## 조회 경로

각 경로에서 첫 조회 → Redis TTL 확인 → 같은 요청 → TTL 비연장 → 대상 키 만료 → 재조회·재적재를 확인한다.

| 조회 | 조건 | 결과 |
| --- | --- | --- |
| 상품 목록 최신순 | 브랜드 없음 / 있음 | 통과 |
| 상품 목록 가격순 | 브랜드 없음 / 있음 | 통과 |
| 상품 목록 좋아요순 | 브랜드 없음 / 있음 | 통과 |
| 상품 상세 | 상품 ID | 통과 |
| 내 좋아요 목록 | 본인 userId | 통과 |
| 관리자 브랜드 목록 | 관리자 인증 | 통과 |
| 좋아요 수 일괄 조회 | 상품 ID 목록 | 통과 |
| 재고 일괄 조회 | 상품 ID 목록 | 통과 |

TTL 생성 범위는 **270~330초**. Redis 초 단위 잔여 TTL 검사는 경과 시간을 고려해 269~330초로 확인한다. hit 검사는 대상 키를 120초로 줄인 뒤 응답이 같고 잔여 TTL이 119~120초인지 확인한다. 만료·재적재 검사는 대상 키만 1ms로 줄여 실제 삭제를 확인한 뒤 요청한다. 실제 5분을 기다린 실험은 아니며, 생성 범위 자체는 별도 단위 테스트로 확인한다.

## 쓰기 후 유효 범위

| 쓰기 | 바뀌는 revision | 확인할 응답 |
| --- | --- | --- |
| 상품 생성 | catalog + stock | 3종 정렬·브랜드 필터 목록에 새 상품 포함 |
| 상품 수정 | catalog | 목록 3종·상세·내 좋아요의 상품 정보 갱신 |
| 상품 삭제 | catalog | 상세 404, 목록·내 좋아요·좋아요 수·재고에서 제외 |
| 브랜드 생성 | catalog | 관리자 브랜드 목록에 추가 |
| 브랜드 수정 | catalog | 목록 3종·상세·내 좋아요·브랜드 목록에 새 이름 |
| 브랜드 삭제 | catalog | 소속 상품 상세 404, 고객 목록·좋아요 수·재고에서 제외 |
| 관리자 재고 변경 | stock | 품절 상태 즉시 갱신 |
| 좋아요 등록·취소 | 해당 사용자 likes | 내 좋아요 목록 즉시 갱신, 다른 사용자 revision 유지 |
| 주문 확정 | stock | 재고 차감 후 품절 상태 갱신 |

상품·브랜드 CUD, 재고 변경, 좋아요 등록·취소는 **실제 HTTP 쓰기 API**로 호출한다. 주문 확정은 기존 `OrderUseCase` 트랜잭션 경로로 실행하고 HTTP 재고 응답을 확인한다. 각 쓰기 전후 catalog·stock·사용자별 revision을 비교해 **변경 대상 외 그룹은 그대로인지** 검사한다.

catalog 변경은 상품별로 좁혀지지 않는다. 현재 설계대로 모든 catalog 참조 키가 새 버전을 사용한다. stock도 전체 재고 그룹이다. 기존 키를 즉시 물리 삭제하는 방식이 아니며 이전 키는 TTL까지 남을 수 있다.

좋아요 수·순위는 좋아요 쓰기 직후 기존 캐시를 유지하고, 만료 후 새 숫자·순서를 반환하는지 별도로 검사한다. 삭제 비노출·본인 확인은 이 지연 허용 대상이 아니다.

## 시나리오 재정리: 캐시 유효 범위 중심

기존 합쳐진 시나리오는 TTL·접근 제어·오류 처리와 쓰기 유효 범위를 분리했다. [CacheInvalidationScopeHttpTest](../../../../apps/commerce-api/src/test/java/com/loopers/config/cache/CacheInvalidationScopeHttpTest.java)는 **브랜드 2개·상품 3개·사용자 2명**으로 쓰기 하나당 변경 대상과 유지 대상을 함께 확인한다.

| 쓰기/상황 | 반드시 갱신 | 반드시 유지 |
| --- | --- | --- |
| 상품 수정 | 이름·가격, 가격순과 페이지 경계, 관련 목록·상세 | 다른 브랜드 상품의 실제 값 |
| 상품 생성 | 전체·해당 브랜드 목록, catalog·stock revision | 다른 브랜드 목록 내용, 기존 상품 숫자·재고 값 |
| 상품 삭제 | 해당 상품만 목록·상세·내 좋아요·일괄 응답에서 제외 | 같은 브랜드의 다른 상품·다른 브랜드 상품 |
| 브랜드 생성·수정·삭제 | 고객·관리자 목록, 소속 상품 정보/비노출 | 다른 브랜드 상품과 사용자 응답 내용 |
| 재고 변경·주문 확정 | stock 키와 해당 상품 품절 상태 | catalog·사용자별 좋아요 키·응답·남은 TTL |
| 좋아요 등록·취소 | 본인 목록 키·응답 | 다른 사용자 목록, 숫자·순위 캐시. 숫자·순위는 만료 후 갱신 |
| 중복 등록·없는 좋아요 취소 | 없음 | 모든 그룹 버전·응답·남은 TTL |
| 상품 수정 롤백 | 없음 | DB 이름·가격, 모든 그룹 버전·응답·남은 TTL |
| 변경 전 시작한 조회의 늦은 완료 | 커밋 이후 새 요청은 새 버전 사용 | 옛 요청은 옛 키에만 저장. 이후 요청에 옛 내용 비노출 |

각 쓰기 전에 정렬 3종 × 브랜드 없음/A/B, 가격순 페이지 0/1, 상품 상세 3개, 사용자별 내 좋아요 2개, 고객/관리자 브랜드 목록, 숫자/재고 일괄 조회의 **20개 요청 조건**을 캐시한다. 각 그룹 revision을 개별 비교하고, 영향받지 않은 캐시는 같은 키·응답과 남은 TTL을 유지하는지 검사한다. catalog 변경 때 다른 브랜드 캐시도 새 키가 되는 것은 현재 그룹 설계이며, 그 브랜드의 실제 데이터 값은 유지되어야 한다.

기존 문자열 포함 검사는 상품 ID·이름·가격·순서의 정확한 값 비교로 보강했다. 늦은 재삽입 검사는 옛 키를 수동으로 쓰는 대신 실제 HTTP 조회를 DB 읽기 직후 latch로 멈추고, 수정/삭제 커밋 후 재개한다. 롤백은 캐시 응답 외에 DB 값과 각 그룹 버전도 직접 확인한다.

기존 TTL·0개 좋아요·접근 제어·깨진 JSON·Redis 오류 fallback 검증은 [ReadCacheHttpTest](../../../../apps/commerce-api/src/test/java/com/loopers/config/cache/ReadCacheHttpTest.java)에 유지했다. 제목·주석만 나눈 것이 아니라 섞여 있던 쓰기 시나리오의 기대값을 위 테스트로 옮겨 강화했다. 실제 Redis 장애·복구, 다중 서버 부하 검증은 여전히 별도다.

재정리 후 전체 테스트 **443개 통과**(일반 439개 + 별도 JVM 비동기 로그 4개, 실패·오류·건너뜀 0개). 유효 범위 시나리오 15개, TTL·접근·오류 HTTP 테스트 10개, TTL 단위 테스트 2개 포함. ArchUnit·도메인 문서 검사·Checkstyle 통과. 실행 시간 2분 20초. 운영 코드는 이번 재정리에서 변경하지 않았다.

좋아요 숫자/순위 키의 잔여 TTL은 **299/321초 → 재조회 후 298/320초**로 연장되지 않았다. 자연 만료 후 재적재 TTL은 **329/314초**였다. 별도 [TTL 스냅샷](ec2-ttl-snapshot.json)에서 캐시 6종의 현재 catalog revision 키 9개 모두 양수 TTL을 확인했다. 이는 생성 시점 jitter 분포 전체를 검증한 수치는 아니다.

테스트 데이터는 soft delete로 정리했고 기존 seed는 수정하지 않았다. catalog revision 변경으로 기존 목록 캐시도 논리적으로 무효화되었다. 사용자 fixture는 생성 API가 없어 SQL로 생성·정리했다. 부하·SLO 측정은 하지 않았다.

로컬 회귀 **28개 통과**(쓰기 유효 범위 15 + TTL·인증·오류 HTTP 10 + TTL 단위 2 + ArchUnit 1), 실패·오류·건너뜀 0. Checkstyle 통과, 45초. 별도 비동기 로그 테스트 4개는 기존 성공 결과를 재사용(`UP-TO-DATE`)했다. 롤백·늦은 재삽입·주문 확정은 로컬 통합 테스트 결과이며 이번 EC2에서 재현한 것으로 세지 않는다.
