# 구매 부하만 올려 읽기·구매 SLO 경계 관찰

읽기 p99 ≤100ms, 구매 전체(주문 생성→확정) p99 ≤300ms가 목표다. 성공률 100%, 미시작 0을 함께 확인한다. 좋아요는 지연을 기록하되 별도 지연 목표를 새로 정하지 않는다.

- 고정: 최신순 첫 페이지 20개 읽기 1,700 RPS/VU 3,000, 좋아요 등록 5+취소 5 RPS/VU 100, TTL 5초, 같은 Write Invalidate + 로컬 Single Flight 빌드.
- 변화: 구매 20건/초부터 10건/초씩 증가. 구매 VU 100은 유지한다. 60초씩 측정한다. 구매 20건/초는 주문 생성·확정 API 약 40 RPS다.
- 각 단계 통과 시 다음 단계로 진행한다. 읽기 또는 구매 지연·성공률·미시작 목표를 넘으면 같은 단계에서 1회 더 확인한 후 증량을 멈춘다. 확인 회차가 통과해도 혼합 판정이며 안정 처리 한계로 확정하지 않는다. 실행 상한은 구매 100건/초이며 모두 통과하면 그 이상은 미측정으로 남긴다.
- 37번 혼합 부하를 마친 같은 JVM의 예열 상태를 이어받는다. 단계마다 추가 예열 없이 preflight·회복을 확인한다. 컨테이너가 바뀌면 중단한다.
- 신규 구매 사용자 수는 요청률×60초+여유로 준비한다. 포인트와 재고는 격리 실습 DB를 사용한다. 단계별 주문·재고·포인트, 좋아요 등록·취소 후 DB 잔존 관계를 대조한다. seed 전체 응답 일치 검사는 생략한다.
- 읽기·구매·좋아요 각각 지연, 시작·완료·성공률, 전체 미시작, 원본 조회·캐시 무효화·Redis hit/miss·앱/DB CPU·Hikari·Tomcat을 보존한다.

현재 구매 10건/초에서도 회차 편차가 있어 이번 결과는 관찰된 목표 위반 단계다. 확정된 최대 처리량이나 장애 없는 운영 용량이라고 주장하지 않는다. 구매 VU 100이 부족해 미시작되면 앱 한계와 구분한다. 앱·API·도메인 계약은 변경하지 않고 기존 공통 부하 도구를 재사용한다.
