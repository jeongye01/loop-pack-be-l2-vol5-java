# 구매 RPS 증량 결과

**읽기 1,700 RPS·좋아요 합계 10 RPS를 고정하고 구매만 10→20건/초로 올렸다.** 목표는 읽기 p99 ≤100ms, 구매 전체 p99 ≤300ms다. 미시작 0과 시작된 요청 성공률 100%도 함께 판정했다. 최신순 TTL 5초, 같은 JVM·Write Invalidate·로컬 Single Flight를 유지했다.

| 구매 부하 | 회차 | 읽기 p99 | 구매 p99 | 미시작 | 목표 |
| --- | --- | ---: | ---: | ---: | --- |
| 10건/초 | 직전 37번 1회 | 214ms | 338ms | 0 | 미달 |
| 10건/초 | 직전 37번 2회 | 197ms | 316.13ms | 0 | 미달 |

계획대로 목표를 넘은 단계는 같은 부하로 한 번 더 확인하고 추가 증량을 중단했다. **구매 10건/초에서도 읽기 목표를 안정적으로 만족한 기준점이 없으므로, 최대 용량을 10~20건/초라고 확정할 수 없다.** 이번 결과는 현재 고정 읽기·좋아요 부하 아래에서 20건/초의 관측값이다. 30건/초 이상은 실행하지 않았다.

## 실행 수·좋아요·구매 대조

| 회차 | 읽기 완료 / 성공률 | 구매 완료 / 성공률 | 좋아요 등록 / 취소 완료 | 등록 / 취소 p99 | 주문·재고·포인트 / 좋아요 대조 |
| --- | --- | --- | --- | --- | --- |
| run-020-1 | 102,000 / 100% | 1201 / 100% | 300 / 300 | 188.16 / 175.04ms | True / True |
| run-020-2 | 102,000 / 100% | 1201 / 100% | 301 / 301 | 115.00 / 110.00ms | True / True |

좋아요 성공률과 실제 등록·취소 DB 대조는 각 run의 like-audit.json에 보존했다. 구매 20건/초는 주문 생성·확정 합계 약 40 API RPS다. 실제 건수는 실행 경계의 초과 시작을 포함한다. 신규 사용자 1,250명 중 예약분을 제외한 1,240명을 준비해 사용자 부족으로 부하가 중단되지 않게 했다. 좋아요는 별도 지연 목표 없이 관찰했다.

## 병목 후보 지표

| 회차 | 재고 원본 횟수 / 최대 동시 | Hikari pending 최대 | Tomcat busy 최대 | 앱 CPU 평균 / 최대 | 삭제 실패 | Redis GET 오류 |
| --- | --- | ---: | ---: | --- | ---: | ---: |
| run-020-1 | 1089 / 2 | 0 | 193 | 162.00% / 197.88% | 1 | 28 |
| run-020-2 | 1109 / 2 | 0 | 97 | 159.77% / 193.48% | 0 | 0 |

구매마다 재고 캐시를 지워 재고 원본 재조회가 늘어나는 구조는 유지했다. CPU·Tomcat 점유와 캐시 오류는 병목 후보 신호이며 단일 원인을 확정하지 않는다. Hikari pending 표본이 0이라고 모든 순간 대기가 없었다는 뜻은 아니다. 원본 동시는 DB 풀 대기를 포함하고 자원은 5초 표본이다. 삭제 실패는 DB 커밋 이후 지표에 기록되므로 API 성공률 100%와 동시에 존재할 수 있다. 표시 정합성이 모두 보장된다는 뜻이 아니다.

## 조건·한계

37번을 마친 같은 서버에서 추가 예열 없이 preflight·회복만 확인했다. 서버 변경 시 중단하도록 했다. 읽기 VU 3,000, 구매 VU 100, 좋아요 VU 100을 유지했다. 기존 10건/초 측정과 JVM 실행 상태·시간대가 완전히 같은 대조군은 아니므로 증량만의 인과 효과를 확정하지 않는다.

공통 부하 도구를 재사용했고 구매 도구가 RPS를 10으로 덮어쓰지 않도록 수정했다. 구매율에 맞게 사용자 수가 늘어나는 테스트 1개, 기존 프로세스 테스트 4개가 통과했다. 앱 코드는 변경하지 않았다. SLO를 읽기·구매로 분리하고 좋아요 지연은 관찰값으로 남겼다.
