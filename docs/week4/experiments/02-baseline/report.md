# 두 번째 Baseline 결과: 상품 100만 개

**5초 타임아웃·본 측정 60초 기준, 0.75 RPS는 3회 모두 성공했고 1 RPS는 3회 모두 타임아웃이 발생했다.** 탐색 간격은 0.25 RPS이며 정확한 최대 처리량이나 장시간 지속 가능한 처리량으로 단정하지 않는다.

첫 실험과 같은 앱 이미지·스키마·인덱스·요청·실행기를 사용했다. 데이터만 `skewed-1m-v1`으로 교체했고 기존 결과는 [첫 baseline](../01-baseline/report.md)에 보존했다. 데이터 건수와 편중이 함께 바뀌었으므로 차이를 상품 수 하나의 영향으로 해석하지 않는다.

## 자원과 SQL 관찰

- 요청마다 SQL 44개가 실행됐다. 상품별 좋아요 수를 세는 SQL 20개가 전체 JDBC 실행 시간의 약 97~98%를 차지했다. 실행 계획은 이번 측정에서 수집하지 않았다.
- 1 RPS에서 DB 컨테이너 CPU가 두 코어 용량에 근접했다. 아래 JSON에 모든 코어 사용량 합산(2 vCPU 상한 약 200%)과 서버 전체 용량 대비(상한 100%)를 구분해 기록했다. 이는 서버 전체 프로세스의 CPU 합계가 아니다.
- DB 서버의 사용 가능 메모리는 측정 중 약 6.3 GiB 이상이었다. 디스크 I/O 원본과 앱 자원·Hikari 상태는 각 Run의 `resources.json`에 보관했다.
- 측정된 CPU 포화와 좋아요 집계 SQL의 시간 비중을 보면 해당 쿼리가 주요 병목 후보다. 쿼리 개선 실험으로 인과를 확인해야 한다.

모든 Run에서 응답 불일치·미시작·미완료 요청은 0건이며 요청별 서버·SQL 기록 연결과 종료 후 회복을 확인했다. 실패는 타임아웃이었다. 집계 도구 단위 테스트 4개를 통과했다. [자원·SQL 집계](analysis.json) · [탐색 결과](discovery.json)
