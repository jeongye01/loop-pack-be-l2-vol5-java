# 캐시 hit 부하 — Tomcat 스레드 포화 확인

**Tomcat 워커 200개가 모두 사용 중인 상태를 확인했다.** 최초 busy=0 표본을 제외한 12개 표본에서 busy=200, current=200, max=200이었다. 이는 워커 포화 근거이며 큐 길이·대기 시간이나 스레드를 붙잡은 원인까지 직접 측정한 것은 아니다.

## 1회 측정 결과

캐시 이미지 `a6ba327`, MBean 지표만 활성화. 300→700 RPS 각 30초 예열 후 서울 EC2에서 1,700 RPS·VU 3,000·60초·timeout 5초 1회. 사용자 요청대로 엄격한 안정화 반복 없이 진행했다.

## 해석

앱 내부 처리와 DB 대기가 짧아도 Tomcat 워커가 전부 점유될 수 있음을 확인했다. Tomcat busy와 앱 내부 active는 측정 범위가 다르므로 차이만으로 작업 큐 길이를 계산할 수 없다. 두 지표의 채집 시점도 완전히 동일하지 않다.

다음 확인은 부하 중 **스레드 덤프**다. 워커가 로그 출력·락·소켓 응답 전송 등 어디에 머무는지 확인한다. 스레드 수 200 자체가 부족한지, 특정 작업이 워커를 오래 점유하는지는 아직 구분되지 않았다. 이번 단일 실행은 예열 조건도 이전 13번과 달라 p99 증가를 MBean 설정 탓으로 단정하지 않는다.

## 공통 수집 반영

- `docker/ec2/experiment-compose.yml`: Tomcat MBean 등록 활성화.
- 공통 Prometheus 수집·자원 집계: busy/current/max를 `name` connector별로 분리. 앱 8080과 관리 8081을 합산하지 않는다.
- `requireTomcatMetrics=true` 실행은 앱 8080의 세 지표가 모든 표본에 있어야 수집 검증 통과. 누락을 0으로 처리하지 않는다.
- 5초 표본이며 이번에는 큐 길이·스레드 덤프를 수집하지 않았다.
- 공통 수집·파싱 테스트 11개 통과. Java 코드 변경 없이 배포 설정만 변경했다.
