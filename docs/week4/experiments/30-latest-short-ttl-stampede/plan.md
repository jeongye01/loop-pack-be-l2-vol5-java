# 최신순 첫 페이지 TTL 2초 — 스탬피드 관찰 3회

## 질문과 고정 조건

캐시 만료 시 같은 원본 목록 조회가 얼마나 겹치며, 1,700 RPS에서 p99 ≤ 200ms를 유지하는가? 스탬피드 발생 여부와 SLO 위반 여부를 따로 판정한다.

- 대상: 최신순·무브랜드·page=0·size=20 통합 상품 API. 같은 seed, 쓰기·지연 주입·Single Flight 없음.
- 실험 프로필에서 해당 목록 캐시 키만 TTL 2초·jitter 0. 가격순·좋아요순·상세·브랜드·다른 페이지·좋아요 수·재고는 기존 TTL 300±30초 유지.
- 캐시 ON·revision DB 확인 ON, hit/miss 트랜잭션 분리 유지. 별도 EC2 부하기, VU 3,000, timeout 5초.
- 300→700 RPS 각 30초 예열 → 회복 확인 → 1,700 RPS 60초. 이를 3회 실행. 2·3회는 앱 재시작 없이 진행.
- 목표: p99 ≤ 200ms·성공률 100%·미시작/미완료/불일치 0. 예열 실패도 별도 기록하며 수집·회복이 정상이면 기존 절차대로 진행한다.

## 측정

| 지표 | 방법·해석 |
| --- | --- |
| 원본 목록 진입 수 | experiment.origin.loads: findBasicPage 진입을 모든 부하 요청에서 집계. 인증·revision SQL을 포함한 전체 DB 쿼리 수와 구분 |
| 원본 조회 최대 동시 실행 수 | active를 진입/종료마다 갱신하고 maximum 보존. 풀 대기를 포함한 원본 호출 실행 구간이며 DB 엔진에서 동시에 실행한 SQL 수와 다름 |
| 중복 조회 | overlapping: 다른 동일 목록 원본 호출이 실행 중일 때 진입한 횟수. 상세 Trace 샘플링과 독립 |
| 실패 | 원본 호출 errors, HTTP 실패·timeout·응답 불일치 함께 기록 |
| 지연 | 전체 요청 p50/p95/p99 및 요청 시작 시각 기준 1초 구간별 p99·성공률. 전체 p99가 짧은 지연 급증을 가리지 않는지 확인 |
| Redis | 전후 키 TTL·hit/miss·만료·eviction·오류. Redis 전체 expired_keys에는 다른 키도 포함될 수 있어 목록의 정확한 만료 횟수라고 단정하지 않음 |
| 자원 | 기존 5초 수집 Hikari active/pending·Tomcat·DB/앱 CPU, 1% SQL Trace |

원본 지표는 유효한 X-Run-ID별로 분리해 사전 검증·회복 요청이 본 부하 카운터에 섞이지 않게 한다. Redis 카운터는 검증·회복을 포함하는 더 넓은 구간이다. 정확한 이벤트별 원본 호출 수는 이벤트 경계를 수집하지 않으므로 단정하지 않고, 원본 호출 총량·중첩·최대 동시 수로 먼저 재현을 판정한다.

## 절차와 비교 한계

배포 후 해당 목록 키의 TTL이 실제 2초 범위인지 확인한다. 이전에 남은 5분 캐시는 실험 대상 키만 만료시키며 전체 Redis를 비우지 않는다. 좋아요·재고 TTL이 길게 유지되는지도 확인한다. 이후 공통 run_combined_slo.py·RemoteRunner·products.js를 재사용해 3회 실행한다.

29번 정상 hit 결과 124/56/96ms와 비교한다. 이번에는 원본 전수 계측과 1초 구간 지연 측정이 추가되므로 정확한 성능 차이를 TTL 하나의 효과라고 단정하지 않는다. 짧은 TTL은 재현 시간을 단축한 실험 조건이며 운영 TTL 5분의 발생 빈도와 같지 않다. 이 설정을 실험 서버에만 유지하고 설정값 0으로 원복할 수 있게 한다.
