# 최신순 TTL 2초 스탬피드 관찰 — 3회 결과

## 변경된 SLO로 재판정 (2026-10-15)

**새 목표 p99 ≤ 100ms에서는 3회 모두 미달이다.** 스탬피드 재현에는 성공했지만 응답 시간 목표는 달성하지 못했다. 재실행 없이 기존 측정값으로 재판정했다.

| 회차 | 전체 p99 | 당시 목표 ≤ 200ms | 새 목표 ≤ 100ms |
| --- | ---: | --- | --- |
| 1 | 138ms | 통과 | 미달 |
| 2 | 112ms | 통과 | 미달 |
| 3 | 144ms | 통과 | 미달 |

아래 실행 당시 판정과 원본 JSON의 `sloPassed`는 200ms 기준 이력이다. 현재 목표 달성으로 해석하지 않는다. 이후 실험은 100ms를 적용한다.

## 실행 당시 결과 (200ms 기준)

**같은 원본 목록 조회가 최대 23~31개 겹치는 현상을 재현했다. 다만 60초 전체 p99는 138 / 112 / 144ms로 3회 모두 200ms SLO를 통과했다.** 1초 구간별 p99에는 200ms를 넘는 구간이 있었다. 원본 중복 조회 재현과 전체 SLO 위반은 다른 판정이다.

## 조건

최신순·무브랜드·page=0·size=20 통합 API, 1,700 RPS·60초·VU 3,000, 같은 seed·별도 EC2 부하기. 캐시 ON·revision DB 확인 ON·hit/miss 트랜잭션 분리. 쓰기·인위적 원본 지연·Single Flight 없음.

실험 프로필에서 **해당 목록 키만 TTL 2초·jitter 0**. 좋아요 수·재고 및 다른 조회는 TTL 300±30초를 유지했다. 배포 후 확인된 남은 TTL은 목록 1,493ms, 좋아요 319,465ms, 재고 306,384ms였다([실제 TTL 확인](ttl-validation.json)). 기존 목록 키만 만료시켰고 전체 Redis는 비우지 않았다.

매회 300→700 RPS 각 30초 예열·회복 확인 후 본 측정. 1회차는 배포 후 첫 실행, 2·3회차는 재시작 없이 실행했다. 각 회차 키 만료를 강제로 맞추지 않고 자연 만료를 관찰했다.

## 본 측정과 DB 원본 조회

| 회차 | 완료·성공 요청 | 평균 | 전체 p99 | 원본 목록 조회 | 최대 동시 원본 호출 | 다른 원본 호출과 겹친 진입 | 당시 SLO (200ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 102,001 | 17.76ms | **138ms** | 384 | 31 | 353 | 통과 |
| 2 | 102,000 | 12.53ms | **112ms** | 241 | 23 | 208 | 통과 |
| 3 | 102,001 | 16.89ms | **144ms** | 321 | 30 | 290 | 통과 |

세 회차 모두 성공률 100%, 미시작·timeout·HTTP 오류·응답 불일치·미완료 0건. 수집과 부하 종료 후 회복 확인도 모두 통과했다. 실행 경계에서 1건 차이 나는 실제 요청 수를 그대로 기록했다.

원본 목록 조회는 `ProductUseCase.findBasicPage` 호출을 **부하 요청 전체에서** 집계한 값이다. 인증·revision 조회를 포함한 전체 SQL 횟수와 구분한다. 최대 동시 수는 원본 호출 진입부터 반환까지(풀 대기·SQL·객체 변환 포함) 겹친 수이며, DB 엔진에서 동시에 실행 중인 SQL 수를 뜻하지 않는다. 다른 원본 호출이 활성 상태일 때 새로 진입한 요청을 overlapping으로 센다. 모든 회차 종료 active=0이고 원본 오류 카운터 발생도 없었다.

데이터 변경과 Redis 오류 증가 없이 TTL이 짧은 동일 목록에 반복 원본 조회와 동시 실행이 발생했다. 따라서 만료 재적재 중복을 관찰했다. 다만 정확한 만료 이벤트 경계를 수집하지 않았으므로 “만료 한 번당 정확히 몇 회”로 환산하지 않는다.

## 짧은 구간의 지연

| 회차 | 가장 느린 1초 구간 p99 | p99 > 200ms인 구간 수 |
| --- | ---: | ---: |
| 1 | 221.02ms | 1 / 60 |
| 2 | 215.02ms | 2 / 60 |
| 3 | 272.03ms | 1 / 60 |

요청 **시작 시각 기준** 1초 묶음이며 전체 요청을 집계했다. 기존 SLO 판정은 회차 전체 60초 p99 기준이므로 세 회차 통과다. 이 표는 짧은 지연 급증을 놓치지 않기 위한 별도 진단이며 SLO를 사후 변경한 것이 아니다. 해당 구간이 정확히 어떤 만료 순간과 일치하는지까지 확인하지 않았으므로, 모든 지연 급증을 만료 하나의 영향으로 단정하지 않는다.

CPU는 1코어=100%, 앱은 2코어다. 자원은 5초 간격 표본, 커넥션 시간은 요청 상세 Trace 1% 표본이다. 최대 동시 원본 호출 지표는 5초 표본과 달리 모든 진입에서 최대값을 보존하므로 짧게 몰린 원본 호출도 잡는다. pending 표본 0은 순간 대기가 전혀 없었다는 의미가 아니다.

본 측정 중 Redis get 오류 3,517→3,517, put 오류 158→158로 모두 증가 0. 누적값은 예열에서 발생했다. 전후 Redis expired_keys는 32 / 33 / 34 증가, keyspace_misses는 953 / 628 / 944 증가했다. Redis 지표는 검증·회복과 다른 키도 포함하므로 원본 목록 조회 횟수나 정확한 해당 목록 만료 횟수와 같지 않다. 애플리케이션도 miss 때 트랜잭션 안에서 캐시를 다시 확인하므로 Redis miss 1건 = DB 원본 조회 1건이 아니다.

1회차 첫 예열 timeout 1,955건은 숨기지 않고 별도 보존했다. 회복 후 다음 단계로 진행했으며 700 RPS와 나머지 예열은 정상이다. 최초 기동부터 SLO를 지켰다고 해석하지 않는다.

29번 정상 hit 기준선 p99는 124 / 56 / 96ms였다. 이번에는 짧은 TTL 외에도 원본 전수 카운터와 1초 지연 구간 수집이 추가됐고 JVM 상태·시간대도 달라, 차이를 TTL만의 정확한 비용으로 환산할 수 없다. 2초 TTL은 만료를 자주 관찰하기 위한 조건이며 운영 TTL 5분의 빈도와 같지 않다.

**다음 비교 후보:** 같은 TTL·부하·계측을 유지하고 Single Flight를 추가해 원본 조회 총량·최대 동시 수가 줄어드는지 비교한다. 락 획득 뒤 캐시를 다시 확인해야 불필요한 재조회가 남지 않는다. 이번 실험에는 해당 방어를 추가하지 않았다.
