## 실험 내용

**상품 목록 조회의 정상 처리 범위와 실패가 시작되는 RPS를 찾아, 이후 개선 실험의 부하 레벨을 정한다.** 처리량·클라이언트/서버 시간·요청별 SQL과 각 실행 시간·자원 사용을 비교한다.

```http
GET /api/v1/products?brandId=7&sort=price_asc&page=0&size=20
X-USER-ID: 1
```

브랜드 7의 가격순 첫 20개를 조회한다. 전체 상품 수는 100개다.

## 변경 사항

쿼리·인덱스·캐시 최적화 없이 현재 구현을 측정한다. 로컬 k6에서 서울 앱 서버로 요청한다.

- 데이터: `uniform-10k-v1`. 브랜드 100·상품/재고/사용자 각 10,000·좋아요 999,493개.
- 분포: 브랜드당 상품 100개. 가격·재고·상품별 좋아요 수는 균등 난수이며 좋아요는 상품당 0~200개, 사용자당 실제 66~145개다. [상세 분포](../dataset-profile.json)

| 부하 설정 | 값 |
| --- | --- |
| 정상 기준 | 요청당 5초 안에 올바른 정상 응답 반환. timeout·HTTP/전송 오류·응답 불일치는 실패 |
| 시작 | 1 → 2 → 3 RPS |
| 확장 | 3까지 정상이면 4 → 6 → 8 → 12 RPS. 12에서도 정상이면 다음 범위 결정 |
| 하향 | 1부터 실패하면 0.5 RPS |
| 경계 확인 | 마지막 정상·최초 실패 사이를 0.25 RPS 단위까지 좁히고 양쪽을 각각 총 3회 측정 |
| 단계별 시간 | 준비 30초 + 본 측정 60초 |
| 실행기 | k6 constant-arrival-rate, 100 VU, timeout 5초, 종료 유예 10초 |

타임아웃은 5초로 확정한다. `config-timeout10.json`으로 실행한 2 RPS·60초 측정은 참고 결과로만 보존한다.

## 적용 전 기록

- 서울 배포·적재 후 CSV와 DB 건수·체크섬, 기준 응답, Trace 수집을 확인한다.
- [시드니 예비 측정](../preliminary/ec2-report.md): 1·2 RPS 정상, 3 RPS에서 실패 발생. 탐색 시작 구간의 참고로만 사용하고 서울에서 다시 측정한다.
