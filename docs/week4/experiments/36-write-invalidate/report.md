# TTL + Write Invalidate — 혼합 부하와 정합성 결과

**DB revision을 읽지 않는 커밋 후 삭제 방식으로 3회를 측정했다. 읽기와 구매가 동시에 p99 ≤100ms를 만족한 회차는 없었다. 정상 수정·삭제·rollback은 확인했지만, 무효화 실패·늦은 채움에서는 삭제 상품이 다시 노출됐다.**

최신순 첫 페이지 20개 1,700 RPS + 구매(주문 생성→확정) 10건/초, 각 60초. VU 3,000/100, 로컬 Single Flight 유지. 최신순 TTL 5초, 나머지 300±30초. 최초 300/700 RPS 각 30초 예열 후 같은 서버에서 추가 예열 없이 반복했다.

| run-1 | 92,783 | 600 | 1622.82 / 2623.00 | 2741.12 / 4889.16 | 9,218 |

## 원본 조회·캐시 삭제

| 회차 | 목록 원본 횟수 / 최대 동시 | 재고 원본 횟수 / 최대 동시 | 삭제 성공 / 실패 | 삭제 키 수 | Redis GET 오류 |
| --- | --- | --- | --- | ---: | ---: |
| run-1 | 19 / 3 | 290 / 3 | 594 / 6 | 266 | 629 |
| run-2 | 13 / 2 | 582 / 2 | 601 / 0 | 581 | 0 |
| run-3 | 12 / 1 | 594 / 2 | 600 / 0 | 593 | 0 |

원본 횟수는 본 측정 X-Run-ID 기준이다. 최대 동시는 원본 진입의 겹침으로, DB 풀 대기를 포함하며 동시에 실행 중인 SQL 수가 아니다. 삭제·오류·Redis hit/miss 증분은 preflight/recovery와 다른 트래픽이 포함될 수 있다. 1회차 삭제 실패 6회는 부하 중 지표에서 실제 관측됐지만, 그 요청의 표시 데이터가 틀렸는지는 부하 응답 전체 대조로 검증하지 않았다. 별도 정합성 재현에서는 옛 값 노출을 확인했다.

| 회차 | Redis key hit / miss | 1초 구간 p99>100ms | 가장 느린 구간 p99 |
| --- | --- | ---: | ---: |
| run-1 | 374,924 / 49,969 | 60 / 60 | 2795.00ms |
| run-2 | 333,032 / 14,612 | 12 / 60 | 388.02ms |
| run-3 | 322,107 / 9,099 | 6 / 60 | 187.00ms |

Redis 수치는 키 조회 단위이며 API 요청 hit율이 아니다. MGET·재확인·수집 요청 등이 섞인다. 1초 구간은 요청 시작 시각 기준으로 묶었고 정확한 TTL 만료 이벤트에 정렬한 결과는 아니다.

## 자원·해석

| 회차 | Hikari pending 최대 | Tomcat busy 최대 | 앱 CPU 평균 / 최대 |
| --- | ---: | ---: | --- |
| run-1 | 60 | 200 | 181.79% / 198.88% |
| run-2 | 0 | 183 | 161.86% / 196.44% |
| run-3 | 0 | 75 | 149.87% / 184.45% |

자원은 5초 간격 표본, 앱은 2코어다. 1회차는 Tomcat 200개와 커넥션 대기, 미시작이 함께 나타났다. 최초 읽기 전용 예열에서 300 RPS는 timeout 4건·p99 2,993ms였고, 회복 뒤 700 RPS는 성공률 100%·p99 30ms였다. 구매 경로까지 충분히 예열됐다는 뜻은 아니다.

35번(동일 TTL, revision OFF·무효화 없음)의 읽기 p99는 2,470/80/48ms, 구매는 4,846.40/232.06/174ms였다. 그때 재고 원본은 본 측정에서 0회였지만 이번에는 구매마다 stock 캐시를 삭제해 재조회가 생긴다. 캐시 값이 soldOut인데 수량 변경마다 전체 stock 캐시를 지우는 기존 범위를 유지한 결과다. 앱 재시작/JVM 상태·시점 차이가 있어 차이 전부를 무효화 비용으로 확정하지 않는다.

현재 삭제는 afterCommit에서 동기 SCAN+UNLINK로 실행되어 구매 응답에 포함된다. Spring 트랜잭션 리소스 정리 전 callback이므로 Redis 삭제 동안 커넥션 반환이 지연될 가능성도 있다. 이를 독립 측정하지 않았으므로 병목의 확정 원인으로 쓰지 않는다. 수집된 trace에서 revision SELECT/쓰기 SQL은 세 회차 모두 0건이었다([확인 결과](revision-sql-check.json)). 인증에 필요한 DB 조회는 유지된다.

## 정합성·검사 범위

[정합성 결과](consistency-report.md): 정상 순차 수정·삭제·rollback·TTL은 확인. 삭제 실패/늦은 채움의 수정·삭제 4개 장면은 정합성 실패. 남은 TTL을 100ms로 줄인 뒤 회복은 확인했다. 운영 TTL을 기다린 검증이나 변경 시점 기준 전역 최신성 보장은 아니다.

재현 테스트 8개, TTL 단위 테스트 5개, ArchUnit 1개, Checkstyle·빌드 통과. 기존 계약 테스트는 삭제·완화하지 않았다. 전체 회귀는 실행하지 않았으며, 새 재현 테스트의 성공을 삭제 비노출 계약 통과로 해석하지 않는다. API·도메인 계약은 변경하지 않았다.
