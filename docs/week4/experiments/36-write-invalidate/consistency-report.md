# TTL + Write Invalidate 정합성 재현 결과

정상 순차 수정·삭제와 rollback은 확인했다. **무효화 실패와 늦은 채움에서는 옛 값이 노출됐고, 삭제 상품도 HTTP 200으로 다시 노출됐다.** 현재 기본 구현은 이 장애·경쟁 상황의 필수 삭제 비노출 계약을 만족하지 못한다.

| 시나리오 | 관찰 | 정합성 판정 |
| --- | --- | --- |
| 정상 수정 후 조회 | 새 값 반환, facade hit의 revision SQL 없음, 비인증 요청 401 | 통과 |
| 정상 삭제 후 상세 조회 | 404 | 통과 |
| rollback | DB·캐시 기존 값 유지, 삭제 호출 없음 | 통과 |
| TTL | 기본 TTL 270~330초, hit 시 비연장, 만료 후 원본 재조회 | 통과 |
| 수정 후 무효화 실패 | DB 변경 커밋, 오류 지표 증가, 새 요청에 옛 값 200 | 실패 |
| 삭제 후 무효화 실패 | DB 삭제 커밋, 새 요청에 삭제 상품 200 | 실패 |
| 수정 후 늦은 채움 | 삭제 완료 뒤 이전 DB 스냅샷 재저장, 새 요청에 옛 값 | 실패 |
| 삭제 후 늦은 채움 | 삭제 완료 뒤 이전 DB 스냅샷 재저장, 새 요청에 삭제 상품 | 실패 |
| 위 4개 실패 이후 TTL 만료 | 변경 값 또는 404로 회복 | 제한된 회복 확인 |

재현은 실제 MySQL·Redis Testcontainers와 MockMvc HTTP를 사용했다. 무효화 실패는 Redis 삭제 메서드에 예외를 주입했다. 늦은 채움은 원본 읽기 직후 latch로 멈추고 관리자 변경·삭제 완료 후 재개했다. 이는 무작위 타이밍에 의존하지 않는 재현이다.

회복 확인은 남은 TTL을 100ms로 단축했다. 기본 5분을 실제로 기다린 결과가 아니며, 늦은 재저장의 TTL은 그 저장 시점부터 시작한다. 따라서 변경 시점부터 5분 내 모든 요청이 최신이라는 전역 상한을 주장하지 않는다.

새 재현 테스트 8개가 모두 통과했다는 것은 위 관찰을 재현했다는 뜻이다. **정합성 기준이 모두 통과했다는 뜻은 아니다.** 기존 보호 계약의 테스트·기대값은 수정하지 않았다. 이 실험에서 정상 삭제는 상세 경로를 검사했으며 모든 조회 경로·장애 조합을 검증한 것은 아니다.
