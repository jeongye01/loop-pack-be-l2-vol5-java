# TTL + Write Invalidate: 혼합 부하와 정합성 한계

## 변경과 범위

실제 catalog-cache 경로를 DB revision 방식에서 커밋 후 Redis 삭제 방식으로 전환한다. 이전 방식은 과거 실험·회귀 비교용 코드로 남기지만 이 배포의 hit/miss/write는 revision SQL을 실행하지 않는다. 새 캐시 키는 v4이며 revision 접미사가 없다.

- 읽기: Cache Aside + 로컬 Single Flight. hit은 원본·revision 조회를 생략하며 인증은 유지한다.
- 쓰기: 같은 트랜잭션의 변경 그룹을 모아 커밋 성공 뒤 SCAN+UNLINK로 관련 캐시를 삭제한다. 롤백에는 삭제하지 않는다.
- catalog 변경은 6개 캐시 버킷의 v4 키 전체, stock 변경은 stocks v4 전체, 내 좋아요 변경은 해당 사용자 목록의 모든 페이지를 삭제한다.
- 기존 revision의 무효화 범위를 유지한다. 이번에는 품절 경계에만 무효화하는 최적화를 함께 넣지 않는다. 수량 감소마다 stock 삭제가 발생한다.
- 좋아요 표시 수·순위는 기존처럼 TTL 갱신이다. 상품·브랜드 CUD로 인한 삭제 범위에는 포함한다.
- 삭제 오류는 지표로 남기고 이미 커밋한 DB 변경을 성공으로 반환한다. 재시도/outbox·지연 삭제·늦은 재채움 차단은 이번 기본 구현에 넣지 않는다.

## 1. 기본 혼합 부하

| 항목 | 설정 |
| --- | --- |
| 읽기 | 최신순 첫 페이지 20개, 1,700 RPS, VU 3,000 |
| 구매 | 주문 생성→확정 10건/초, VU 100 |
| 시간 | 본 측정 60초 × 3회 |
| 예열 | 최초 300/700 RPS 각 30초, 이후 동일 서버에서는 회복 확인만 |
| TTL | 최신순 첫 페이지 5초, 나머지 300±30초 |
| SLO | 읽기·구매 각각 p99 ≤100ms, 성공률 100%, 미시작 0 |
| 비교 | 35번 revision OFF/무효화 없음, 32번 revision ON |

읽기·구매 지연 분포, 원본 목록/재고 호출, 삭제 성공/실패/키 수, Redis hit/miss/error, CPU·Hikari·Tomcat, 주문·재고·포인트 대조를 기록한다. 삭제는 커밋 후 동기 실행하므로 쓰기 응답 시간에 포함한다. seed 응답 일치 검사는 생략한다.

## 2. 정합성 시나리오

| 장면 | 재현 순서 | 판정 기준 |
| --- | --- | --- |
| 정상 변경 | 캐시 채움 → 관리자 수정 완료 → 새 조회 | 변경 값, hit의 revision SQL 0 |
| 정상 삭제 | 캐시 채움 → 관리자 삭제 완료 → 새 조회 | 고객 404/목록 제외 |
| rollback | 캐시 채움 → 수정 후 rollback → 조회 | 기존 DB·캐시 유지, 삭제 호출 없음 |
| TTL | 저장 → hit 반복 → 만료 → 조회 | TTL 비연장, 만료 후 원본 재조회 |
| 무효화 실패 | 캐시 채움 → 삭제 경로 오류 주입 → DB 변경 커밋 → 새 조회 | 옛 값 노출 여부·오류 지표·만료 후 회복 기록 |
| 늦은 재채움 | 원본 읽은 요청 정지 → 변경 커밋·캐시 삭제 → 옛 읽기 재개 → 새 조회 | 오래된 값 재노출 여부 기록 |
| 삭제의 늦은 재채움 | 위 순서에서 변경 대신 삭제 | 삭제 상품 노출/오류가 있으면 필수 보호 실패로 판정 |

정합성 재현은 별도 로컬 MySQL·Redis Testcontainers에서 실행한다. 실제 HTTP·실제 Redis를 사용하며 실패 주입은 삭제 호출만 한정한다. TTL 회복을 빠르게 확인하는 테스트에서는 해당 키의 남은 TTL만 짧게 조정하고 이를 결과에 표시한다. 운영 TTL 시간 전체를 기다린 실험으로 주장하지 않는다.

실패를 재현했다는 테스트 성공과 정합성 기준 통과를 구분한다. 기존 보호 계약 테스트의 기대값은 완화하지 않는다. TTL을 변경 시점 기준 전역 최신성 상한이라고 주장하지 않는다. 늦게 저장되면 그 저장 시점부터 새 TTL이 시작된다.

## 작업 파일

WriteInvalidation, CacheVersions의 전략 분기, application-catalog-cache.yml, 새 정합성 재현 HTTP 테스트, 공통 부하 스크립트의 기존 지표 수집, 이 계획서·결과·ADR만 변경한다. API·domain-rules·requirements는 변경하지 않는다.
