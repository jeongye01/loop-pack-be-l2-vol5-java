## 실험 내용

메인 화면이 최신순·무브랜드·첫 페이지 상품 20개를 보여주고 여기에 요청이 집중된다고 가정한다. 실제 트래픽 분포를 측정한 결과는 아니다. 현재 구현에서 정상 상태 SLO부터 확인하고, 캐시 만료 구간과 비교한다.

대상은 `GET /api/v1/products?sort=latest&page=0&size=20` 한 번이다. 상품 정보·좋아요 수·품절을 서버에서 합치며 내부 캐시는 분리한다. 세 API 조합 계획은 폐기했고, 정상 상태 기준선은 [24번 실험](../24-combined-product-slo/plan.md)에서 먼저 측정한다. 프론트 렌더링은 제외한다.

### 1단계: 정상 hit → 만료 구간

동일 목록 요청을 **1,700 RPS**로 보낸다. 정상 hit 기준선은 p99 ≤ 200ms·성공률 100%·미시작 0을 확인한다. 같은 부하가 흐르는 중 짧은 TTL로 인기 키가 만료되게 하여 만료 전·직후·재채움 후를 비교한다. 각 조건 3회, 예열·캐시 채움·회복을 확인한다. 짧은 TTL에서는 정상 hit 측정 구간에 만료가 섞이지 않았는지 확인하고, 만료 구간은 별도로 집계한다.

전체 실행 p99와 함께 만료 주변의 짧은 시간 구간별 지연·miss·원본 조회 횟수를 기록한다. 전체 통계에 짧은 지연 급증이 묻히지 않게 한다. 만료 시각부터 재채움 완료까지 원본 조회가 실제 겹쳤는지 확인하며, 모든 요청이 miss이거나 SLO가 깨질 것이라고 가정하지 않는다.

### 통합 API의 SLO

초당 1,700 요청에서 전체 p99 ≤ 200ms·성공률 100%·미시작/미완료 0을 확인한다. 내부 세 캐시의 만료 시각은 각각 기록한다. 동시에 만료된다고 가정하지 않는다.

| 관측 대상 | 남길 값 |
| --- | --- |
| 클라이언트 | 실제 시작·완료·성공·거절·timeout·미시작 수, p50/p95/p99 |
| Redis | hit/miss, 만료·재적재 시각, 재적재 횟수, 명령 지연·CPU |
| DB | 해당 키의 원본 조회 실행 횟수·최대 동시 실행 수, SQL 지연·CPU·I/O |
| 앱 | Hikari active/pending·획득 대기, Tomcat busy |
| 보호 장치 적용 시 | Bulkhead 허용·거절·대기, Single Flight 대표 조회·합류 요청 수 |

인증·revision 조회와 캐시 원본 조회를 구분한다. 중복 조회 횟수는 전수 카운터로 확인하고 1% 상세 Trace로 추정하지 않는다. 성공 응답의 내용 일치도 검증한다.

## 변경 사항

전체 캐시를 비우지 않고 **대상 키만 테스트용 짧은 TTL로 만료**시킨다. 만료 시점을 제어하기 위한 실험 설정이며, 설계의 기본 TTL 5분·Jitter ±30초를 바꾸는 결정은 아니다. 실험용 TTL·Jitter 수치는 아직 미정이다. 확정한 설정과 실제 Redis 키는 실행 기록에 남긴다. 재채움 후에도 반복해서 짧은 TTL이 적용되는지 확인한다.

먼저 현재 구현의 중복 조회를 측정한다. Bulkhead·Single Flight 적용 후 비교는 해당 정책·구현이 정해지면 진행한다. Jitter는 여러 키의 동시 만료를 분산하지만 인기 키 하나의 동시 miss를 막지는 않는다.

공통 부하기·수집기를 재사용한다. 1,700 RPS 지속 부하·통합 API·만료 구간 계측 지원 여부는 실행 전에 확인한다. 이번 문서는 계획만 작성하며 배포·키 만료·부하 실행은 하지 않는다.

### 해결책 후보

| 방법 | 효과·범위 |
| --- | --- |
| Single Flight | 같은 키의 동시 miss를 하나의 원본 조회로 합치고 결과를 공유. 앱 내부 구현이면 인스턴스별로 동작 |
| 분산 락 | 여러 인스턴스의 같은 키 재적재를 조율. 락 만료·획득 실패·대기 시간·소유권 처리가 필요 |
| TTL Jitter | 서로 다른 키의 만료 시점을 분산. 인기 키 하나의 동시 miss는 해결하지 못함 |
| Bulkhead | DB로 넘어가는 동시 요청 수를 제한. 초과 요청의 대기·거절 정책 필요 |

적용 확정이 아닌 비교 후보다. 중복 조회를 줄이는 방법과 DB 전체 동시성을 제한하는 방법은 함께 사용할 수 있다. Redis 장애 중에는 Redis 기반 분산 락에도 의존할 수 없으므로 DB 보호를 별도로 검증한다.

## 적용 전 기록

[19번 캐시 hit 실험](../19-cache-sampled-log/report.md)은 1,700 RPS·60초·3회에서 p99 51 / 73 / 30ms, 성공률 100%였다. 고정 데이터의 hit 중심 결과이므로 현재 구현의 정상 상태 기준선으로 그대로 대체하지 않는다.

정상 상태 목표 p99 ≤ 200ms·성공률 100%와 비교하되, 거절로 지연만 낮아진 결과는 목표 달성으로 판단하지 않는다. 실험 결과에서 DB 유입량과 대기를 확인한 뒤 보호 한도를 정한다.

3개 API 계획은 폐기했다. 통합 API 정상 상태 기준선은 [24번 실험](../24-combined-product-slo/plan.md)에서 측정한다.
