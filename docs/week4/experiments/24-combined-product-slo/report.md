# 통합 상품 API SLO 측정·원인 분석

**1,700 RPS 목표·60초 실행에서 p99 5,001ms로 SLO 200ms를 충족하지 못했다.** 실제 시작은 43,965건이며 목표 1,700 RPS를 지속 전달하지 못했다. 부하 종료 후 앱·DB 회복과 기준 응답 일치를 확인했다.

통합 이미지 `commerce-api:catalog-8732303`, 캐시 ON, 기존 고정 데이터 캐시 OFF. 별도 8 vCPU 부하 EC2에서 앱 사설 IP로 최신순 첫 20개를 요청했다. 프론트 제외, VU 3,000, timeout 5초, TTL 5분 ±30초 유지. [계획](plan.md) · [배포](deployment.json).

| 항목 | 300 RPS 예열 20초 | 1,700 RPS 본 측정 60초 |
| --- | ---: | ---: |
| 계획 요청 | 6,000 | 102,000 |
| 실제 시작·완료 | 6,001 | 43,965 |
| 성공 / 실패 | 5,915 / 86 | 40,303 / 3,662 |
| 성공률 — 시작 요청 기준 | 98.57% | 91.67% |
| 미시작 | 0 | 58,036 |
| 시작했으나 미완료 | 0 | 0 |
| p50 / p95 / p99 | 3,281 / 4,510 / 5,000ms | 4,325 / 5,000 / 5,001ms |
| 성공 응답만의 p99 | 4,826ms | 4,977ms |
| 응답 불일치 | 0 | 0 |

k6 스케줄 경계로 시작+미시작은 계획보다 1건 많다. 본 측정의 시작량/설정 60초는 약 733건/초이며 k6 `http_reqs.rate` 693건/초는 종료 대기를 포함한다. 이를 달성한 1,700 RPS라고 표현하지 않는다. 미시작 요청에는 지연 표본이 없으므로 p99에 포함되지 않는다. 실패 상세 분류는 이번 요약 지표에 남지 않아 3,662건 모두를 timeout이라고 단정하지 않는다(5초 제한 근처 지연·동일 수의 Request Failed 로그 관측).

300 RPS 예열 실패 후 자동 증량을 멈췄지만, 사용자의 즉시 본 실험 지시에 따라 회복 확인 후 1,700 RPS를 별도 실행했다. 예열 안정화를 확인한 실험이 아니며 1회 결과로 지속 처리 한계를 확정하지 않는다.

## 원인: 캐시 hit에도 남는 DB 비용과 대기

샘플 Trace **439건 전부 SQL 5회**였다. 상품·좋아요·재고 원본 조회는 표본에 없고, **사용자 확인 1회 + revision 조회 4회**였다.

```text
사용자 확인 SELECT 1회
→ 읽기 트랜잭션 시작
  → catalog revision SELECT → 상품 Redis GET
  → catalog revision SELECT → 좋아요 수 Redis GET
  → catalog revision SELECT + stock revision SELECT → 재고 Redis GET
  → JSON 합성
→ 트랜잭션 종료·커넥션 반환
```

`CacheVersions.key()`가 namespace마다 DB를 호출하고, `ProductReadFacade`의 전체 읽기 트랜잭션이 Redis 조회·역직렬화·합성 중에도 커넥션을 유지한다. 같은 catalog revision을 한 요청에서 3번 읽는다. 목표 1,700 RPS라면 hit이어도 이 경로만 약 8,500 SELECT/초다. 정합성 검증을 넣은 현재 경로는 고정 데이터 캐시로 컨트롤러 응답을 즉시 반환하던 19번(p99 51ms)과 다르다.

| 관측 | 본 측정 결과 |
| --- | --- |
| Hikari active / pending 최대 | 40 / 161 |
| Tomcat busy 최대 | 200 / 설정 200 |
| 표본 커넥션 획득 대기 평균 / 최대 | 248 / 1,753ms |
| 표본 SQL execute 합계 평균 | 요청당 12.5ms |
| 표본 서버 내부 평균 | 313ms |
| 클라이언트 TTFB 평균 | 4,133ms |
| 연결 준비(blocked) / TCP connect 평균 | 0.048 / 0.039ms |
| 앱 Docker CPU 평균 / 최대 | 177.5 / 199.8% — 2 vCPU 합산, 최대 약 100% 사용 |
| DB Docker CPU 최대 | 68.2% — 코어 합산 |
| Redis master Docker CPU 최대 | 3.16% |
| 비동기 로그 큐 최대 | 0 |

**느린 SQL 한 개보다 커넥션을 얻기 위한 대기와 앱 처리 용량 포화가 눈에 띈다.** 연결 준비·전송보다 서버의 첫 응답을 기다리는 시간이 대부분이다. Tomcat 200개가 모두 바쁘므로 앞단 대기도 유력하지만, 클라이언트 전체와 1% 서버 표본의 시간 차이를 정확한 큐 대기시간으로 빼지는 않는다.

Hikari usage 누적 약 2,416초/시작 43,965건은 요청당 커넥션 점유 합계 약 55ms다(인증과 본문 조회 각각 사용). 포화 상태에서 40개/0.055초는 약 728요청/초로 관측 처리 규모와 비슷하다. 수집 구간·회복 요청이 섞인 근사치이며 독립적인 처리 한계 증명은 아니다. 커넥션 수만 늘리면 이미 포화된 앱 CPU와 DB 부하를 더 키울 수 있다.

## 캐시·부하기·예열의 구분

- 본 측정 전후 Redis miss·expired·evicted 증가 **0**, hit **131,904 증가**, 캐시 오류 증가 **0**. 세 키 TTL도 양수로 감소했다. 이번 병목은 캐시 만료나 재채움 폭주로 설명되지 않는다. Redis 카운터는 측정 주변 점검을 포함한 전역 값이다.
- 부하기 8 vCPU에서 k6 CPU 최대 482%(코어 합산), 연결 준비 p99 0.46ms. 부하기 CPU 포화가 주원인이라는 증거는 없지만 모든 부하기 제약을 배제한 것은 아니다.
- 요청이 약 4.1초 머무르며 VU 3,000개가 점유된다. `1,700 × 4.1 ≈ 7,000`개의 동시 요청이 필요한 상태라 미시작이 생긴다. VU 확대는 서버 지연 자체를 고치지 않는다.
- 본 측정 중 누적 JIT 컴파일 시간이 약 70초 증가했다. 병렬 컴파일의 누적 경과 시간이며 CPU 시간으로 해석하지 않는다. GC pause 합계는 약 0.71초. 예열이 충분했다고 단정할 수 없다.

## 다음 확인 순서

1. 같은 읽기 스냅샷 안에서 catalog·stock revision을 **한 번에 조회하고 요청 내 재사용**한다. 사용자 확인과 삭제·늦은 채움 보호는 유지한다. 현재 5 SELECT를 2 SELECT로 줄이는 후보이며 효과는 비교 측정해야 한다.
2. 조회 트랜잭션이 커넥션을 잡는 범위와 Redis/JSON 처리 비용을 프로파일로 확인한다. 정합성 테스트 없이 트랜잭션부터 제거하지 않는다.
3. 예열 안정화 후 같은 조건으로 재측정한다. CPU 원인의 정확한 비중은 현재 로그만으로 확정할 수 없어 JFR/스레드 표본과 변경 한 가지씩의 비교가 필요하다.

분석을 위해 운영 코드를 추가 변경하거나 풀·스레드·VU를 늘리지는 않았다. 스탬피드 연구 전에 현재 hit 경로의 기준선을 개선·확정해야 한다.
