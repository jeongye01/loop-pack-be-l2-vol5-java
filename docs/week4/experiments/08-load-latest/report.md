# 최신순 부하 테스트 결과

**VU 3,000·1,000 RPS를 60초씩 3회 반복했으나, 세 번 모두 목표 부하를 유지하지 못했다. 이 조건을 개선 전 과부하 기준으로 보존한다.**

무필터 `latest`, `page=0`, `size=20`, 사용자 1. 상품 100만·좋아요 69만, 캐시 없음. 로컬 k6 → 서울 앱 → 서울 DB. 각 실행 전후 회복 확인, 비교 3회에는 프론트 수동 조회를 제외하도록 요청했다. 개선 작업은 아직 적용하지 않았다.

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 43,597 | 21,378 | 22,219 | 0 | 16,404 | 4.00초 | 5.001초 |
| 2 | 45,024 | 23,877 | 21,139 | 8 | 14,977 | 3.81초 | 5.001초 |
| 3 | 44,256 | 21,525 | 22,690 | 41 | 15,745 | 3.88초 | 5.001초 |

매회 목표는 약 60,000건이다. 실행 경계에서 k6가 1건을 추가 예약할 수 있어 시작+미시작 합계가 60,001건인 실행도 있다. 정상 응답은 HTTP·내용 검증 성공 건수이며, 오류율·timeout 비율의 분모는 실제 시작 건수다. 전체 응답 시간은 오류·timeout을 포함한다. timeout 설정은 5초지만 발생기 스케줄링 등을 포함한 관측 시간은 5초를 넘기도 한다.

| 회차 | 완료 처리량¹ | 정상 응답 처리량¹ | 서버 처리 평균² | 누적 SQL 평균² | 커넥션 획득 대기 평균² |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 673.1 RPS | 330.1 RPS | 200.6ms | 23.1ms | 142.9ms |
| 2 | 702.8 RPS | 372.7 RPS | 172.3ms | 22.6ms | 116.1ms |
| 3 | 684.2 RPS | 332.8 RPS | 189.7ms | 23.1ms | 132.5ms |

¹ 첫 요청 시작부터 마지막 클라이언트 요청 종료까지의 건수/초. 목표 RPS와 다르며 최대 처리량을 뜻하지 않는다. ² 연결된 서버 Trace만 집계했다. SQL·커넥션 대기는 서버 처리에 포함되므로 합산하지 않는다.

## 병목 관측

| 회차 | 앱 CPU 평균: 합산 / 전체 대비 | MySQL CPU 평균: 합산 / 전체 대비 | Hikari active / pending 최대 | 처리 중 요청 최대 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 154.2% / 77.1% | 105.1% / 52.6% | 40 / 160 | 200 |
| 2 | 156.1% / 78.0% | 107.4% / 53.7% | 40 / 160 | 200 |
| 3 | 158.6% / 79.3% | 100.2% / 50.1% | 40 / 158 | 196 |

Docker 코어 합산은 2 vCPU에서 최대 200%, 전체 대비는 이를 2로 나눈 값이다. 약 5초 간격 표본의 평균·관측 최대다.

- 요청당 SQL은 연결된 Trace에서 모두 5회다. N+1 재발은 관측되지 않았다.
- **커넥션 40개가 모두 사용되고 대기가 최대 158~160개 쌓였다.** 앱 CPU도 전체 용량 대비 평균 77~79%였다. 요청 대기와 커넥션 경합이 다음 분석 대상이다.
- 클라이언트 평균 3.8~4.0초에 비해 기록된 서버 처리는 평균 172~201ms다. k6의 응답 첫 바이트 대기는 평균 3.8~4.0초였다. 서버 계측 시작 전의 요청 대기·연결 처리·통신 등이 포함될 수 있어, 차이를 순수 네트워크 시간 또는 SQL 시간으로 단정하지 않는다.
- 로컬 k6의 CPU·메모리도 원본에 기록했다. VU 3,000은 유지해야 할 RPS가 아니라 요청을 수행할 수 있는 가상 사용자 수다. 이를 늘린다고 서버 처리량이 보장되지는 않는다.

**60초 정상 처리를 확인한 최고 단계는 500 RPS다. 정확한 정상 한계는 500~1,000 RPS 사이에서 아직 좁히지 않았다.** 600 RPS 실행은 사용자 요청으로 중단해 한계 판정에서 제외했다. 예비 실행에는 프론트 수동 확인이 섞일 수 있으므로 위의 고정 3회와 구분한다.

최초 100 RPS는 응답은 전부 성공했으나 서버 Trace 68건이 빠졌다. 실행 후 일괄 수집을 실행 중 연속 수집으로 바꾸고 100 RPS부터 다시 측정했다. 서버 설정·쿼리·인덱스는 변경하지 않았다.

## 측정의 한계와 기록

고정 3회에서도 서버 Trace가 각각 2·15·48건 연결되지 않았다. 응답을 받지 못한 요청을 포함하며, 미도달·연결 종료·수집 누락을 이 자료만으로 구분할 수 없다. 따라서 서버 통계는 전체 요청에 대한 완전한 통계가 아니며 검증 결과도 `measurementComplete=false`로 보존했다. 자원 수집과 회복 확인은 세 번 모두 통과했다.
