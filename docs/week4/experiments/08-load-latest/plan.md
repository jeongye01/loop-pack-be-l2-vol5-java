# 조회 성능 실험 계획서: 최신순 부하 한계와 개선 전 기준

- 실험 ID: 08-load-latest
- 상태: 고정 부하 3회 측정 완료, 개선 전 기준 기록
- 작성일: 2026-10-14
- 실행 버전: 코드 기준 `3bc0f0c`, 배포·인덱스는 Run 환경에 기록
- 공통 절차·결과 형식: [프로토콜](../protocol.md)
- 장비 사양: [서울 EC2](../environments/ec2-seoul.md)

## 실험 내용

`GET /api/v1/products?sort=latest&page=0&size=20`, 사용자 1, 브랜드 필터 없음.

예비 탐색 이후 **VU 3,000·1,000 RPS·60초·timeout 5초**를 3회 반복하여 개선 전 기준으로 삼는다. 프론트 수동 조회는 제외하도록 요청했다. 매회 서버 회복을 확인하며, 같은 부하에서의 오류·누락은 그대로 기록한다. 응답 불일치나 회복 실패 시 남은 실행을 중단한다.

RPS별 응답 시간·성공/오류/미시작 수와 앱/DB CPU·Hikari 대기·발생기 상태를 비교한다. CPU는 Docker 코어 합산과 전체 2 vCPU 대비 사용률을 구분한다. VU 부족이나 발생기·통신 제약을 서버의 최대 처리량으로 단정하지 않는다.

## 변경 사항

쿼리·인덱스·데이터·서버 설정은 유지한다. 예비 측정은 100 RPS 간격으로 시작했고 이후 사용자 요청에 따라 1,000 RPS로 올렸다. VU는 100 → 300 → 1,000 → 3,000으로 변경했으며 각 Run 설정을 보존한다.

100 RPS 최초 실행에서 종료 후 로그 수집 시 초기 Trace가 유실되어, 실행 중 SSH로 연속 수집하도록 공통 실행기를 수정했다. 집계 테스트 4개 통과, 100 RPS 재측정에서 전체 Trace 연결을 확인했다. 부하 생성은 로컬 k6이며 연속 로그 수집의 비용도 포함된 환경이다.

## 적용 전 기록

- [50 RPS 예비 결과](../07-load-likes/report.md): 최신순 3,000건 전부 성공, 평균 13.2ms·p95 18ms.
- 이번 예비 탐색: 500 RPS(VU 300) 정상. 1,000 RPS에서는 요청 누락과 대기 증가, VU 3,000에서 timeout 발생.
- 프론트 수동 확인이 가능했던 예비 실행과 고정 조건 3회 결과를 구분한다. 중단한 600 RPS는 정상/실패 경계 판정에서 제외한다.
