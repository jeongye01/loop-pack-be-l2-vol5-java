# 상품 목록 RPS 예비 측정 결과

측정일: 2026-10-13 (KST)

**현재 로컬 환경에서는 5~6 RPS에서 지연이 크게 증가하고, 8 RPS에서는 명확한 과부하가 관찰됐다.** 6 RPS는 반복에 따라 실패율이 0~3.87%로 달라 정확한 최대 처리량으로 단정하지 않는다.

## 조건

- 요청: `GET /api/v1/products?brandId=7&sort=price_asc&page=0&size=20`, `X-USER-ID: 1`.
- 데이터: `uniform-10k-v1`, 상품 10,000·브랜드 100·좋아요 999,493개. 응답은 상품 20개·전체 건수 100.
- Mac14,2 / 8코어 / 메모리 16 GiB. Docker VM 8 CPU / 약 7.65 GiB. 앱·DB·k6 및 다른 로컬 프로그램이 같은 장비를 공유한다.
- Java 21.0.12.1, MySQL 이미지 8.0.46, k6 2.3.0. 앱은 `local,perf`, `ddl-auto=none`, SQL 출력 없음.
- Hikari 최대 40·최소 유휴 30·연결 대기 3초. Tomcat 최대 스레드 200. 기존 값 유지.
- 현재 미커밋 변경을 포함해 bootJar로 빌드했다. Git SHA만으로 실행 소스를 식별할 수 없으며 environment.json의 작업 트리 상태를 함께 봐야 한다.
- Nginx·Redis 캐시·Grafana 없이 k6가 Spring Boot에 직접 GET 요청. Actuator 스냅샷과 프로세스·컨테이너 자원 샘플도 기록했다.
- 요청 전송률 고정, 100 VU 사전 할당, 요청 timeout 5초, 종료 유예 10초. 처음 1 RPS로 15초 준비 후 1·2·3·5 RPS를 측정했다. 이후 앱 재시작 없이 회복 상태에서 6, 5·6, 8 RPS를 추가 측정했다.

## 초기 10 RPS 실행

[첫 실행](results/20261013-004229/results.json)은 준비 30초·측정 20초에서 이미 과부하가 발생했다. 준비 실행 HTTP 실패율 95.68%, 측정 실패율 100%였다. JSON 필드 순서까지 비교하던 초기 검증기도 이 실행에서 오검출했고, 이후 객체 키를 정렬해 비교하도록 수정했다. 따라서 이 실행의 응답 검증 실패율은 해석에서 제외하고, 정상 단계와 동일 조건의 비교 결과로 사용하지 않는다. HTTP timeout·DB 연결 풀 고갈 기록은 초기 과부하 관찰 근거로만 남긴다.

## 관찰한 병목 후보

- 5 RPS는 두 번 모두 오류 없이 p95 약 690~792ms였다.
- 6 RPS는 p95 약 3.44~4.86초로 증가했다. 8 RPS는 요청 약 80.75%가 실패했다.
- 최초 6 RPS 실행의 MySQL CPU 샘플 평균은 약 759%, 최대 약 883%였다. Docker CPU는 여러 코어 합산 수치이며 호스트 전체 사용률과 동일하지 않다. 같은 실행의 k6 프로세스 CPU 샘플 최대는 6.4%였다.
- 초기 10 RPS 서버 로그에서 Hikari `total=40, active=40, idle=0` 및 연결 획득 timeout을 확인했다. 풀 증설이 해결책이라는 의미는 아니다.
- 코드상 상품 20개에 각각 `countByProductId`를 호출한다. [ProductUseCase](../../../../apps/commerce-api/src/main/java/com/loopers/product/application/ProductUseCase.java)의 목록 조회 경로다.
- 실제 `product_like` 인덱스는 PK와 `(user_id, product_id)` 유일 인덱스다. 상품별 COUNT에 대응하는 SELECT의 EXPLAIN은 `Using index for skip scan`을 표시했다. [읽기 전용 확인 결과](results/query-evidence.txt).
- 좋아요 집계 반복과 인덱스 접근 비용이 다음 분석 대상이다. 이번에는 요청당 SQL 수 전체를 계측하거나 실제 API SQL의 EXPLAIN ANALYZE까지 수행하지 않았으므로 원인별 비용을 확정하지 않는다.

## 검증·정리

앱 빌드, Python 구문 확인, k6 실제 실행 및 성공 응답 비교를 완료했다. 프로덕션 코드는 변경하지 않아 이번 측정만을 위해 전체 회귀·lint·ArchUnit을 다시 실행하지 않았다. 실험 데이터와 인덱스는 변경하지 않았다. 이번에 실행한 실험 앱은 종료했고, MySQL 컨테이너와 데이터는 유지했다.
