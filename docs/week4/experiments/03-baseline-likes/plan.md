# 좋아요순 Baseline 실험 계획

- 실험 ID: `03-baseline-likes`
- 상태: 실행 완료. 0.5 RPS 정상·0.75 RPS 실패를 각각 3회 확인. [결과](report.md)
- 비교 대상: [가격순 baseline](../02-baseline/report.md)
- 공통 기준: [프로토콜](../protocol.md)

## 실험 내용

브랜드 7의 상품 5,000개 중 좋아요가 많은 첫 20개를 조회한다. 정렬만 바꿔 정상 처리 범위와 실패가 시작되는 RPS를 찾는다.

```http
GET /api/v1/products?brandId=7&sort=likes_desc&page=0&size=20
X-USER-ID: 1
```

## 변경 사항과 실행 조건

`02-baseline`에서 `sort`만 `price_asc` → `likes_desc`로 변경한다. 같은 서울 EC2·앱 이미지·DB·100만 상품 데이터셋을 사용한다.

| 항목 | 조건 |
| --- | --- |
| 시작·확장 | 1 → 2 → 3 → 4 → 6 → 8 → 12 RPS. 실패하면 상승 중단 |
| 하향·경계 | 1부터 실패하면 0.5 RPS. 정상·실패 사이를 0.25 RPS까지 좁히고 양쪽 각각 총 3회 측정 |
| 실행 | 각 부하에서 준비 30초 + 본 측정 60초 |
| 도구 | 기존 k6 실행기, 100 VU, 타임아웃 5초, 종료 유예 10초 |

## 적용 전 기록

부하 없는 단일 curl 요청은 HTTP 200, `time_total` 1.657999초였다(2026-10-13, 제한 시간 30초). 캐시는 초기화하지 않았다. 본 실험 전 CSV로 계산한 좋아요순 기대 응답과 실제 응답, 서버·SQL 기록 연결을 검증한다.
