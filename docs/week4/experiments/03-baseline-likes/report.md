# 좋아요순 Baseline 결과

**5초 타임아웃·본 측정 60초 기준, 0.5 RPS는 3회 모두 성공했고 0.75 RPS는 3회 모두 타임아웃이 발생했다.** 0.25 RPS 간격으로 탐색한 경계이며 정확한 최대 처리량이나 장시간 지속 가능한 처리량을 뜻하지 않는다.

브랜드 7·첫 페이지 20개·사용자 1로 요청했다. [가격순 실험](../02-baseline/report.md)과 같은 데이터·장비·앱·타임아웃을 사용하고 `sort=likes_desc`만 변경했다. 기존 공통 실행기를 재사용했다.

## 가격순과 비교

| 정렬 | 0.5 RPS | 0.75 RPS | 1 RPS |
| --- | --- | --- | --- |
| 가격순 | 1회 성공, 평균 1.47초 | 3회 모두 성공, 평균 2.15~2.36초 | 3회 모두 타임아웃 발생 |
| 좋아요순 | 3회 모두 성공, 평균 1.62~1.68초 | 3회 모두 타임아웃 발생 | 1회 타임아웃 발생 |

평균 범위는 Run별 평균의 범위다. 두 정렬은 서로 다른 시각에 순차 측정했고 캐시는 초기화하지 않았다. 이 결과만으로 차이를 정렬 비용만의 효과로 확정하지 않는다.

0.5 RPS는 93건 모두 성공했다. 0.75 RPS는 총 137건 중 89건이 타임아웃이었다. 실패 구간의 클라이언트 시간은 타임아웃을 포함하며 약 5초에서 잘리므로 서버가 처리를 끝낸 시간과 다르다.

단일 curl 요청은 HTTP 200·1.657999초였다(제한 시간 30초, 캐시 초기화 없음). 본 부하 테스트의 타임아웃은 5초다.

진단 시작부터 마지막 측정 종료까지 956.0초(약 15.9분) 걸렸다. 표의 소요 시간은 준비 30초·본 측정 60초에 환경 수집·응답 확인·회복·로그 수집 시간을 포함한다.

## SQL·자원 관찰

- 요청마다 SQL 44개: 사용자 1·브랜드 1·목록 1·재고 20·좋아요 수 20·전체 상품 수 1.
- 좋아요순 목록은 `product_like`를 LEFT JOIN하고 상품별 GROUP BY 후 `COUNT(id) DESC, product.id`로 정렬한다. 이 SQL이 JDBC 실행 시간의 약 10~12%를 차지했다.
- 목록을 얻은 후 상품마다 실행하는 좋아요 수 조회 20개가 약 87~89%를 차지했다. 목록에서 집계한 좋아요 수를 응답에 재사용하는 것은 개선 후보이며 이번 실험에서는 코드를 바꾸지 않았다.
- DB CPU는 [집계 JSON](analysis.json)에 모든 코어 합산(2 vCPU 상한 약 200%)과 서버 전체 용량 대비(상한 100%)를 나누어 저장했다. 이는 컨테이너 사용률이며 서버 전체 프로세스의 사용률이 아니다.
- 메모리·디스크 I/O·앱 지표 원본은 각 Run의 `resources.json`, 요청별 SQL과 시간은 `traces.jsonl`에 보관했다. SQL 실행 계획은 별도로 수집하지 않았다.
