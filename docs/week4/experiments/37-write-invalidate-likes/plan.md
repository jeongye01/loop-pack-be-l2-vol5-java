# 읽기 + 구매 + 좋아요 등록·취소 혼합 부하

36번 Write Invalidate 배포 그대로 사용한다. 최신순 첫 페이지 20개 1,700 RPS/VU 3,000, 구매 10건/초/VU 100에 좋아요 등록·취소 합계 목표 10 RPS/VU 100을 추가한다. 최신순 TTL 5초, 나머지 300±30초, 로컬 Single Flight 유지.

좋아요는 초당 5개 사용자 흐름이 등록→취소를 순차 실행한다. 등록 5건/초·취소 5건/초를 목표로 하며 취소 시작은 등록 응답만큼 늦어진다. 독립적인 두 constant-arrival 시나리오는 아니다. 매 흐름에 신규 사용자를 배정하고 상품 1~20에 분산하여 중복 등록으로 인한 무변경 응답을 피한다. 같은 회차 구매용 신규 사용자를 활용하되 좋아요 관계는 흐름별 고유하다. 등록 201·취소 200과 성공 body를 확인한다. 모호한 쓰기 응답은 재시도하지 않는다.

60초 × 3회, 최초 300/700 RPS 각 30초 예열 후 회차 사이 회복만 확인한다. 현재 서버는 36번 실험을 이미 수행했으므로 재시작 직후의 36번과 예열 상태가 다르다. 결과 비교에 이 차이를 명시한다.

읽기, 구매 전체, 좋아요 등록, 취소 각각 평균·p95·p99·성공률·실행 수를 기록한다. 지연 목표는 각각 p99 ≤100ms, 시작된 요청 성공률 100%, 미시작 0이다. 1분 목표: 조회 102,000건, 구매 600건(쓰기 API 약 1,200회), 좋아요 등록 300건+취소 300건. 경계에서 초과 실행된 수는 실제 값으로 보고한다.

구매 주문·재고·포인트 대조, LIKE_JSON과 DB의 해당 사용자 좋아요 잔존 관계 확인, 원본 호출·Redis hit/miss·삭제 성공/실패·CPU·Hikari·Tomcat 수집을 유지한다. seed 응답 전체 일치 검사는 하지 않는다. 좋아요 표시 수와 순위는 기존 TTL 정책을 유지하며 이번 실험은 그 표시 신선도 검증이 아니다. 최신순 공통 목록은 좋아요 변경으로 삭제하지 않고 해당 사용자의 내 좋아요 캐시만 무효화한다. 이 실험은 내 좋아요 목록 캐시를 미리 채우지 않는다.

공통 products.js·결과 집계와 좋아요 사후 대조만 확장한다. 앱 코드·API·도메인 계약은 변경하지 않는다.

## 측정 중 목표 정정

사용자가 읽기 p99 100ms, 구매 전체 p99 300ms로 확정했다. 원본 실행 판정은 보존하고 결과 문서와 revised-slo.json에서 새 기준으로 해석한다. 좋아요는 별도 지연 목표 없이 관찰한다. 다음 38번에서는 구매만 증량한다.
