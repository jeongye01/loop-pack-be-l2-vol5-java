# Redis 분산 락 혼합 부하 — 3회 결과

**세 회차 모두 읽기·구매 p99 100ms SLO에 미달했다. 기록상 로컬 Single Flight보다 느렸으며, 원본 목록 조회 감소만으로 지연이 해결되지는 않았다.**

읽기 최신순 첫 20개 1,700 RPS + 주문 생성→확정 10건/초, 각 60초. VU 3,000/100, 최신순 TTL 2초, 나머지 300±30초, DB revision 유지. 앱 1대에서 최초 예열 후 재시작 없이 3회 측정했다.

락·오류 증분은 preflight 마지막 표본부터 recovery 마지막 표본까지이므로 순수 60초만의 값이 아니다. 경합은 고유 요청 수가 아닌 SET NX 실패 시도 수다. Redis hit/miss는 전역 카운터로 캐시 외 락 해제 Lua의 GET 등도 포함하므로 응답 캐시 적중률로 읽으면 안 된다. put 오류 증분은 세 회차 모두 0이다.

## 로컬 Single Flight와 비교

| 회차 | 로컬 읽기 p99 | Redis 락 읽기 p99 | 로컬 구매 p99 | Redis 락 구매 p99 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 3,064 | 3,264 | 5,677 | 6,057.16 |
| 2 | 1,524 | 2,252 | 2,897 | 4,207.03 |
| 3 | 841 | 1,923 | 1,531 | 3,584.22 |

목록 원본 횟수는 로컬 41/44/38회, Redis 락 45/41/35회로 비슷하다. 앱 1대에서는 서버 간 조율의 이점을 측정하지 못하는 반면 SET NX·해제·주기적 재조회 비용이 추가된다. 현재 코드는 대기자도 매번 DB revision→캐시를 다시 읽고 miss면 SET NX를 다시 시도한다. 수만 회의 경합 시도와 앱 CPU·Tomcat 포화는 이 경로를 다음 분석 대상으로 지목한다. 다만 각 비용의 기여도를 직접 분리 계측하지 않았으므로 분산 락 하나만 지연 원인으로 확정하지 않는다.

32번은 회차마다 300/700 RPS 예열, 이번은 최초 한 번만 예열했다. 신규 배포·시간 경과·데이터 변경량도 다르다. 따라서 위 표는 관측 비교이며 엄밀한 동일 조건 A/B나 분산 락 일반에 대한 우열 결론이 아니다. 회차별 결과 개선 역시 안정적인 SLO 달성으로 보지 않는다.

## 예열·구현·검증

첫 300 RPS 예열은 p99 5,001ms, timeout 4,377건이었다. 회복 후 700 RPS는 p99 64ms·성공률 100%·미시작 0건이었다. 예열 실패를 숨기거나 본 측정에 합치지 않는다. 2·3회차 warmup-policy.json에는 같은 컨테이너라 예열 생략한 이유를 기록했다.

락 TTL 5초·대기 예산 1초·재확인 간격 20ms. UUID 소유자 확인 Lua로 해제하며 오류·대기 초과 시 DB fallback한다. 대기자는 DB 트랜잭션 밖에 있고 소유자는 기존 miss 트랜잭션에서 revision·캐시를 재확인한다. 락 만료·eviction·장애·다른 revision·후속 캐시 miss에서는 중복 원본 조회가 가능하다. 기존 revision 정합성 보호를 유지하며 Bulkhead는 추가하지 않았다.

전체 테스트 494개(일반 490·비동기 4), 실패·skip 0. Checkstyle·ArchUnit 통과. 기존 miss 테스트가 중복 revision 조회를 잡아 기대값 수정 없이 구현에서 제거했다. Redis 공유 락·소유자 변경·오류·대기 초과·트랜잭션 밖 대기 테스트를 추가했다. 세 본 측정 모두 회복·원본 수집·구매 대조 성공. 측정 로그의 Stop escalation 예외는 미시작 요청 판정이며 반복 실행기는 회복·수집·구매 검증을 확인한 후 고정된 다음 회차를 진행했다.
