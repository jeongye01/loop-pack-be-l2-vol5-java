# 캐시 변경·롤백·늦은 채움 보호 검증

**관리자 변경 후에는 새 결과를 반환하고, 롤백하면 기존 결과를 유지한다. Redis에 옛 값이 남거나 뒤늦게 저장되어도 변경 완료 후 새 요청은 이전 캐시를 사용하지 않는다.**

과제 체크리스트의 “정상 관리자 변경·삭제·rollback의 기존 계약을 지키고, 무효화 실패·늦은 채움에서는 선택한 표시 신선도·복구 정책과 필수 보호 조건을 검증했다”에 대응하는 기록이다.

## 1. 정상 변경·삭제·롤백

실제 애플리케이션·MySQL·Redis Testcontainers에서 캐시를 먼저 채운 뒤 기존 쓰기 경로로 변경하고 다시 조회했다.

| 장면 | 확인한 결과 |
| --- | --- |
| 상품 이름·가격 수정 | 새 이름·가격과 가격순 정렬 반영, 다른 브랜드 상품 값 유지 |
| 상품 생성 | 전체·해당 브랜드 목록에 추가 |
| 상품 삭제 | 목록·상세·내 좋아요에서 제외, 다른 상품 유지 |
| 브랜드 이름 수정·생성 | 브랜드 목록과 관련 상품 응답 반영 |
| 브랜드 삭제 | 소속 상품 전체 제외, 다른 브랜드·상품 유지 |
| 재고 변경·주문 확정 | 품절 전환 시 해당 상품 표시 갱신, 상품 기본 정보·좋아요 캐시 유지 |
| 상품 수정 rollback | DB 이름·가격·revision과 기존 캐시 유지 |
| 품절 전환 rollback | 기존 품절 상태·캐시 유지, 이후 정상 변경은 반영 |

코드 근거: [CacheInvalidationScopeHttpTest](../../apps/commerce-api/src/test/java/com/loopers/config/cache/CacheInvalidationScopeHttpTest.java)의 `productUpdateRefreshesExactFieldsAndPriceOrder`, `productDeletionDoesNotRemoveOtherProducts`, `brandDeletionDoesNotRemoveAnotherBrandsProducts`, `rollbackPreservesDatabaseRevisionAndAllCachedViews`, `availabilityRollbackDoesNotLeakState` 등.

## 2. 선택한 표시 신선도 정책

- 상품·브랜드 변경과 품절 전환은 DB 변경과 revision을 같은 트랜잭션에서 갱신한다. 정상 변경 완료 후 시작한 조회는 새 revision 키를 사용한다.
- 좋아요 등록·취소는 본인의 내 좋아요 목록만 즉시 반영한다. 공통 좋아요 수·순위는 무효화하지 않고 TTL 5분 ±30초로 갱신한다.
- 변경과 겹쳐 이미 진행 중인 조회는 변경 전 DB 시점의 결과를 반환할 수 있다. 변경 완료 후 새 요청과 구분한다.
- 삭제 상품 비노출, 사용자 소유권, 주문 금액·재고·포인트 판단은 표시 지연 허용 대상이 아니다.

정책·비용은 [캐시 ADR](ADR.md), 쓰기별 범위는 [키·TTL·사용자 정보와 쓰기 영향 범위](캐시%20키·TTL·사용자%20정보와%20쓰기%20영향%20범위.md)에 정리했다.

## 3. 늦은 채움을 어떻게 재현했나

latch로 실제 HTTP 조회를 DB 읽기 직후 멈추고 아래 순서를 강제했다.

```text
이전 DB 결과 읽기 → 조회 정지
→ 관리자 수정 또는 삭제 commit
→ 이전 조회 재개 → 옛 revision 키에 캐시 저장
→ 새 HTTP 조회
```

옛 값이 Redis에 실제 저장된 것까지 확인한 뒤, 새 요청은 수정된 값을 반환하거나 삭제 상품에 404를 반환하는지 검사했다. 단순히 캐시 저장을 막아 통과시킨 검증이 아니다. 대기에는 10초 제한을 두고 finally에서 latch와 worker를 정리했다.

코드 근거: `CacheInvalidationScopeHttpTest.delayedRealHttpReadCannotRepopulateCurrentVersion` — 수정·삭제 두 조건.

## 4. 무효화 실패·Redis 복구는 어떻게 보호하나

현재 방식은 Redis 키 삭제 성공에 의존하지 않는다. **DB 변경과 revision이 함께 commit되면 기존 키가 그대로 남아도 새 요청이 사용하지 않는다.** Redis 삭제 실패를 주입한 테스트와 구분해, 실제 Redis 중단으로 접근이 불가능하고 복구 후 옛 키가 남는 상황을 검증했다.

| 순서 | 검증 |
| --- | --- |
| 기존 캐시 준비 | 가격 100원과 삭제 대상 상품을 캐시하고 옛 키 보존 |
| 실제 Redis 중단 | 테스트 전용 컨테이너 중단 확인 |
| 관리자 변경 commit | 가격 400원 수정·상품 삭제 성공 |
| 장애 중 재조회 | DB 우회로 400원 반환, 삭제 상품 404. Redis 읽기·저장 오류 발생 확인 |
| 동일 Redis 재시작 | 서버와 앱 연결 복구, 옛 키가 실제 남아 있는지 확인 |
| 복구 후 재조회 | 옛 키를 무시하고 현재 revision에 새 결과·TTL 저장, 이후 hit은 원본 조회 생략 |

코드 근거: [RedisRecoveryHttpTest](../../apps/commerce-api/src/test/java/com/loopers/config/cache/RedisRecoveryHttpTest.java)의 `outageWritesAndRecoveryNeverReuseOldRevision`. 상세 절차는 [Redis 장애 복구 검증 결과](Redis%20장애%20복구%20검증%20결과.md)에 있다.

## 5. 장애·늦은 채움에도 유지하는 필수 계약

| 보호 대상 | 확인한 결과 |
| --- | --- |
| 사용자 소유권 | 타인의 좋아요·주문 조회와 주문 확정 거절, 본인 목록·잔액 유지 |
| 주문 가격 | 캐시의 옛 표시 가격 대신 DB 가격으로 주문 생성, 이후 상품 가격이 바뀌어도 주문 저장 단가로 결제 |
| 재고·포인트 | DB의 실제 수량·잔액으로 판단. 부족하면 확정 거절, 주문·재고·잔액 유지 |
| 삭제 상품·브랜드 | 고객 조회·새 주문에서 제외, 다른 브랜드와 과거 주문 보존 |

늦은 채움은 `delayedPrivateListNeverBypassesOwnership`, `delayedDisplayFillCannotChangeOrderDecisions`로, 장애·복구는 `ownershipSurvivesOutageAndRecovery`, `orderUsesDatabaseAndStoredOrderPrice`, `brandDeletionPreservesPastOrders`로 확인했다.

## 검증 결과와 범위

2026-10-16 전체 검사에서 변경·늦은 채움 보호 테스트 **26개**, Redis 장애 복구 테스트 **9개**가 통과했다. 전체 514개 중 513개 성공, 실패·오류 0개, 장시간 선택 관측 1개 skip이며 Checkstyle·ArchUnit도 통과했다. [실행 결과 기록](ADR.md)

이 문서는 기존 테스트·실행 결과를 정리했으며 새로 실행한 측정은 아니다. 로컬 Testcontainers 검증으로, EC2 장애 부하나 혼합 읽기·쓰기의 지연 상한을 입증한 결과는 아니다.
