# 스키마 제약 반영 계획

작성일: 2026-10-12

## 목적과 범위

기존 도메인·서비스 코드가 보장하는 규칙 중 DB에서도 강제할 수 있는 조건을 스키마에 반영한다. SQL·CSV 직접 적재에서도 잘못된 저장 상태를 막는다.

- 대상은 이번 데이터 적재에 사용하는 브랜드·상품·재고·좋아요다. 주문·포인트는 이번 변경 범위에 포함하지 않는다.
- 기준은 [도메인 불변식](../week2/domain-rules.yaml)과 현재 구현이다. 기존 규칙과 2주차 문서는 변경하지 않는다.
- FK는 추가하지 않는다.
- 구현 및 개발·실험 DB 적용을 완료했다. 실행 방법과 검증 결과는 [migrations/README.md](migrations/README.md)에 기록한다.

## 불변식별 반영 계획


| 불변식              | 기존 규칙                               | DB 반영 계획                                                                                               |
| ---------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `INV-BRAND-01`   | 브랜드명은 앞뒤 공백 제거 후 1~50자              | `brand.name`에 NOT NULL, 길이 제한, 빈 이름·정규화되지 않은 앞뒤 공백을 막는 CHECK를 적용한다. Java `trim()`과 UTF-16 길이 기준을 고려한다. |
| `INV-BRAND-02`   | 미삭제 브랜드끼리 이름 중복 금지. 대소문자는 구분        | 미삭제 행의 이름에만 유일 제약을 적용한다. 삭제된 이름의 재사용을 허용하고 Java 문자열 동등성과 맞는 비교 기준을 사용한다.                               |
| `INV-PRODUCT-06` | 상품명은 앞뒤 공백 제거 후 1~100자              | `product.name`에 NOT NULL, 길이 제한, 빈 이름·정규화되지 않은 앞뒤 공백을 막는 CHECK를 적용한다.                                  |
| `INV-PRODUCT-07` | 같은 브랜드의 미삭제 상품끼리 이름 중복 금지. 대소문자는 구분 | 미삭제 행의 `(brand_id, name)`에 유일 제약을 적용한다. 다른 브랜드의 같은 이름과 삭제된 이름의 재사용은 허용한다.                              |
| `INV-PRODUCT-08` | 가격은 1~1,000,000,000원                | 기존 `price` NOT NULL을 유지하고 `price BETWEEN 1 AND 1000000000` CHECK를 추가한다.                                |
| `INV-PRODUCT-09` | 상품은 존재하는 미삭제 브랜드에 속함                | `brand_id`에 NOT NULL을 추가한다. **불변식의 일부만 보호**하며, 브랜드 존재·미삭제 여부는 서비스·CSV 검증에 남긴다.                         |
| `INV-STOCK-14`   | 재고 수량은 0 이상                         | 기존 `quantity` NOT NULL을 유지하고 `quantity >= 0` CHECK를 추가한다.                                              |
| `INV-LIKE-24`    | 한 고객은 한 상품에 좋아요 하나만 가짐              | 기존 `(user_id, product_id)` UNIQUE를 유지하고 두 컬럼에 NOT NULL을 추가한다.                                          |


이름의 공백 제거는 기존 코드가 담당한다. DB는 이름을 자동 수정하지 않고, 공백 제거가 끝난 유효한 저장 상태인지 검사한다. 단순한 SQL `TRIM()`이나 문자 수 검사가 Java의 `trim()`·`String.length()`와 같다고 가정하지 않는다.

조건부 이름 유일성은 미삭제 행의 이름을 binary로 변환하고 삭제된 행에서는 NULL인 `active_name_key` 생성 컬럼과 UNIQUE 인덱스로 구현했다. 실제 구현에서는 대소문자·악센트·유니코드 문자열을 임의로 같은 이름으로 취급하지 않도록 검증한다. 상품명 전체 고유성은 CSV 생성 조건이므로 DB에서는 강제하지 않는다.

### 기존 매핑 제약 유지

- `stock.product_id`의 NOT NULL·UNIQUE를 유지한다. 이는 상품별 재고가 **최대 하나**임을 보장하며, 재고 행이 반드시 존재하는지는 서비스·CSV 검증에서 확인한다. 이 구조 제약에 별도의 불변식 번호를 임의로 부여하지 않는다.
- 공통 ID의 PK·자동 증가, 생성·수정 시각의 NOT NULL을 유지한다.

## 변경할 파일과 이유

아래 파일에 구현했다. 기존 도메인·API 정책과 FK 제외 조건은 유지한다.

### 기존 코드 수정

Java 파일 경로는 `apps/commerce-api/src/main/java/com/loopers/` 기준이다.

| 파일 | 바꿀 내용 | 이유 |
| --- | --- | --- |
| `brand/domain/Brand.java` | 이름에 NOT NULL·길이·CHECK와 활성 이름 생성 컬럼·UNIQUE 매핑 추가 | Hibernate로 새 테이블을 만들 때도 브랜드명 규칙이 DB 제약으로 생성되게 한다. |
| `product/domain/Product.java` | 이름에 NOT NULL·길이·CHECK와 활성 이름 생성 컬럼·UNIQUE, 가격에 범위 CHECK, 브랜드 ID에 NOT NULL 추가 | 새 테이블에서도 잘못된 이름·가격과 NULL 브랜드 ID를 거절하게 한다. |
| `product/domain/Stock.java` | 재고 수량에 0 이상 CHECK 추가 | SQL로 직접 넣거나 수정해도 음수 재고를 막는다. 기존 상품 ID의 NOT NULL·UNIQUE는 유지한다. |
| `like/domain/Like.java` | 사용자 ID·상품 ID에 NOT NULL 추가 | 사용자 ID나 상품 ID가 NULL인 좋아요 행을 막는다. ID의 실제 존재 여부를 검사하는 FK는 추가하지 않는다. |
| `brand/infrastructure/BrandRepositoryAdapter.java` | 저장·수정 SQL을 실행하는 지점에서 브랜드명 유일 제약 위반을 식별해 `DUPLICATE_BRAND_NAME`으로 변환 | 동시 요청이 서비스의 중복 검사를 통과해도 DB가 중복을 막고, API는 기존 이름 중복 오류를 반환하게 한다. |
| `product/infrastructure/ProductRepositoryAdapter.java` | 저장·수정 SQL을 실행하는 지점에서 상품명 유일 제약 위반을 식별해 `DUPLICATE_PRODUCT_NAME`으로 변환 | DB가 발견한 상품명 중복도 기존 API 오류로 반환하게 한다. 가격·다른 제약 위반을 이름 중복으로 처리하지 않는다. |

`support/error/DatabaseConstraintErrors.java`를 추가해 MySQL 중복 키 오류와 제약 이름을 식별한다. 실행 스크립트의 실제 적용·검증 코드는 `docs/week4/migrations/apply_catalog_constraints.py`에 둔다.

생성자와 이름 검증 서비스의 기존 검사는 유지한다. 저장 어댑터에서는 UPDATE가 메서드 반환 뒤 commit 시점까지 미뤄져 예외 변환을 빠져나가지 않도록 SQL 실행 시점도 확인한다.

### SQL·실행 파일

SQL·스크립트 경로는 `docs/week4/migrations/` 기준이다. 아래 파일을 추가했다.

| 파일 | 내용 | 이유 |
| --- | --- | --- |
| `02-check-catalog-data.sql` | NULL·가격·재고 범위·이름 길이와 공백·활성 이름 중복을 조회하는 SQL | 제약을 추가하기 전에 기존 데이터가 규칙을 위반하는지 확인한다. 데이터를 자동 수정하거나 삭제하지 않는다. |
| `03-add-catalog-column-constraints.sql` | 기존 테이블에 NOT NULL·이름 길이·CHECK를 추가하는 ALTER SQL | 엔티티 매핑 변경만으로는 이미 존재하는 DB가 바뀌지 않으므로 기존 DB에도 같은 기본 제약을 적용한다. |
| `04-add-active-name-uniqueness.sql` | 브랜드·상품의 미삭제 이름을 대상으로 하는 생성 컬럼과 UNIQUE 인덱스 추가 SQL | 삭제 상태와 대소문자 구분을 고려한 이름 중복 규칙을 단순한 `unique=true` 대신 표현한다. |
| `apply-catalog-constraints.sh` | 지정한 DB에 사전 점검과 필요한 제약 SQL을 순서대로 실행하는 스크립트 | 기존 DB와 Hibernate로 갓 만든 DB 모두에 빠진 제약을 적용한다. 이미 있는 제약은 정의를 확인하고, 데이터 위반·정의 불일치·SQL 오류가 있으면 중단한다. |

실행 흐름은 다음과 같다.

- **기존 DB:** 사전 점검 → 빠진 기본 제약 추가 → 활성 이름 UNIQUE 추가.
- **새 실험 DB:** Hibernate `create`로 테이블·기본 제약 생성 → 앱 종료 → 같은 스크립트로 제약 정의 검증 → `none`으로 전환 → CSV 적재.

이름 유일 제약까지 엔티티 매핑에 포함했다. 새 DB에서도 `apply-catalog-constraints.sh`를 실행해 정의를 확인하며, 모두 일치하면 추가 변경 없이 종료한다.

### 오류 응답을 확인할 테스트 파일

테스트 경로는 `apps/commerce-api/src/test/java/com/loopers/` 기준이다. 새 스키마·마이그레이션 테스트 클래스는 이번 구현 범위에서 제외하고, 기존 테스트에 오류 변환·응답 검증을 추가한다.

| 구분 | 파일 | 바꿀 내용과 이유 |
| --- | --- | --- |
| 수정 | `brand/infrastructure/BrandRepositoryIntegrationTest.java` | DB에서 발생한 브랜드명 유일 제약 위반이 `DUPLICATE_BRAND_NAME`으로 변환되는지 확인한다. |
| 수정 | `product/infrastructure/ProductRepositoryIntegrationTest.java` | DB에서 발생한 상품명 유일 제약 위반이 `DUPLICATE_PRODUCT_NAME`으로 변환되는지 확인한다. 다른 제약 위반을 이름 중복으로 잘못 변환하지 않는지도 확인한다. |
| 수정 | `brand/interfaces/BrandHttpTest.java` | DB에서 발견한 브랜드명 중복이 기존 HTTP 상태·오류 코드로 응답되는지 확인한다. |
| 수정 | `product/interfaces/ProductHttpTest.java` | DB에서 발견한 상품명 중복이 생성·수정 API의 기존 HTTP 상태·오류 코드로 응답되는지 확인한다. |

서비스의 사전 중복 검사만 통과시켜 보는 데 그치지 않고, DB 유일 제약에서 실제로 발생한 오류를 처리하는 경로를 확인한다. 기존 상품·브랜드·좋아요·주문 테스트와 Checkstyle·ArchUnit은 삭제하거나 완화하지 않고 회귀 검사로 실행한다.

## 적용·검증 순서

1. 기존 데이터의 NULL·범위 위반·이름 길이·공백·활성 이름 중복을 조회한다. 위반 데이터가 있으면 임의 삭제·수정 없이 먼저 보고한다.
2. 엔티티 매핑과 기존 DB 적용 SQL, 이름 중복 오류 변환을 구현한다.
3. 격리된 MySQL에서 SQL을 직접 실행해 제약을 확인한다. 가격 1·10억 원, 재고 0·`int` 최댓값은 허용하고 범위를 벗어난 값은 거절하는지 확인한다. 별도 자동 테스트 클래스를 만들지는 않는다.
4. 같은 방식으로 이름의 길이·NULL·빈 값·앞뒤 공백, 활성 이름 중복 거절을 확인한다. 대소문자가 다른 이름·삭제 후 이름 재사용·상품의 다른 브랜드 내 동명은 허용되어야 한다.
5. 신규 스키마와 기존 스키마에 SQL을 적용한 결과를 확인한다. FK는 추가되지 않아야 한다.
6. 위 표의 오류 변환·HTTP 응답 테스트와 기존 회귀·Checkstyle·ArchUnit을 실행한다. 통과를 위해 기존 테스트·기대값을 완화하지 않는다.
7. 검증한 SQL로 기본 개발 DB에 반영하고 실제 테이블 정의를 다시 확인한다. MySQL DDL을 일반 데이터 트랜잭션처럼 전체 rollback할 수 있다고 가정하지 않는다.
