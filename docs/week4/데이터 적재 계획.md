# 데이터 적재 계획

작성일: 2026-10-12

## 목적

도메인·DB 규칙을 만족하는 상품 10,000개와 관련 데이터를 생성하고, CSV로 보관해 빠르게 반복 적재한다. 현재 생성할 데이터 버전은 브랜드별 균등 분포 하나다. 기준 요청은 브랜드 필터 + `price_asc` + 첫 페이지(`page=0`, `size=20`)로 둔다.

## 최초 기준 데이터 생성

- 상품 10,000개를 여러 브랜드에 균등하게 배분한다.
- 상품명은 브랜드와 관계없이 전체 상품에서 고유하게 생성하고, CSV로 내보내기 전에 전체 상품명 중복이 없는지 검증한다. 이는 브랜드 재배치 후에도 브랜드 내 상품명 중복이 생기지 않도록 하는 실험 데이터 생성 조건이다.
- 상품별 재고와 좋아요에 필요한 사용자를 함께 만든다.
- 가격과 좋아요 수는 다양하게 구성하고, 좋아요 0개·동점·인기 상품을 포함한다.
- Java 생성 스크립트에서 Datafaker와 고정 seed를 사용해 값을 만들고 CSV를 직접 생성한다. 도메인 객체 생성과 JPA 저장은 거치지 않는다.
- Datafaker는 이름 등 입력값 생성을 맡고, 스크립트는 ID 할당·고유성·참조 관계·건수·분포를 제어한다. 생성 시각과 수정 시각은 고정 기준 시각으로 채운다.
- 스크립트는 [도메인 규칙](../week2/domain-rules.yaml)과 실제 엔티티의 DB 매핑을 기준으로 생성 결과를 검증한다. Datafaker가 도메인 규칙을 자동으로 보장하는 것은 아니다.

### 생성·검증 조건

| 대상 | 조건 |
| --- | --- |
| 브랜드 | 이름은 Java `trim()` 적용 후 1~50자이며 중복이 없다. 이름 비교는 도메인 규칙대로 대소문자를 구분한다. |
| 상품 | 이름은 Java `trim()` 적용 후 1~100자이며 전체 상품에서 고유하다. Datafaker로 만든 이름에 고유 순번을 붙이되 최종 길이 제한을 지킨다. 가격은 1~1,000,000,000원이고, 존재하는 미삭제 브랜드를 참조한다. |
| 재고 | 각 상품에 재고 행이 정확히 하나 존재한다. 수량은 0 이상이며 Java `int`와 DB 컬럼의 표현 범위 안이다. |
| 사용자·좋아요 | 좋아요는 존재하는 사용자와 미삭제 상품을 참조한다. `(user_id, product_id)` 쌍은 중복되지 않는다. 상품별 목표 좋아요 수만큼 서로 다른 사용자를 선택해 관계 행을 만들고, 실제 관계 개수와 목표값이 같은지 검증한다. |
| 공통 컬럼 | 테이블별 ID는 양수이며 고유하다. `created_at`·`updated_at`은 필수로 채우고, 초기 데이터의 `deleted_at`은 NULL로 둔다. 실제 스키마의 컬럼명·자료형·길이·NULL 허용 여부·유일 제약에 맞춘다. |
| 전체 데이터 | 상품 10,000개, 설정한 테이블별 건수와 분포, 참조 누락과 중복 여부를 검증한다. 상품별 좋아요 수는 사용자 수를 넘지 않는다. |

CSV의 문자 인코딩·열 순서·따옴표와 이스케이프·NULL 표현·시각 형식은 적재 스크립트와 일치시킨다. 검증을 통과한 CSV만 기준 데이터셋으로 보관한다.

### CSV 필드별 유효 상태

아래 표는 현재 도메인 코드와 JPA 매핑을 대조한 생성 스크립트의 입력·검증 기준이다. DB 제약 표기는 매핑에 명시된 내용이며, 실험 DB의 실제 DDL을 조회한 결과는 아니다. 적재 스크립트는 스키마 생성 후 컬럼 자료형·길이·NULL 허용 여부·키 제약을 확인한다. 도메인 유효 범위와 DB 허용 범위를 모두 만족하는 값을 사용한다.

#### 모든 CSV의 공통 필드

출처: [BaseEntity.java](../../modules/jpa/src/main/java/com/loopers/domain/BaseEntity.java), [jpa.yml](../../modules/jpa/src/main/resources/jpa.yml).

| CSV 컬럼 | Java 자료형·DB 매핑 | 이번 데이터의 유효 상태·생성 기준 |
| --- | --- | --- |
| `id` | `Long`, PK, `IDENTITY` 자동 증가 | CSV에서 테이블별로 1부터 건수까지 직접 할당한다. NULL·0·음수·테이블 내 중복은 없다. 서로 다른 테이블의 ID가 같은 것은 허용한다. |
| `created_at` | `ZonedDateTime`, NOT NULL | 고정 기준 시각을 UTC로 기록한다. CSV 직접 생성이므로 JPA 콜백에 의존하지 않는다. |
| `updated_at` | `ZonedDateTime`, NOT NULL | 초기 데이터는 `created_at`과 같은 시각으로 기록한다. |
| `deleted_at` | `ZonedDateTime`, NULL 허용 | 모두 NULL이다. 삭제된 브랜드·상품·사용자·재고와 취소된 좋아요는 생성하지 않는다. |

날짜는 UTC 기준 `yyyy-MM-dd HH:mm:ss.SSSSSS` 형식으로 직렬화하며, 기준 시각은 초 단위로 고정해 소수부를 `000000`으로 둔다. 적재 세션도 UTC로 맞춘다. 고정 기준 시각은 생성 조건에 기록한다.

#### 브랜드: `brands.csv` → `brand`

출처: [Brand.java](../../apps/commerce-api/src/main/java/com/loopers/brand/domain/Brand.java), [BrandNameValidator.java](../../apps/commerce-api/src/main/java/com/loopers/brand/domain/BrandNameValidator.java). 관련 규칙: `INV-BRAND-01`, `INV-BRAND-02`.

| CSV 컬럼 | Java 자료형·DB 매핑 | 유효 상태·생성 기준 |
| --- | --- | --- |
| `name` | `String` — 별도 길이·NOT NULL·UNIQUE 어노테이션 없음 | NULL 불가. Java `trim()` 후 `String.length()` 기준 1~50. 전체 브랜드에서 대소문자를 구분해 중복 검사한다. Datafaker 이름에 브랜드 순번을 붙이고 최종 길이를 검증한다. |

공통 `id` 범위는 1~100이다. 이름 유효성은 DB 저장 성공 여부와 별개로 검증한다.

#### 사용자: `users.csv` → `users`

출처: [User.java](../../apps/commerce-api/src/main/java/com/loopers/user/domain/User.java).

사용자는 공통 필드만 갖는다. `id` 범위는 1~10,000이다. 이름·이메일·비밀번호·잔액 컬럼을 임의로 추가하지 않는다. 이번 CSV 묶음은 포인트·주문을 생성하지 않는다. 현재 [PointUseCase.java](../../apps/commerce-api/src/main/java/com/loopers/user/application/PointUseCase.java)는 포인트 행이 없는 사용자의 잔액을 0으로 처리한다(`INV-USER-22`).

#### 상품: `products.csv` → `product`

출처: [Product.java](../../apps/commerce-api/src/main/java/com/loopers/product/domain/Product.java), [ProductNameValidator.java](../../apps/commerce-api/src/main/java/com/loopers/product/domain/ProductNameValidator.java). 관련 규칙: `INV-PRODUCT-06`~`INV-PRODUCT-10`.

| CSV 컬럼 | Java 자료형·DB 매핑 | 유효 상태·생성 기준 |
| --- | --- | --- |
| `brand_id` | `Long` (`brandId`) — 별도 NOT NULL·FK 어노테이션 없음 | NULL 불가. `brands.csv`에 존재하는 미삭제 브랜드 ID 1~100. 상품 ID가 `i`이면 `((i - 1) % 100) + 1`로 배정한다. 각 브랜드에 정확히 100개가 속한다. |
| `name` | `String` — 별도 길이·NOT NULL·UNIQUE 어노테이션 없음 | NULL 불가. Java `trim()` 후 `String.length()` 기준 1~100. Datafaker 이름에 상품 순번을 붙여 전체 10,000개에서 고유하게 생성한다. 이는 브랜드 내 고유성보다 강한 실험 데이터 조건이다. |
| `price` | `long` | 소수 없는 정수, 1~1,000,000,000원. 범위 내에서 고정 seed로 생성하며 0·음수·NULL은 허용하지 않는다. |

공통 `id` 범위는 1~10,000이다. 이름의 고유 순번 공간을 먼저 확보하고 본문 길이를 제한한다. 최종 문자열에서 순번을 잘라내지 않는다. 이름 길이는 Java UTF-16 코드 단위 기준이며 UTF-8 바이트 수와 구분한다.

#### 재고: `stocks.csv` → `stock`

출처: [Stock.java](../../apps/commerce-api/src/main/java/com/loopers/product/domain/Stock.java). 관련 규칙: `INV-STOCK-14`.

| CSV 컬럼 | Java 자료형·DB 매핑 | 유효 상태·생성 기준 |
| --- | --- | --- |
| `product_id` | `Long` (`productId`), NOT NULL, UNIQUE | `products.csv`에 존재하는 상품 ID 1~10,000. 상품마다 정확히 하나의 재고 행을 생성한다. 참조 존재 여부는 스크립트가 검증한다. |
| `quantity` | `int` | 소수 없는 정수, 0~2,147,483,647. 음수·NULL 불가. 0은 품절이며 양수는 판매 가능한 재고다. |

공통 `id` 범위는 1~10,000이며, 생성 편의를 위해 `id = product_id`로 둔다. 이는 도메인 규칙이 아닌 생성 방식이다. `soldOut`은 `quantity == 0`으로 계산되는 응답값이므로 CSV 컬럼으로 만들지 않는다.

#### 좋아요: `likes.csv` → `product_like`

출처: [Like.java](../../apps/commerce-api/src/main/java/com/loopers/like/domain/Like.java), [LikeUseCase.java](../../apps/commerce-api/src/main/java/com/loopers/like/application/LikeUseCase.java). 관련 규칙: `INV-LIKE-23`~`INV-LIKE-25`, `INV-LIKE-45`.

| CSV 컬럼 | Java 자료형·DB 매핑 | 유효 상태·생성 기준 |
| --- | --- | --- |
| `user_id` | `Long` (`userId`) — 별도 NOT NULL·FK 어노테이션 없음 | NULL 불가. `users.csv`에 존재하는 사용자 ID 1~10,000. |
| `product_id` | `Long` (`productId`) — 별도 NOT NULL·FK 어노테이션 없음 | NULL 불가. `products.csv`에 존재하는 미삭제 상품 ID 1~10,000. |

공통 `id` 범위는 1~1,000,000이다. DB 매핑에는 `(user_id, product_id)` 복합 UNIQUE 제약 `uk_product_like_user_product`가 있다. 스크립트에서도 같은 쌍이 중복되지 않는지 검사한다. 상품별 좋아요 수는 0~10,000이며 전체 합계는 정확히 1,000,000이다. `like_count` 컬럼은 만들지 않고 관계 행 개수로 계산한다. 현재 취소 처리는 행을 삭제하므로 취소 상태의 행은 생성하지 않는다.

#### CSV 컬럼 순서와 적재 후 검증

각 CSV는 아래 헤더 순서로 출력하고, 적재 명령에서도 대상 컬럼을 명시한다. 테이블의 물리적인 컬럼 순서에 의존하지 않는다.

```text
brands.csv:   id,name,created_at,updated_at,deleted_at
users.csv:    id,created_at,updated_at,deleted_at
products.csv: id,brand_id,name,price,created_at,updated_at,deleted_at
stocks.csv:   id,product_id,quantity,created_at,updated_at,deleted_at
likes.csv:    id,user_id,product_id,created_at,updated_at,deleted_at
```

브랜드·사용자 → 상품 → 재고·좋아요 순서로 적재한다. 적재 후에는 필드별 조건뿐 아니라 브랜드당 상품 100개, 상품마다 재고 하나, 좋아요 쌍 중복 0건, 모든 참조 누락 0건을 확인한다. 이름의 대소문자 구분은 Java 문자열 비교 기준으로 검사해 DB collation에 따른 비교 차이를 피한다. 원본 CSV와 DB의 값·건수 일치도 확인한다.

### 기준 데이터 규모

| 대상 | 건수 |
| --- | --- |
| 브랜드 | 100개 |
| 사용자 | 10,000명 |
| 상품 | 10,000개 |
| 재고 | 10,000개, 상품마다 하나 |
| 좋아요 | 총 1,000,000개 |

좋아요는 총량을 유지하면서 상품별 0개·동점·인기 상품을 포함하도록 배분한다. 이 규모를 조회 부하를 관찰하기 위한 실험 시작값으로 사용한다.

## CSV 버전 관리와 분포 변경

데이터셋마다 브랜드·사용자·상품·재고·좋아요 CSV와 생성 조건·건수·분포·체크섬을 보관한다. 생성 조건에는 seed·기준 시각·Datafaker 버전·로케일·생성 스크립트 버전을 포함한다. ID도 CSV에 고정한다.

현재는 균등 분포 버전 하나만 생성한다. 비교용 편중 버전은 생성 범위에 포함하지 않는다.

| 버전 | 브랜드별 상품 분포 |
| --- | --- |
| 균등 | 100개 브랜드에 각각 100개 |

향후 브랜드 분포를 바꾸는 실험이 필요하면 다음 절차를 사용한다. 현재 스크립트의 생성 대상은 균등 버전뿐이다.

1. 검증된 기준 CSV 묶음을 복사한다.
2. 스크립트로 `products.csv`의 `brand_id` 열만 재배치한다.
3. 브랜드 존재·미삭제 여부와 브랜드별 상품 수·전체 상품 수를 검증하고, `brand_id` 이외의 값이 기준 CSV와 동일한지 확인한다.
4. 원본을 유지하고 새 데이터셋 버전과 체크섬·분포 정보를 저장한다.

상품 ID·상품명·가격·시각과 재고·사용자·좋아요 데이터는 버전 간 그대로 유지한다. 전체 상품명이 고유하므로 브랜드를 재배치해도 브랜드 내 상품명 중복이 생기지 않는다. 브랜드 재배치는 실험 데이터 생성에 한정하며, 기존 상품의 브랜드 변경을 금지하는 업무 정책은 유지한다.

## 실험 DB와 반복 적재

- 기본 개발 DB와 분리된 실험용 MySQL 컨테이너를 사용한다.
- MySQL 인스턴스 하나에 데이터셋 버전별 DB를 만들어 동시에 보관한다.
- 매번 빈 DB에 실제 프로젝트 스키마를 먼저 생성하고, 검증된 CSV를 `LOAD DATA`로 적재한다.
- 적재 경고·누락, 원본과의 값·건수 일치, 참조 관계·중복을 확인하고 검증을 통과한 DB만 실험에 사용한다.
- 애플리케이션의 접속 DB를 바꿔 데이터셋을 선택한다.
- 스키마 생성 이후 CSV 적재와 반복 실험에서는 `spring.jpa.hibernate.ddl-auto=none`을 사용한다. Hibernate의 자동 스키마 생성·변경·검사를 끄고, 앱 재시작 시 적재 데이터를 유지한다.

실험용 애플리케이션 설정:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: none
```
