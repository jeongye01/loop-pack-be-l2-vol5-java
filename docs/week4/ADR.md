# Redis 캐시 전략 ADR

## 2026-10-16 결정: 과제의 필수 보호 조건을 위해 DB revision 복원

과제 요구사항을 충족하기 위해 DB revision 방식을 복원한다. 과제가 revision 구현 자체를 강제하는 것은 아니다. [과제](../../.handoff/week4-과제.md)의 **늦은 채움·무효화 실패·Redis 복구 중에도 삭제 상품을 노출하지 않는 조건**을, 현재 Write Invalidate + TTL만으로 충족하지 못했기 때문에 선택했다. Lua는 사용하지 않는다.

- 상품·브랜드 변경은 `catalog`, 내 좋아요 변경은 `likes:{userId}`, 품절 상태 전환은 `stock:{productId}` revision을 데이터와 같은 DB 트랜잭션에서 변경한다. 롤백은 revision도 되돌린다.
- 캐시 키는 기존 v4 본문에 DB revision 접미사를 붙인다. 이전 고정 v4 키는 사용하지 않는다. revision은 UUID로 발급하는 변경 식별 토큰이며 숫자 증가 순서를 비교하지 않는다.
- miss에서는 REPEATABLE_READ 트랜잭션 안에서 revision과 원본을 읽는다. 늦게 끝난 옛 조회는 옛 revision 키에만 저장하므로 변경 완료 후 시작한 새 조회가 사용하지 않는다.
- hit에서도 DB revision을 확인한다. 통합 상품 응답은 기본 정보 revision 1회, 상품별 표시 revision 일괄 1회이며 비싼 상품·집계 원본 조회는 생략한다. Redis 오류에도 revision 확인은 DB를 사용한다.
- 상품별 재고·좋아요 수 캐시와 MGET, 로컬 Single Flight, 품절 상태가 변할 때만 재고 revision 갱신, TTL 5분 ±30초를 유지한다. 좋아요 수·순위는 기존 TTL 지연 정책을 유지한다.
- 비용: hit의 DB 접근, revision 쓰기 잠금 경합, TTL까지 남는 이전 버전 키의 메모리 사용이 발생한다. DB 장애 시 캐시만으로 응답하는 정책은 제공하지 않는다. 변경과 겹쳐 이미 진행 중인 조회는 그 조회 시점의 결과를 반환할 수 있다.
- 기존 Write Invalidate의 실패 재현 테스트는 `experiment` 프로필에서 `experiment.catalog-write-invalidate.enabled=true`를 명시할 때만 해당 방식을 사용한다. 기본·catalog-cache 경로는 DB revision이다. 과거 측정 결과는 현재 revision 성능 결과로 재사용하지 않는다.
- 배포 전 쓰기를 멈추고 [revision 테이블 SQL](migrations/05-add-read-cache-revision.sql)을 적용해 catalog 토큰을 갱신한다. 이전 인스턴스와 혼합 쓰기를 하지 않는다. 이번 작업은 로컬 복원·검증이며 배포와 운영 DB 변경은 하지 않는다.

검증: `./gradlew :apps:commerce-api:check :modules:redis:check --continue` — 2026-10-16 로컬 MySQL·Redis Testcontainers에서 BUILD SUCCESSFUL(2분 35초). 총 514개 중 513개 성공, 실패·오류 0개, opt-in 장시간 관찰 실험 1개 skip. 변경·늦은 채움 보호 26개, Redis 장애 복구 9개, 캐시 조회 37개와 Checkstyle·ArchUnit을 통과했다. 통합 hit의 두 revision 조회 사이 삭제가 커밋되는 경우도 새 DB 스냅샷에서 다시 읽는 테스트로 확인했다. 물리적 키 삭제·DB 0회에 대한 구현 검사만 revision 키 변경·revision SQL 2회로 맞췄고, 삭제 후 404·롤백·소유권·주문 판단의 업무 기대값은 유지했다.

아래의 revision 제거 및 Write Invalidate 결정은 실험 이력이다. 현재 결정은 이 절을 따른다.


## 2026-10-16 변경: Revision 구현 제거

현재 구현은 **Cache Aside + 커밋 후 Write Invalidate + TTL/Jitter + 로컬 Single Flight**를 사용한다. 아래 Revision 관련 내용은 과거 설계·실험 기록이며 현재 실행 경로가 아니다.

- `CacheVersions`, `CacheReadPolicy`, `ReadRevision` 엔티티를 제거한다. `catalog.cache.enabled`만으로 캐시 ON/OFF를 제어하고 별도의 `write-invalidate`·Revision 우회 모드는 없앤다.
- 캐시 키는 `v4:` API/파라미터 키를 그대로 사용한다. 요청마다 DB에서 버전을 조회하지 않으며 쓰기에서도 버전을 갱신하지 않는다.
- 상품·브랜드 CUD: 커밋 후 catalog 범위의 캐시 키를 삭제한다. 롤백에서는 삭제하지 않는다.
- 재고: 상품별 품절 여부를 저장한다. 잠금 조회 전후 `quantity == 0`이 바뀔 때만 해당 상품 키를 삭제한다. 상태를 확보하지 못한 저장·생성은 보수적으로 삭제한다.
- 좋아요 등록·취소: 해당 사용자의 내 좋아요 목록을 무효화한다. 상품별 좋아요 수와 순위는 기존 TTL 갱신 정책을 유지한다.
- TTL 기본값은 5분 ±30초, hit은 TTL을 연장하지 않는다. 실험 프로필의 최신순 첫 페이지 TTL 오버라이드는 유지한다.
- hit은 DB 트랜잭션 없이 처리한다. miss는 Single Flight 대표 요청만 DB 트랜잭션을 열고 원본을 읽는다. 재고·좋아요 수는 상품별 키를 MGET으로 읽는다.
- 기존 DB revision 테이블을 삭제하는 DDL은 실행하지 않는다. 기존 migration과 실험 보고서는 이력으로 보존한다.
- 전환 시 이전 인스턴스와의 혼합 쓰기를 피하고, 캐시 OFF 중 변경이 있었거나 기존 v4 키를 재사용하는 경우 쓰기를 멈춘 상태에서 관련 키를 비운 뒤 활성화해야 한다. 현재 작업에서는 배포·Redis 데이터 삭제를 실행하지 않는다.

정상 순차 변경·롤백·TTL·Single Flight·인증·주문 계약은 계속 검증한다. 삭제 실패·늦은 채움의 표시 최신성은 이전 Revision과 동등하지 않다. 삭제 비노출 보호 기준 변경 여부는 사용자 확인 중이며, 관련 실패를 숨기거나 성공으로 기록하지 않는다.


## 2026-10-16 추가: 표시 상태 전환으로 재고 갱신 범위 제한

상품별 재고 캐시는 수량이 아닌 품절 여부만 담는다. 기존 잠금 조회에서 얻은 상태를 트랜잭션 synchronization에 기억해 저장 후와 비교하며 추가 DB 조회는 하지 않는다. 수량이 달라도 품절 여부가 같으면 revision·캐시를 유지한다. 초기 생성 또는 이전 상태를 확보하지 못한 저장은 보수적으로 갱신한다. 사용자 승인에 따른 표시 캐시 정책 변경이며 실제 구매 재고 판단·API 계약은 그대로다. [43번 실험 계획](experiments/43-availability-revision-mixed/plan.md).

## 2026-10-16 변경: 상품별 재고·좋아요 수 캐시, revision ON 검증

상품 목록은 필터·정렬·페이지별로 저장하고, 재고와 좋아요 수는 **상품 ID별**로 저장한다. API는 기존 통합 응답을 유지한다. 여러 상품의 표시 값은 Redis MGET 한 번으로 읽고, 각 종류의 miss 상품 ID만 모아 원본을 일괄 조회한다. 상품별 SQL 조회를 반복하지 않는다. 기존 `ids` 조합 키는 읽지 않으며 TTL로 정리된다. 배포 전 기존 쓰기 인스턴스를 중단해 공통 stock revision을 갱신하는 구버전과 상품별 revision을 갱신하는 신버전이 섞이지 않게 한다. revision OFF 동안의 상품 변경까지 반영하려면 쓰기를 멈춘 상태에서 catalog revision을 갱신하고 전환한다.

| 캐시 | 키 본문(revision 접미사 제외) | 갱신 범위 |
| --- | --- | --- |
| 상품 목록 | 기존 필터·정렬·페이지 키 | 기존 catalog 그룹 유지 |
| 재고 표시 | `v3:products/{productId}/stocks` | `catalog` + **`stock:{productId}`** |
| 좋아요 수 | `v3:products/{productId}/like-counts` | `catalog`; 좋아요 변경은 기존 TTL 갱신 |
| 내 좋아요 목록 | 기존 사용자·페이지 키 | `catalog` + `likes:{userId}` |

| 쓰기 | 실제 무효화 범위 |
| --- | --- |
| 관리자 A 재고 변경·구매 확정 | 품절 여부(`quantity == 0`)가 달라질 때만 A의 `stock:{A}`를 같은 DB 트랜잭션으로 갱신. 100→99는 유지, 1→0·0→10은 갱신. B 캐시 유지 |
| 좋아요 등록·취소 | 해당 사용자의 내 좋아요 revision만 즉시 갱신. 상품별 좋아요 수·순위는 TTL 유지 |
| 상품·브랜드 CUD | 기존 catalog 갱신 유지. 목록·상세·브랜드·내 좋아요·상품별 재고·좋아요 수를 포함하는 넓은 범위이며, 이번 변경에서 세분화하지 않음 |
| 롤백 | 데이터와 revision 모두 롤백. 기존 캐시 버전 유지 |

catalog-cache 프로필은 revision ON(`write-invalidate=false`)으로 검증한다. 기본 TTL 5분 ±30초·로컬 Single Flight는 유지한다. 비교용 Write Invalidate 설정에서도 A 품절 여부가 달라질 때만 A의 상품별 재고 키를 삭제한다. 삭제 실패·늦은 채움에 대한 그 방식의 기존 한계는 해결됐다고 주장하지 않는다.

DB revision은 요청 간 캐싱하지 않는다. 상품별 revision을 한 번에 조회하며 원본 miss는 트랜잭션 안에서 다시 snapshot을 확보한다. 목록 revision 1회와 상품별 재고 revision 일괄 1회, 총 두 단계 조회로 합의했고 5개 읽기 경로에서 검증했다. 상품별 키·revision이 늘어나는 저장 비용은 후속 성능 실험에서 함께 관찰한다.

**아래 내용은 변경 전 설계 이력이다. `stock` 공통 그룹·`ids` 조합 키에 대한 설명은 위 결정으로 대체한다.**

## 2026-10-16 변경: TTL + Write Invalidate 기본 실험

당시 catalog-cache 프로필은 **Write Invalidate**를 사용했다. DB 커밋 후 관련 Redis 키를 삭제하며, hit/miss/write에서 DB revision을 읽거나 갱신하지 않는다. v4 키에는 revision 접미사를 붙이지 않는다. Single Flight와 기존 TTL 정책을 유지한다(부하 실험의 최신순 첫 페이지만 5초).

무효화 범위는 기존 그룹과 같고 롤백에서는 삭제하지 않는다. 삭제 실패·늦은 재채움 보호는 기본 구현의 한계로 재현하며, 정합성이 확보됐다고 미리 선언하지 않는다. [36번 계획서](experiments/36-write-invalidate/plan.md)에 부하와 실패 시나리오를 함께 정리했다.

아래 revision 관련 설명은 이전 설계·실험 기록이다. 비교용 구현은 남기지만 현재 프로필의 실행 경로와 구분한다.


## 설계 결정과 검토 항목

RDB가 원본이고 Redis는 Cache Aside로 사용한다. 무효화는 기존 DB revision 방식을 유지한다. 데이터 변경과 그룹 revision을 같은 DB 트랜잭션으로 갱신하고, 커밋 후 조회는 새 버전의 캐시 키를 사용한다.

| 항목 | 결정·검토 상태 |
| --- | --- |
| 기본 TTL | 전체 5분 — 좋아요 수·순위 포함 |
| Jitter | ±30초 — 실제 TTL 4분 30초~5분 30초 |
| 메모리 관리 | allkeys-lru / maxmemory 용량 미정 |
| Redis 장애 | RDB fallback |
| DB 보호 | Bulkhead 우선 적용, 허용 동시 요청 수 미정 |
| 추가 검토 | Circuit Breaker, 짧은 Redis timeout, Rate Limiter, Single Flight |
| 무효화 | 그룹별 DB revision 갱신. 개별 Redis 키 검색·삭제는 하지 않음 |
| 정합성 | 데이터·revision 함께 커밋/롤백. 늦은 재적재는 이전 버전 키에 격리 |
| 부하 거절 | HTTP 응답·재시도 정책 미정 |
| 정상 상태 목표 | 1,700 RPS, p99 ≤ 200ms |

Redis 장애 중 서비스 지속·DB 보호는 정상 상태 SLO와 별도로 검증한다. 기본 TTL 5분·Jitter ±30초와 revision 유지에 합의했다. 합의한 revision 유지·TTL 정책은 로컬 코드에 반영한다. 나머지 미정 항목은 계속 검토한다.

### 그룹 revision 방식

같은 그룹에 속한 캐시 키들이 DB의 공통 revision을 참조한다. 그룹 버전 하나를 바꾸면 이후 요청은 모두 새 버전 키로 조회한다. 기존 키를 찾아 일일이 수정·삭제하지 않으며, 옛 키는 설계의 TTL로 정리한다.

현재 구현의 그룹은 아래와 같다. 한 캐시가 여러 그룹의 revision을 함께 참조할 수 있다.

| 그룹 | 버전을 바꾸는 쓰기 | 영향을 받는 캐시 |
| --- | --- | --- |
| catalog | 상품·브랜드 CUD | 상품 목록·상세, 내 좋아요 목록, 브랜드 목록, 좋아요 수·재고 일괄 조회 전체 |
| stock | 재고 변경·주문 확정의 재고 차감 | 재고 일괄 조회 전체 |
| likes:{userId} | 해당 사용자의 좋아요 등록·취소 | 해당 사용자의 좋아요 목록 전체 |

개별 키 추적은 필요 없어지지만 **쓰기와 그룹의 연결은 유지해야 한다.** 새 쓰기 경로에서 revision 갱신을 빠뜨리면 옛 캐시가 재사용된다. 넓은 그룹은 변경 직후 miss를 늘릴 수 있으며 hit에도 DB revision 조회가 남는다. 좋아요 표시 수·순위는 현재 TTL로 갱신하며, 즉시 무효화 여부는 별도 검토한다.

### TTL과 Jitter

- 기본 TTL은 저장 시점부터 5분이다. 저장할 때마다 Jitter를 더해 여러 키의 만료가 한꺼번에 몰리는 것을 완화한다.
- Jitter는 ±30초로 확정한다. 캐시 저장 시마다 -30초~+30초의 무작위 값을 기본 TTL에 더하며, 실제 TTL은 4분 30초~5분 30초다.
- 좋아요 수·순위도 기본 TTL 5분으로 통일한다. 동일하게 ±30초 Jitter를 적용한다. 내 좋아요 목록은 TTL과 별개로 본인의 등록·취소를 반영해야 한다.
- TTL은 변경 시 무효화를 대체하지 않는다. 늦은 재적재·삭제 상품 비노출·무효화 실패 복구는 별도로 처리한다. Jitter도 인기 키 하나의 동시 miss를 막아 주지는 않는다.

### 쓰기 동작별 캐시 영향 범위

아래는 응답 내용이 영향을 받는 범위의 매핑이다. 실제 revision 그룹은 위 표처럼 더 넓게 묶여 있으므로 해당 상품의 키만 찾아 삭제할 필요가 없다. 그룹을 세분화할 때 참고하며, 현재 응답 필드를 기준으로 한다.

- **전체 목록**은 모든 정렬·브랜드 필터·페이지·크기를 포함한다. 내 좋아요 목록도 사용자별 모든 페이지를 포함한다. 상품·브랜드 정보 변경 시 영향받는 사용자를 역추적하지 않고 전체를 무효화하는 안이다.
- **소속 상품 상세**만 갱신하려면 브랜드별 그룹 또는 상품 ID 목록이 필요하다. 구현을 단순화하려면 브랜드 변경 시 상품 상세 전체를 무효화할 수도 있다.
- **해당 상품의 좋아요 수·재고**는 그 상품을 포함하는 모든 일괄 조회 캐시를 뜻한다. 현재 `ids` 조합 키에서 상품 하나의 키만 삭제할 수 있는 것은 아니다. 상품별 저장 또는 포함 키 추적 없이 처리하려면 해당 일괄 조회 캐시 전체를 무효화해야 한다.
- 상품 생성 시 신규 ID를 미리 조회한 빈 결과가 캐시돼 있을 수 있어 좋아요 수·재고 조회도 영향 범위에 포함한다. 상세 오류는 현재 캐싱하지 않는다.
- 좋아요 수·순위는 변경의 영향을 받지만 **TTL은 기본 5분으로 통일하며, 변경 시 즉시 무효화할지는 미정**이다. 내 좋아요 목록의 등록·취소 반영과 구분한다.
- 실제 변경이 커밋된 경우를 기준으로 한다. 롤백·중복 좋아요 등록·이미 취소된 좋아요·주문 생성만으로는 위 데이터가 바뀌지 않는다. 상품의 브랜드 변경은 현재 계약에서 금지되어 있다.

### 주의사항

| 항목 | 주의할 점 |
| --- | --- |
| TTL·LRU 역할 | TTL은 저장된 키의 수명을 제한하고 LRU는 메모리 공간을 확보한다. 늦은 재적재까지 포함한 전체 요청의 최신성 상한을 TTL만으로 보장하지 않는다. |
| revision 누락 | 모든 관련 쓰기가 데이터와 revision을 같은 트랜잭션에서 갱신해야 한다. DB revision 조회 실패 시 옛 버전 캐시로 우회하지 않는다. |
| 늦은 재적재 | 조회 시작 시 확보한 revision 키에 저장한다. 조회가 끝난 뒤 새 revision을 읽어 옛 결과를 새 버전 키에 저장하면 안 된다. |
| Redis 장애 | 느린 Redis를 기다린 뒤 DB까지 조회하면 지연이 누적된다. Redis timeout과 DB fallback 시간을 합쳐 요청 시간 예산을 잡는다. |
| DB 보호 | Bulkhead는 장애 fallback뿐 아니라 일반 miss·LRU 제거·복구 재적재의 DB 진입에도 적용해야 한다. 읽기 제한이 주문 등 핵심 쓰기에 필요한 DB 여유를 잠식하지 않는지 확인한다. |
| Bulkhead 한도 | 허용 동시 요청 수·대기 한도·초과 요청의 HTTP 응답·재시도 정책을 함께 정한다. 앱 인스턴스가 늘면 DB로 향하는 합산 동시성도 늘어난다. |
| 장애 복구 | 인기 키에 동시 miss가 몰리면 같은 DB 조회가 반복된다. Single Flight 등을 검토하되 DB 동시성 제한을 대신한다고 보지 않는다. |
| 성능 판정 | 거절률을 높여 p99만 낮아진 결과를 성공으로 보지 않는다. 실제 처리량·성공률·거절률·미시작 수를 함께 본다. |

삭제 상품 비노출·사용자 소유권·주문 금액·재고 판단은 표시 데이터의 일시적 지연 허용과 구분한다. 캐시 장애나 복구 중에도 기존 계약을 유지해야 한다.

### 검증할 흐름

| 상황 | 확인할 지표 |
| --- | --- |
| 정상 hit | 실제 전달 RPS·성공률·p99, Redis hit/miss·명령 지연·CPU·메모리, 원본 SQL 실행 수 |
| 인기 키 만료 직후 동시 miss | [20번 실험 계획](experiments/20-cache-stampede/plan.md): 중복 원본 조회·재적재·풀 대기·p99 |
| LRU로 miss 증가 | evicted_keys 증가, miss 비율, DB로 넘어간 요청 수·SQL 수·지연·CPU·I/O·Hikari active/pending |
| Redis 장애 | timeout·오류, fallback 시도·허용·거절 수, Bulkhead 실행 중 요청 수·대기 시간, DB 자원·p99 |
| 장애 복구 | 재적재 요청 수·동시성, DB 부하, 커밋된 revision 사용·옛 값 재노출 여부 |

요청 흐름은 `전체 요청 → hit / miss / Redis 오류 → DB 진입 시도 → 허용 / 거절 → 완료 / 실패`로 계측한다. 캐시 miss뿐 아니라 인증·revision 등 부가 DB 호출도 따로 집계해 실제 DB 부하를 빠뜨리지 않는다. 성공 응답만의 p99와 전체 성공률·거절률·미시작 요청 수를 함께 기록한다. 제한으로 요청을 버려 낮아진 p99만으로 SLO 달성을 선언하지 않는다.

## 현재 구현 기록

**그룹 DB revision과 전체 TTL 5분 ±30초를 사용한다.** EC2에는 `catalog-6cae328`로 API 분리·캐시 확장을 배포했고, 후속 `catalog-b2e84c4`에 Redis 타임아웃 설정을 반영했다. [캐시 배포·쓰기 검증](experiments/21-cache-path-validation/report.md)과 [타임아웃 배포 기록](experiments/22-cache-redis-recovery/report.md)을 구분한다. 아래 기능 테스트의 통과가 새 설계의 혼합 부하 SLO 달성을 의미하지는 않는다.

상품 목록·상세·내 좋아요 API는 분리 전 응답으로 복원한다. 상품 기본 정보·좋아요 수·품절 상태는 내부 캐시만 분리하고 서버가 일괄 조회 후 합친다. 아래 키의 `like-counts`·`stocks`는 내부 캐시 이름이며 외부 API가 아니다. 이 변경은 아직 배포하지 않았다.

| 읽기 경로 | 내용을 변경하는 쓰기 동작 | 키 본문 | TTL | 무효화 |
| --- | --- | --- | --- | --- |
| 상품 목록 최신순·가격순 | 상품 CUD / 브랜드 UD | `v3:products?sort={sort}&brand={brand}&page={page}&size={size}` | 5분 ±30초 | catalog revision |
| 상품 목록 좋아요순 | 위 동작 / 좋아요 등록·취소 | 위 키, sort=likes_desc | 5분 ±30초 | 상품·브랜드는 revision / 좋아요는 만료 |
| 상품 상세 | 상품·브랜드 UD | `v3:products/{id}` | 5분 ±30초 | catalog revision |
| 내 좋아요 목록 | 내 좋아요 등록·취소 / 상품·브랜드 UD | `v3:users/{userId}/likes?page={page}&size={size}` | 5분 ±30초 | catalog + 사용자 revision |
| 고객 브랜드 목록 | 브랜드 CUD | `v3:brands?page={page}&size={size}` | 5분 ±30초 | catalog revision |
| 관리자 브랜드 목록 | 브랜드 CUD | `v3:admin:brands?page={page}&size={size}` | 5분 ±30초 | catalog revision |
| 좋아요 수 일괄 조회 | 좋아요 등록·취소 / 상품·브랜드 D | `v3:products/like-counts?ids={ids}` | 5분 ±30초 | 좋아요는 만료 / 상품·브랜드는 revision |
| 품절 상태 일괄 조회 | 재고 변경·주문 확정 / 상품·브랜드 D | `v3:products/stocks?ids={ids}` | 5분 ±30초 | catalog + stock revision |

C 생성, U 수정, D 삭제. 모든 행에 캐시를 적용한다. 키 생성은 `CacheKeys`에서 관리하며 실제 Redis 키는 `캐시이름::키본문:rev=...`이다. 브랜드 미지정은 `all`, ids는 중복 제거·오름차순, 생략한 페이지·정렬 조건은 기본값으로 정규화한다.

## 읽기와 쓰기

- 읽기: 요청자·소유권 확인 → DB revision 조회 → `@Cacheable` → miss면 DB 조회·저장. Redis 오류는 DB로 우회하며 오류 지표를 남긴다.
- 쓰기: 기존 관리자·좋아요·주문 경로에서 데이터와 revision을 **같은 DB 트랜잭션**으로 변경한다. 커밋 이후 요청은 새 revision 키를 사용한다. 롤백은 revision도 취소한다.
- 늦은 재삽입: 변경 전 조회가 뒤늦게 캐시에 저장해도 이전 revision 키라 이후 요청이 사용하지 않는다. Redis 삭제 성공 여부에 의존하지 않는다.
- 삭제·사용자 경계·주문 판단은 TTL 지연 대상이 아니다. 모든 공통 조회 캐시는 저장 시점부터 5분 ±30초 TTL을 사용하고 hit은 만료를 연장하지 않는다. TTL이 모든 장애·동시 요청의 데이터 최신성에 대한 전역 상한을 보장하지는 않는다.

## 비용과 적용 조건

- catalog·stock revision은 공통 범위이므로 한 상품 변경도 관련 목록 전체를 논리적으로 무효화한다. hit에도 revision DB 조회가 남고 동시 쓰기는 공통 revision 행에서 경합할 수 있다.
- 동시에 발생한 cache miss를 하나로 합치는 처리는 아직 없다. 인기 키의 동시 재채움 비용은 혼합 부하에서 확인한다.
- 이전 revision 키는 TTL로 정리한다. TTL이 없던 v2 키와 격리하도록 키 버전을 v3로 올렸다. 기존 v2 키는 자동으로 TTL이 생기지 않으므로 재사용 중단 확인 후 별도 정리가 필요하다. Redis maxmemory 용량·제거 정책의 배포 설정은 아직 적용하지 않았다.
- `catalog-cache` 프로필로 활성화한다. 기존 고정 데이터 실험용 `experiment.latest-cache.enabled`와 동시 사용은 금지한다.
- 활성화·재활성화 전에 쓰기를 멈추고 [revision SQL](migrations/05-add-read-cache-revision.sql)을 적용한다. 캐시를 끈 동안 발생한 변경까지 무효화하도록 catalog revision도 갱신한다. 혼합 ON/OFF 쓰기 인스턴스로 운영하지 않는다.
- 신규 경로·직접 SQL 적재도 revision 갱신을 누락하면 안 된다. 모든 쓰기가 저장소 어댑터의 save/delete를 거치는 현재 경로를 기준으로 한다.

## 프론트 계약

목록·상세·내 좋아요 응답은 `id`, `name`, `price`, `brand`, `likeCount`, `soldOut`을 포함한다. 프론트는 한 번만 요청한다. 고객 브랜드 목록 추가는 유지한다. API 계약은 분리 전 `a6ba327`을 기준으로 복원했다.

서버는 페이지 ID를 모아 좋아요 수·재고를 각각 한 번에 읽는다. 통합 응답 자체는 캐시하지 않아 재고 변경 시 기본 정보 캐시를 유지하면서 품절을 갱신한다. 각 캐시의 TTL·revision 정책은 유지한다. 구성 요소와 revision은 하나의 읽기 트랜잭션에서 조회한다. 따라서 조회 도중 변경이 커밋되어도 같은 DB 스냅샷의 키를 사용하며, 다음 요청은 새 revision으로 읽는다. Redis 접근 중 DB 연결을 유지하는 비용은 후속 부하 측정에 포함한다. 주문 판단은 기존 DB 검증을 유지한다.

실행 순서는 [캐시 설계 적용 후 실행 계획](experiments/execution-plan.md)을 따른다.


## 고객용 브랜드 목록 API

관리자 목록과 분리한 `GET /api/v1/brands`를 브랜드 필터에 사용한다. 기존 고객 API와 같이 `X-USER-ID`로 사용자를 식별한다.

| 항목 | 결정 |
| --- | --- |
| 대상·응답 | 삭제되지 않은 브랜드의 `id`, `name` |
| 정렬·페이지 | 기존 브랜드 목록과 같은 createdAt DESC, id ASC. page=0, size=20 기본, size 1~100. content/page/size/totalElements 반환 |
| 캐시 키 | `v3:brands?page={page}&size={size}`. 관리자 키 `v3:admin:brands?...`와 분리 |
| TTL·무효화 | 5분 ±30초, catalog revision. 브랜드 CUD 후 커밋된 변경 반영 |
| 관리자 API | 기존 삭제 포함 목록·관리자 접근 제한 유지 |
| 프론트 | 정적 브랜드 JSON 대신 고객 목록 API에서 페이지별로 전체 브랜드를 받아 검색·선택 |

삭제 필터는 DB 페이지 조회와 전체 개수 계산에 모두 적용한다. 페이지를 읽은 뒤 앱에서 삭제 항목을 걸러 페이지가 비거나 개수가 어긋나지 않게 한다.


## 통합 API revision 조회 개선

각 통합 요청의 읽기 트랜잭션에서 필요한 catalog·stock(내 좋아요는 사용자 revision 포함)을 한 SQL로 조회해 불변 snapshot으로 전달한다. 키별 namespace 조합·순서와 없는 revision의 `0` 처리는 유지한다. snapshot은 요청 간 공유하지 않으며 Redis 장애에도 DB revision 조회는 우회하지 않는다. 읽기 트랜잭션 범위는 이번 비교에서 유지한다.

### 통합 응답의 표시 캐시 일괄 읽기

상품 목록 GET에서 ID를 얻은 뒤 좋아요 수·재고 키를 Redis MGET 한 번으로 읽는다. 서로 다른 캐시 키와 revision·TTL 5분 ±30초는 유지하며, 부분 miss는 해당 원본만 조회해 기존 CacheManager 정책으로 저장한다. hit의 TTL은 연장하지 않는다. Redis 장애 fallback과 손상 JSON 제거는 유지한다. DB 읽기 트랜잭션 범위 변경은 별도 비교 대상으로 남긴다.
