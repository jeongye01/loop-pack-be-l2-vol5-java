# 캐시 변경·장애 보호 검증 결과

2026-10-15, 로컬 실제 MySQL·Redis Testcontainers 기준.

| 검증 항목 | 결과 |

추가한 보호 조건은 **3개 시나리오 × 장애/복구 2가지 = 6개 모두 통과**. 기존 복구 테스트 포함 7개, 실패·오류·건너뜀 0개. [실행 결과](experiments/22-cache-redis-recovery/protection-results.json)

이는 개선 전 개별 검사 결과다. 당시 후속 전체 회귀에서 **기존 복구 테스트의 앱 자동 재연결 확인이 다시 실패**했다. 당시에는 전체 장애·복구 검증을 완료로 판단하지 않고 관련 체크리스트를 미완료로 유지했다. 10초 재연결 대기는 테스트의 유한한 관찰 범위이며 합의된 서비스 SLO는 아니다.

**개선 전 전체 검사: 450개 중 449개 통과·1개 실패**, 오류·건너뜀 0개. 추가한 보호 조건 6개는 전체 검사에서도 모두 통과했고, 실패는 기존 자동 재연결 검사 1개다. Checkstyle·ArchUnit은 통과했다. [전체 검사 결과](experiments/22-cache-redis-recovery/protection-full-check.json)

반복 중단을 같은 앱 연결에서 실행한 초기 검사에서는 **약 60초 대기·재연결 확인 실패**도 관측됐다. 시나리오별 컨텍스트를 격리한 정확성 검증의 성공과 별개로, 반복 장애의 지연·재연결 안정성은 후속 확인이 필요하다. EC2·부하 상태까지 검증한 결과는 아니다.

## 재연결 실패 원인 분석

DEBUG 로그를 추가한 재현에서 **Redis 명령 기본 타임아웃 60초와 재연결 대기 증가**를 확인했다. 장애 중 조회가 60,168ms 걸렸고, Lettuce 재연결 간격은 최대 30초까지 늘었다. Redis 서버는 다시 PONG을 반환했지만 테스트는 앱 연결을 약 10초만 기다려, 다음 재연결 시도 전에 실패했다.

이번 재현의 원인은 확인했지만 이전 모든 실패가 동일 원인이라고 확정하지 않는다. 진단 당시에는 운영 설정을 수정하지 않았고, 이후 실제 재연결 성공도 해당 관찰 범위에서는 확인하지 못했다. 테스트 대기만 늘려 장애 중 60초 지연을 해결한 것으로 보지 않는다.

## 설정 개선 후 최종 결과

명령·연결 타임아웃 **각 100ms**, 재연결 대기 **최대 1초**로 변경했다. 기존 복구 검증을 유지하고 3회 반복 및 장애 조회 5초 미만 회귀 검사를 추가했다.

- 단독 복구 3회 + 보호 조건 6개 통과. 수정 상품 조회 249·229·13ms, 앱 연결 확인 81·56·57ms.
- 전체 회귀에서도 복구 3회 통과. 수정 상품 조회 12·218·53ms, 앱 연결 확인 51·99·42ms.
- 테스트 결과 **452개 통과**, 실패·오류·skip 0개. 전체 회귀 448개 + 직전 실행한 비동기 로그 4개(UP-TO-DATE). Checkstyle·ArchUnit 통과.

[최종 전체 결과](experiments/22-cache-redis-recovery/timeout-fix-full-check.json) · [단독 반복 결과](experiments/22-cache-redis-recovery/timeout-fix-focused.json)

로컬 컨테이너에서 이전 실패의 재검증을 마쳤다. EC2 배포·장애 부하 p99는 별도다. 명령별 100ms 제한은 API 전체 100ms 제한이 아니며, 이번 결과로 모든 네트워크 장애에서의 복구를 보장하지 않는다.

후속 EC2 배포 완료: `b2e84c4`, health UP·브랜드/최신순 상품 조회 HTTP 200 확인. [배포 기록](experiments/22-cache-redis-recovery/deployment.json). 장애 부하 SLO는 아직 별도 검증 대상이다.
